# 行业级 Agent 趋势判断：产品表面与生产治理

> 本文档拆自 [行业级Agent趋势判断设计文档.md](../行业级Agent趋势判断设计文档.md)，是行业级 Agent 趋势判断设计文档包的一部分。

## 核心产品表面

Weekly 的行业层固定为五段式：

1. `行业主判断`
   - 本周是否存在核心行业趋势。
   - 行业证据覆盖是否完整。
   - 哪些证据轴本周缺失或降级。
2. `核心行业趋势`
   - 已满足核心趋势门槛的行业方向主张。
   - 每条趋势显示主导证据轴、辅助证据轴、缺失/反证轴和下周观察点。
3. `观察中趋势与风向探针`
   - 尚未成为核心趋势，但具备跨轴信号或前置信号的方向。
   - 风向探针必须明确写成“可能方向”，不能写成已成立趋势。
4. `项目热度簇`
   - 项目/开源轴很强，但行业外部证据不足的方向。
   - 它只作为落地样本和补证触发器。
5. `证据不足与缺口账本`
   - 被搜过但证据不足、工具不可用、来源冲突或 Agent relevance 不足的方向。
   - 用户能看到缺的是哪个轴，下一步应该补什么。

用户可见等级语义冻结如下：

| 等级 | 用户读法 | 不能做的事 |
| --- | --- | --- |
| `core_industry_trend` | 这个 Agent 行业方向本周已经形成较强行业主张 | 不能只靠项目数量、资本、政策、新闻或宣传中的某一项升级 |
| `observing_industry_trend` | 这个方向有多轴证据，但还未达到核心趋势 | 不能和核心趋势混写成同等确定语气 |
| `wind_probe` | 这是前置信号，值得观察但尚未落地确认 | 不能写成技术成熟或商业已验证 |
| `project_heat_cluster` | GitHub / 开源活动强，但行业外部确认不足 | 不能进入行业主叙事 |
| `insufficient_evidence` | 有线索或被搜过，但不足以形成趋势判断 | 不能静默消失，也不能伪装成没有信号 |

## 生产级产品与治理边界

本设计的目标态不是只生成一段更长的 weekly 文案，而是提供一个可运营、可复盘、可审批的行业趋势判断面。ExecPlan 不得把以下内容降级成“后续运营优化”。

### 用户工作流与决策场景

主要用户是需要判断 Agent 行业方向是否值得继续跟踪、研究、投资时间或进入产品路线讨论的内部使用者。Weekly 行业层的标准使用路径冻结为：

1. 用户先读取 `行业主判断`，确认本周是否存在核心行业趋势，以及行业证据窗口是否完整。
2. 用户进入 `核心行业趋势` 或 `观察中趋势与风向探针`，查看每条主张的十轴矩阵、主导证据、缺失轴和反证轴。
3. 用户下钻到 `source_trace_refs`，核查关键 event、source、tool route、agent contribution 和 counter-evidence。
4. 用户根据 `what_to_watch_next_week_cn` 形成下一周观察任务，而不是从模型自由生成的新建议中临时挑选。
5. 当发现明显误判、来源错误、证据过期或敏感信息风险时，用户必须能进入人工复核 / 覆盖流程。

用户可见信息架构必须遵守：

- 默认页只展示五个等级分区、每条趋势的裁决理由和证据矩阵摘要。
- 下钻页展示 claim ledger、event/source 追溯、agent contribution、tool coverage、counter evidence、message/artifact lineage。
- `partial / missing / unavailable / stale / needs_review` 不能被隐藏在 tooltip 或日志中；凡是影响趋势等级的状态必须在 weekly 用户表面可见。
- 十轴矩阵必须同时区分“`required` 但缺失”和“`not_material_for_archetype`”；后者可见，但不得被渲染成用户需要 same-run 补齐的主缺口。
- weekly 头部必须区分展示 `evidence_window_status`、`publication_readiness_status` 和 `governance_load_status` 的摘要，不能只给一个模糊总状态。
- 空结果不是“没有行业趋势”的同义词。只有证据窗口完整且裁决规则执行成功时，才能表达“本周未发现核心行业趋势”；否则必须表达“行业证据不足 / 降级”。
- internal weekly 与 public weekly 的阻断口径必须分开表达；公开阻断不得自动改写 internal ledger 的 tier 语义。

### SLO、成本与运行预算

当前设计的运行口径冻结如下，ExecPlan 可以细化实现指标，但不得删除这些预算维度：

| 预算项 | 设计口径 | 失败 / 升级处理 |
| --- | --- | --- |
| freshness SLO | weekly 消费的 daily evidence pack 默认覆盖最近 7 个自然日；缺失天数必须进入 `evidence_window_status` 并同步反映到聚合 `industry_window_status` | 缺失超过 ExecPlan 阈值时，行业层降级为 partial 或 unavailable |
| weekly generation latency | 行业层不得无限等待外部 Agent / 工具；每个 Agent 和工具 route 必须有 timeout | timeout 产出 `unavailable / partial`，不得阻断项目级 weekly |
| source freshness | `source_published_at` 与 `observed_at` 必须保留，用于判断 stale evidence | stale evidence 不能作为核心趋势主导证据，除非有更新来源复核 |
| tool cost budget | 每个 evidence axis 必须能设置 primary / secondary / fallback / last_resort 的调用预算 | 超预算时进入降级 route，并记录 cost reason，不得静默跳过轴 |
| manual review capacity | `needs_review` 项必须有队列，不得只写入日志 | 超过复核容量时仍需展示待复核数量和受影响趋势 |
| public-safe budget | 公开 artifact 验证必须在 weekly 消费前完成 | public-safe 失败的 artifact 不得进入 weekly |

当前默认数值地板冻结如下。ExecPlan 可以基于本地运行成本细化或收紧，但不得删除这些默认值；如需放宽，必须在 ExecPlan 中写明理由、影响范围、降级语义和对应测试。

| 项 | 默认值 | 降级 / 阻断规则 |
| --- | --- | --- |
| `evidence_window_status` | 只衡量 7 日证据窗口和 lineage 是否足够。`ok` 需满足 `usable_day_count >= 5`、`recent_3d_usable_day_count >= 2` 且 lineage 完整。 | `usable_day_count=3-4` 或最近 3 日不足时为 `partial`；`1-2` 为 `missing`；关键 lineage 非法、超过半数轴失败或 claim ledger 缺审计链时为 `failed`。 |
| `publication_readiness_status` | 只衡量行业层 public-safe / publication snapshot 是否允许公开消费。 | 局部 claim 被阻断时为 `partial_blocked`；整层公开输出不可生成时为 `blocked`。 |
| `governance_load_status` | 只衡量 fallback、预算超限、review backlog 等治理负载。 | fallback / backlog / budget 压力升高时进入 `stressed` 或 `saturated`，但不得直接偷换成“证据窗口失败”。 |
| `industry_window_status` | 面向用户总览的聚合摘要。 | 只能由前三类状态汇总得出；不能再单独承载证据、公开阻断和治理积压三种语义。 |
| daily pack 新鲜度 | weekly 只默认消费最近 `7` 个 Asia/Shanghai 自然日；单个 pack 生成时间晚于目标日期 `36h` 以上需标 `stale_pack`。 | stale pack 可参与背景，但其事件不能作为核心趋势主导证据，除非 source freshness 另有更新证据。 |
| weekly 行业层总等待 | 默认总等待上限 `30min`，不得无限等待外部 Agent / 工具。 | 超过上限时停止行业层未完成任务，输出 partial / unavailable，并继续项目级 weekly。 |
| `task-timeout-profile.v1` | 不再按 Agent 一刀切；必须按 task profile 设 timeout。默认：`fast_feed_scan=5min`、`oss_api_scan=8min`、`academic_metadata_scan=12min`、`paper_fulltext_or_benchmark_check=18min`、`finance_filing_or_ir_check=20min`、`policy_official_doc_check=20min`、`normalization_merge=5min`、`audit_pass=8min`、`tier_decision=5min`。 | timeout 必须生成 `failure_notice.v1` 或 contribution `failed/unavailable`；不同 task profile 不得共用一个保守默认值后再靠静默重试掩盖失败。 |
| `tool-call-timeout-profile.v1` | 不再按 route 统一 `90s`；必须区分调用形态。默认：metadata / feed / API 调用 `90s`，official doc / PDF / release page 抓取 `120s`，benchmark / fulltext 检查 `180s`，last_resort 单 URL `45s`。 | 超时先尝试同 profile 的替代 route；全部失败时 `active_route_level="none"` 且轴为 `unavailable`。 |
| route 重试 | 同一 tool route 默认最多 `2` 次重试，且必须共享 `correlation_id` 并使用不同 `message_id`。 | 重试耗尽后不得静默换工具；必须记录 `degradation_reason_codes`。 |
| `axis-runtime-budget-profile.v1` | 不再全轴统一；每个 axis family 必须按 profile 设置 daily run 调用预算。 | 超预算时停止扩展采集，保留已得证据并标 `budget_exceeded`；不得把未覆盖写成无趋势。 |
| source-class priority | 政策、金融、官方产品发布三类高权威轴必须优先尝试官方结构化或官方自有文档来源；发现型 Agent 只负责找线索、补元数据和提取候选引用。 | 如果只拿到搜索聚合、新闻转述或研究 Agent 摘要而没有 canonical fetch，则相关轴最高只能为 `weak` 或 `needs_review`。 |
| 高成本 / 授权受限来源 | `cost_tier="high"`、`license_risk="high/unknown"` 或 `access_mode="optional_paid/human_exception"` 不得成为当前自动化硬依赖。 | 只能进入 `needs_review`、`optional_paid`、`human_exception_required` 或 `unavailable` 状态。 |
| seed monitoring tier | seed registry 必须完整 materialize，但不要求所有 seed 同频主动扫描。默认只有 `core_monitor` 进入常规主动扫描；`watchlist` 由触发信号或轮巡进入；`cold_archive` 只做低频健康检查和实体对齐。 | 不得因为预算不足把未主动扫描的 `watchlist/cold_archive` 写成“设计未覆盖”；必须保留 tier、原因和可触发入口。 |
| watchlist / archive rotation budget | `watchlist` 与 `cold_archive` 不能无限轮巡。 | 没有显式 rotation budget 时，不得默认扫描全部 `watchlist` 或 `cold_archive`。 |
| manual review capacity | 不再只冻结一个全局条数；必须先分 `P0/P1/P2`。默认：`P0` 为 same-run blocking、`P1` 为 `24h` 内处理、`P2` 允许进入 backlog；可参考单次 weekly run `P0<=3`、`P1<=5`、`P2<=20`。 | 超过容量时必须首先体现在 `governance_load_status` 与受影响 claim 的 `needs_review / blocked_public_output`，而不是直接把证据窗口口径写成失败。 |
| high-impact override review | tier override、authority promotion、public-safe failure、claim suppression 默认必须人工或双 Agent 复核。 | 未完成复核不得被当作通过；过期 review 必须进入 `expired` 并保留 audit。 |
| public-safe gate | 公开 weekly 消费前 public-safe artifact 通过率必须为 `100%`。 | 任一公开 artifact public-safe 失败时，不得进入公开 weekly / public projection；internal weekly 可保留，但相关 claim 必须进入 `blocked_public_output` 或 `needs_review`，行业层可降级，主 weekly 保持项目级输出。 |
| citation trace floor | `source_trace_refs` 默认可解析率不得低于 `0.98`；核心趋势关键引用必须 `100%` 可解析。 | 低于地板时核心趋势不得输出为 `high` confidence；关键引用缺失时不得进入 core。 |

成本策略必须体现“高价值来源优先、低确定性扩展受控”。高成本、授权受限、登录态或不可公开复现的来源可以作为 local-only raw input 或人工复核材料，但不能绕过 canonical artifact 和 public-safe 边界。

### `axis-activation-policy.v1`

高成本轴不能靠“默认全扫”或“默认不扫”这两种极端方式落地。当前设计补充冻结 `axis-activation-policy.v1`，用于约束 `capital_finance`、`policy_regulatory`、`policy_research_thinktank`、学术全文/benchmark 深查和高成本 official fetch 的激活条件。

每个高成本 axis family 至少必须定义：

- `activation_cues`
- `promotion_threshold`
- `hold_conditions`
- `skip_with_reason_codes`
- `deep_check_trigger_budget_class`
- `pre_admission_allowed_actions`
- `post_admission_unlock_conditions`

执行约束：

- `capital_finance`、`policy_regulatory` 和高成本学术深查默认不得在所有 topic 上无差别全量激活；必须先命中显式 cue、候选 materiality 或 authority 需求后再进入深查。
- `capital_finance`、`policy_regulatory`、高成本 academic fulltext / benchmark 深查和高成本 official fetch，在 `claim family fold / overlap collapse` 完成且候选尚未通过 `claim-admission-budget-profile.v1` 之前，默认只允许低成本 discovery、context、watch 或 metadata 级动作；不得提前消耗 official fetch、全文深查或高权威核验预算。
- 只有 admitted claim 通过 `claim-runtime-budget-profile.v1` 与 `shared-capacity-policy.v1` 的仲裁后，才允许解锁对应 axis family 的 deep check；不得把“先查了再说”当成 admission 前默认策略。
- 未命中激活条件时，系统可以保留发现型线索、context 或 watch 信号，但不得伪装成该高成本轴已经完成 canonical 覆盖。
- 激活策略必须与 `axis-runtime-budget-profile.v1`、`claim-runtime-budget-profile.v1` 联动；不能一边定义 budget，一边让 activation policy 失控地触发全部深查。
- 若因预算、容量或 stop policy 未进入深查，必须输出稳定 `reason_code`，并体现在 `tool_status_report`、coverage 或 claim 缺口中；不得静默跳过。

### `canonical-fetch-stop-policy.v1`

official-first 的目标是优先命中高权威 canonical source，不是为了“再试一次也许就能找到”而无限烧预算。当前设计补充冻结 `canonical-fetch-stop-policy.v1`，专门约束 `policy_regulatory`、`capital_finance`、`product_vendor_release` 等高权威轴何时必须停止继续追官方源，并把缺口显式写成可审计状态。

最小停止条件如下：

1. 已尝试该 axis / claim 允许的 `primary route`。
2. `primary route` 失败后，已尝试对应 `secondary route`。
3. 若仍失败，已尝试当前 policy 允许的 `fallback route`，且未命中禁止继续扩张的 veto。
4. 已达到该 claim / axis 的 `max_canonical_fetch_attempts` 或对应 `claim-runtime-budget-profile.v1` 的 official fetch 上限。
5. 或命中以下任一停止原因：
   - `license_risk_high`
   - `access_mode_optional_paid`
   - `human_exception_required`
   - `timeout_budget_exhausted`
   - `no_canonical_source_available`
   - `public_fetch_disallowed`

执行约束：

- 达到 stop policy 后，系统必须输出 `stop_reason_code`、`attempted_route_refs`、`active_route_level` 和受影响 axis / claim；不得继续无限扩张抓取。
- 停止 canonical fetch 不等于 claim 消失；默认只能进入 `needs_review`、`unavailable`、`weak`、`partial` 或相应缺口状态。
- 若 canonical fetch 被 stop policy 阻断，但已有非官方候选来源，系统可以保留其作为 `context`、`watch`、`ordinary` 或 `needs_review` supporting input；不得伪装成 official-first 已满足。
- `canonical-fetch-stop-policy.v1` 只解决“什么时候诚实停下”，不降低目标标准；任何停止都必须可 replay、可审计、可解释。

### 运行时间层分层与 same-run 约束

目标态能力必须完整，但不要求所有高成本能力都在同一轮 weekly run 里临时完成。当前设计冻结三层运行时间层：

| 时间层 | 默认承载内容 | 对 weekly 的约束 |
| --- | --- | --- |
| `day-level prerequisite` | 专责搜寻 Agent 常规扫描、tool route 选择、source-chain 去重、Fact 归并、普通 authority review、daily pack 落账 | 默认应在 weekly 前准备好；finance / policy / academic 深查的常规材料优先前置到这一层 |
| `weekly decision-critical` | claim-builder、已 admitted claim 的 material audit、少量 single-gap 补证、headline / public-safe / blocking 裁决 | 只处理会影响本轮主叙事或公开消费的关键缺口，不承担长尾治理清洗 |
| `post-weekly governance` | `P1/P2` 复核、长尾 authority 清洗、watchlist / cold archive 补扫、长期 topic / alias 词表扩充、显式 rerun backlog | 可以影响后续窗口或 rerun，但不得静默改写已发布 weekly |

冻结规则：

- 高标准目标不变；分层只约束“何时完成”，不删减“必须存在什么能力”。
- 只有命中 `tier_blocking`、`impact_scope=public_output_only`、`blocking_output_scope="public_output"`，或正在阻断既有 headline core 的争议，才允许占用 same-run blocking 容量。
- 未命中 same-run blocking 的缺口，默认只能影响 `decision_confidence`、`coverage_audit_state`、`consumer_readiness_state` 或公开分桶；不得因为本轮未处理就把 claim 静默改写为不存在。
- `day-level prerequisite` 未完成应优先暴露为窗口缺口、coverage 缺口或 authority hold，不应把本应前置的工作无上限挤进 weekly 总等待。

容量分层补充冻结如下：

- same-run 审计、补证和 `P0` 复核容量只保留给会影响 `headline core`、`tier_blocking`、`impact_scope=public_output_only` 或 `blocking_output_scope="public_output"` 的 claim。
- 容量不足时，系统默认动作是限制消费范围，而不是修改事实判断：应优先下调 `decision_confidence`、`coverage_audit_state`、`consumer_readiness_state` 或公开分桶，不得把本应保留的 claim 静默改写为“不存在”。
- 未进入 same-run 高优先级队列的 claim 不得消失；必须至少保留在 internal ledger、`watchlist_only`、`needs_review` 或 `insufficient_evidence` 等可审计分桶中。

### `run-critical-path-budget.v1`

仅有 timeout、axis budget、claim budget 和 shared pool 还不够回答“same-run 最多允许这条 claim 在关键路径上走多深、重试几次、耗多久”。当前设计补充冻结端到端关键路径预算：

每个 admitted claim 至少必须定义：

- `critical_path_class`
- `max_end_to_end_minutes`
- `max_cross_agent_hops`
- `max_full_reaudit_rounds`
- `max_same_run_gap_loops`
- `max_late_result_reopens`
- `max_publication_hold_minutes`

默认关键路径预算地板如下：

| `critical_path_class` | 适用对象 | 默认端到端预算 |
| --- | --- | --- |
| `critical_headline` | 已达 `core_industry_trend`、或正在阻断既有 headline core 的 claim | `max_end_to_end_minutes=18`、`max_cross_agent_hops=6`、`max_full_reaudit_rounds=1`、`max_same_run_gap_loops=1`、`max_late_result_reopens=1` |
| `high_priority` | 距离 `core/observing/wind_probe` 仅差一个 material gap 的 claim | `max_end_to_end_minutes=12`、`max_cross_agent_hops=5`、`max_full_reaudit_rounds=1`、`max_same_run_gap_loops=1`、`max_late_result_reopens=0` |
| `deferred_followup` | 长尾候选、重复候选或本轮不会改变主叙事的候选 | 默认不得进入 same-run 关键路径，只能进入后续窗口、watchlist 或治理队列 |

执行约束：

- same-run 关键路径预算是 claim 级硬约束，不得通过“再补一次也许就好了”的临时判断突破。
- 同一 claim 在 same-run 内最多允许一次完整 `gap_followup -> normalization -> audit -> tier_decider` 闭环；若还需要第二次完整重跑，只能进入下一 run 或显式 rerun。
- 任何会触发 full re-audit 的补证，都必须先检查剩余 `max_end_to_end_minutes` 与 `max_full_reaudit_rounds`；预算不足时默认保留 claim、下调 `decision_confidence` / `coverage_audit_state`，而不是继续拖延 weekly 发布时间。
- `critical_headline` 的 same-run allowed micro-task set 必须显式冻结为“小而关键”的补证集合：默认最多允许一次高成本 canonical fetch（`paper_fulltext_fetch`、`benchmark_or_leaderboard_check`、`filing_fetch_and_section_parse`、`transcript_fetch_and_segment`、`official_pdf_fetch + pdf_parse_and_anchor_extract` 五选一）和一次 full re-audit；超出则必须转入 `day-level prerequisite`、`post-weekly governance` 或显式 rerun。
- 任何单个 micro task 只要其 timeout 已逼近当前 claim 剩余 `max_end_to_end_minutes`，或执行后无法为 `publication_snapshot_at` 保留至少 `5min` 发布窗口，就不得再进入 `weekly decision-critical`；默认只能前置到 `day-level prerequisite` 或后置到治理队列。
- `publication_snapshot_at` 前为 public packaging 至少预留 `5min`；不得把全部 same-run 时间耗尽在上游补证，最后让 weekly packager 无窗口完成发布。

### `same-run-eligible-micro-task-matrix.v1`

是否“理论上重要”不足以决定一个高成本动作能否进入 same-run。当前设计补充冻结 `same-run-eligible-micro-task-matrix.v1`，专门回答“这个 micro task 在当前 claim 剩余关键路径预算下，是否仍然可执行”。

每个会消耗 same-run 关键路径的 micro task 至少必须显式计算：

- `micro_task_id`
- `critical_path_class`
- `remaining_end_to_end_minutes_before_start`
- `estimated_total_minutes_if_started`
- `required_downstream_reserve_minutes`
- `same_run_eligible`
- `ineligible_reason_codes`

默认 eligibility matrix 冻结如下：

| `critical_path_class` | 默认允许进入 same-run 的 micro task | 额外 eligibility gate |
| --- | --- | --- |
| `critical_headline` | metadata / HTML fetch、一次高价值 canonical fetch、一次 full re-audit | 启动前必须证明：执行后仍能为 `audit_pass + tier_decision + publication reserve` 留足剩余预算；否则该动作即使重要，也只能转为 `missing / partial / needs_review` 或后续窗口处理 |
| `high_priority` | metadata / HTML fetch、低到中成本确认动作 | `finance_filing_or_ir_check`、`policy_official_doc_check`、`transcript_fetch_and_segment`、`filing_fetch_and_section_parse` 这类高成本动作，只有在核心材料已于 `day-level prerequisite` 预抓取、本轮只剩局部解析或单次确认时才可进入 same-run；否则默认 same-run ineligible |
| `deferred_followup` | 无 | 默认不得进入 same-run 高成本路径，只能转 backlog、watchlist 或后续 rerun |

执行约束：

- 若某 micro task 的默认 timeout 已经大于当前 claim 剩余 `max_end_to_end_minutes`，则该动作默认 `same_run_eligible=false`；不得以“再试一次也许就好”突破关键路径预算。
- same-run eligibility 必须按 claim 当下剩余预算实时计算，而不是只按 task family 的理论允许性判断。
- `same_run_eligible=false` 不等于否定该能力目标；它只表示当前 run 不能继续执行，系统必须把缺口显式落成 `missing`、`partial`、`degraded`、`needs_review` 或下一轮 follow-up。
- 对 finance / policy / high-cost academic 的 canonical fetch，设计目标仍然完整保留；但如果当前窗口只剩不足以完成该动作加下游审计/发布保留时间的预算，系统必须诚实停下，而不是在规则上允许、运行上注定超时。

`task-timeout-profile.v1` 冻结如下：

| task_profile | 默认 timeout | 适用任务 |
| --- | ---: | --- |
| `fast_feed_scan` | `5min` | 新闻、RSS、社区、feed 型快速扫描 |
| `oss_api_scan` | `8min` | GitHub、包生态、benchmark 或开源 API 扫描 |
| `academic_metadata_scan` | `12min` | 论文元数据、OpenReview / arXiv / OpenAlex / conference metadata |
| `paper_fulltext_or_benchmark_check` | `18min` | 论文全文、benchmark、复现、数据集或 leaderboard 深查 |
| `finance_filing_or_ir_check` | `20min` | SEC、IR、财报电话会、融资 / 并购核验 |
| `policy_official_doc_check` | `20min` | 政策、监管、标准、公共采购、官方项目文件核验 |
| `normalization_merge` | `5min` | 实体对齐、去重、source-chain merge |
| `audit_pass` | `8min` | counter evidence、conflict、bias 审计 |
| `tier_decision` | `5min` | claim ledger 裁决与 weekly card 汇总 |

执行约束：

- timeout 必须先按 task profile 选取，而不是先按 Agent 类别给一个统一上限。
- `finance-agent`、`policy-agent`、学术全文 / benchmark 检查不得被 `fast_feed_scan` 或 `oss_api_scan` 的预算偷换。
- 任何 task profile 如果被 ExecPlan 放宽，必须同时写明成本影响、失败降级语义和 fixture。

### `micro-task-runtime-budget-profile.v1`

`task-timeout-profile.v1` 只描述任务族的粗粒度上限，真正执行时必须进一步细化到更小任务。当前设计冻结面向小任务的默认运行时预算：

| micro task | 默认 timeout | 说明 |
| --- | ---: | --- |
| `feed_list_fetch` | `45s` | RSS、列表页、事件流首页抓取 |
| `candidate_url_metadata_fetch` | `30s` | 单 URL metadata、title、timestamp、content-type 探测 |
| `official_html_fetch` | `90s` | 官方公告、docs、release page、监管正文 HTML 抓取 |
| `official_pdf_fetch` | `120s` | PDF 下载，不含全文解析 |
| `pdf_parse_and_anchor_extract` | `150s` | PDF 正文解析、章节锚点与关键信号抽取 |
| `transcript_fetch_and_segment` | `180s` | 财报电话会、访谈 transcript 抓取与切段 |
| `filing_fetch_and_section_parse` | `180s` | filing / IR / 披露文档抓取和结构化分段 |
| `paper_metadata_lookup` | `60s` | arXiv / OpenAlex / OpenReview / proceedings metadata 查询 |
| `paper_fulltext_fetch` | `150s` | 论文全文抓取，不含 benchmark 交叉核验 |
| `benchmark_or_leaderboard_check` | `180s` | leaderboard、benchmark、dataset 更新核验 |
| `source_chain_dedupe_batch` | `90s` | 传播链/转载链批处理去重 |
| `fact_partition_merge` | `120s` | 单个 `fact_partition` 的事实归并 |
| `owner_arbitration_partition` | `90s` | 单个 partition 的 owner transfer / attestation 结算 |
| `claim_family_fold` | `90s` | 同一 claim family 的 overlap collapse |
| `claim_link_materiality_build` | `120s` | claim-evidence link 构建与 materiality 标注 |
| `registry_snapshot_read` | `30s` | runtime snapshot 读取和版本校验 |
| `registry_material_review` | `120s` | 影响 admitted claim 的实体 authority 审核 |
| `audit_material_pass` | `180s` | 只针对 `is_tier_material=true` links 的审计 |
| `audit_supporting_pass` | `90s` | supporting / confidence-only 层审计 |
| `gap_request_dispatch` | `30s` | gap 请求落账、去重和派发 |
| `gap_followup_fetch` | `180s` | 单个 gap scope 的补证抓取 |
| `tier_decision_batch` | `120s` | claim ledger 决策与 readiness / display priority 产出 |
| `consumer_projection_pack` | `90s` | consumer / public projection 打包 |

执行约束：

- 任何 same-run 高成本动作都必须命中一个 `micro-task-runtime-budget-profile`；不得只挂在宽泛的 `finance_filing_or_ir_check` 或 `policy_official_doc_check` 下统一处理。
- 同一 claim 的端到端关键路径预算，应由这些 micro-task timeout 累加约束；不得表面上遵守大 task timeout，实际在内部串很多个高成本小动作。
- `critical_headline` 与 `high_priority` claim 的 micro-task 预算允许更严格，不允许更宽松；若需放宽，必须同步写明它会挤占哪一段 same-run 关键路径。

`axis-runtime-budget-profile.v1` 冻结如下：

| axis family | 默认 daily run 预算 | 说明 |
| --- | --- | --- |
| `project_open_source` | `1` 个 primary run，最多 `10` 个 API / registry 原子调用，最多 `3` 个 fallback URL | 适合 repo、包生态、benchmark、dependency adoption 检查 |
| `research_paper` / `conference_academic` | `1` 个 academic primary run，最多 `2` 个 metadata API，最多 `20` 个 paper refs，最多 `5` 个 official / PDF 页面 | 学术类需要更高引用和全文检查预算，不能与新闻同配额 |
| `product_vendor_release` | `2` 个 official / feed route，最多 `8` 个 docs / blog / release refs | 用于厂商 release、SDK、API docs、客户案例核验 |
| `developer_studio` / `community_discussion` | `1` 个 primary run，最多 `20` 个候选帖子 / thread，去重后最多 `8` 个 accepted supporting refs | 先广搜，再靠 dedupe 和 quality gate 收紧 |
| `capital_finance` | `2` 个 filing / IR / research route，最多 `10` 个 filing / report / transcript refs | paid sources 只能进入 `needs_review` 或 local-only human exception |
| `policy_regulatory` / `policy_research_thinktank` | `2` 个 official / policy route，最多 `12` 个 official docs / report refs | 适合政策文件、标准、采购、智库报告核验 |
| `news_pr_narrative` | `1` 个 primary run，最多 `15` 个 candidate refs，source-chain 去重后最多 `6` 个 accepted refs | 强制压制转载链与 SEO 内容吞没 |

执行约束：

- `axis-runtime-budget-profile.v1` 的单位不是 accepted event 数，而是可消耗的调用和核验预算。
- `axis-runtime-budget-profile.v1` 的粗粒度预算只负责约束 axis family；真正的执行成本必须继续映射到小任务级 `micro-task-runtime-budget-profile.v1` 与 `micro-task-cost-profile.v1`。
- 不同 axis family 的预算差异是设计语义，不得在实现阶段回退成统一 `1/2/5/3` 配额。
- 如果某个 axis family 预算耗尽，系统必须输出 `budget_exceeded`、`active_route_level` 和受影响 axis，不得把“没来得及看”伪装成“没有趋势”。
- `core_monitor` 默认吃上述预算；`watchlist` 只能消耗轮巡或事件触发预算；`cold_archive` 不得偷偷消耗主扫描预算。

### `micro-task-cost-profile.v1`

当前成本模型不能只按“调用次数、refs 数、slot 数”计数。PDF、全文、transcript、filing、人工例外处理的成本差异必须成为运行时硬约束。为此补充冻结小任务级成本画像：

| micro task | 默认 `estimated_cost_units_per_attempt` | 默认 `cost_class` | 说明 |
| --- | ---: | --- | --- |
| `feed_list_fetch` | `1` | `low` | 快速发现型抓取 |
| `candidate_url_metadata_fetch` | `1` | `low` | 单 URL metadata 探测 |
| `official_html_fetch` | `2` | `medium` | 官方正文或 docs 页面抓取 |
| `official_pdf_fetch` | `3` | `medium` | PDF 下载与可用性验证 |
| `pdf_parse_and_anchor_extract` | `4` | `high` | PDF 正文解析与结构抽取 |
| `transcript_fetch_and_segment` | `5` | `high` | transcript 抓取与分段 |
| `filing_fetch_and_section_parse` | `5` | `high` | filing / IR 文档结构化解析 |
| `paper_metadata_lookup` | `2` | `medium` | 学术 metadata 解析 |
| `paper_fulltext_fetch` | `4` | `high` | 全文抓取 |
| `benchmark_or_leaderboard_check` | `4` | `high` | leaderboard / benchmark 深查 |
| `source_chain_dedupe_batch` | `2` | `medium` | 批处理去重 |
| `fact_partition_merge` | `3` | `medium` | partition 级事实归并 |
| `owner_arbitration_partition` | `3` | `medium` | owner/attestation 结算 |
| `claim_family_fold` | `2` | `medium` | 候选折叠 |
| `claim_link_materiality_build` | `3` | `medium` | materiality 标注 |
| `registry_material_review` | `4` | `high` | admitted claim 相关 authority 审核 |
| `audit_material_pass` | `4` | `high` | material links 审计 |
| `audit_supporting_pass` | `2` | `medium` | supporting/confidence-only 审计 |
| `gap_followup_fetch` | `5` | `high` | gap 级补证 |
| `manual_exception_review` | `8` | `exceptional` | 需人工或付费例外的动作 |

执行约束：

- 所有会占用共享池、会进入 same-run 关键路径、或会触发 official fetch / deep check 的动作，都必须声明 `micro_task_id`、`estimated_cost_units_per_attempt` 和 `cost_class`。
- 仲裁时不得把一个 `feed_list_fetch` 与一个 `transcript_fetch_and_segment` 当作同权“一个 slot”；若成本类别相差一个级别以上，必须显式进入 cost-weighted 仲裁。
- `actual_cost_units` 与 `actual_latency_ms` 必须可回写到运行态审计；否则 shared pool 只能视为名义限流，不能证明成本真实受控。

`rotation-budget-profile.v1` 冻结如下：

| monitor tier | 默认 rotation 预算 | 说明 |
| --- | --- | --- |
| `watchlist` | 每次 weekly run 最多轮巡 `10` 个 entries，且同一 axis family 最多 `2` 个 | 用于补充覆盖、冷启动补证和避免 watchlist 永久沉底 |
| `cold_archive` | 每次 weekly run 最多抽检 `2` 个 entries | 只做低频健康检查、实体对齐和历史 continuity 复核 |

执行约束：

- `rotation-budget-profile.v1` 只用于 `watchlist` 和 `cold_archive`，不得挤占 `core_monitor` 主扫描预算。
- 若某主体配置了 `axis_monitoring_overrides`，rotation 预算必须按 override 后的 axis tier 计算。

### `claim-runtime-budget-profile.v1`

axis 预算和 task 超时还不够回答“单条 claim 最多可以消耗多少关键产能”。当前设计补充冻结 `claim-runtime-budget-profile.v1`，把成本控制提升到 claim 级，以避免热点周 few-shot headline 候选把 finance / policy / audit / review 全部拖爆。

每个 admitted claim 至少必须可计算以下预算：

- `max_registry_reviews`
- `max_audit_passes`
- `max_official_fetches`
- `max_gap_loops`
- `max_manual_review_escalations`
- `max_runtime_minutes`
- `max_cost_units`

默认预算消耗顺序固定如下：

1. 主支柱和关键独立交叉确认。
2. authority / public-safe / blocking counter evidence。
3. same-run headline 所需的 single-gap canonical fetch。
4. supporting axis 完整度补强。
5. 长尾上下文、附加 narrative 和非关键美化证据。

高成本预算仲裁顺序固定如下：

1. 先完成 `claim family fold / overlap collapse`，避免语义重复候选分别消耗稀缺资源。
2. 再执行 `claim-admission-budget-profile.v1`，决定本轮哪些 claim 候选有资格进入 same-run 关键闭环。
3. 再检查 `claim-runtime-budget-profile.v1`，确认单条 claim 是否仍有可用预算。
4. 再申请 `shared-capacity-policy.v1` 中对应共享池的 slot。
5. 最后才允许对应 axis 的 official fetch、deep check、same-run gap loop 或等价高成本扩张。

执行约束：

- `critical_headline`、`high_priority` 不仅受数量 admission budget 约束，也必须受 claim-level 成本预算约束；不得只按条数限流。
- claim-level 预算仲裁必须消费同一份 `ClaimAdmissionAssessment`；coordinator、trend-agent、queue dispatcher 和 shared pool allocator 不得各自私算一套 `projected decision_tier`、`consumer_readiness_state` 或预估成本。
- claim 预算耗尽时，默认动作是下调 `decision_confidence`、`coverage_audit_state`、`consumer_readiness_state` 或公开分桶；不得直接把 `decision_tier` 打低来伪装“系统更保守”。
- same-run 中若多个 claim 同时竞争 finance / policy / registry / audit 稀缺资源，必须先执行 claim-level 预算仲裁，再执行 axis 扩张；不得按谁先到谁先烧完。
- 若 claim 在本轮未消耗到足够预算完成 high-cost canonical fetch，必须显式把该 claim 留在 internal ledger / watchlist / needs-review，而不是静默消失。
- 任何高成本预算分配都必须生成可审计的 `budget_arbitration_record`，至少保留 `claim_family_key`、`candidate_group_id`、`requested_budget_class`、`requested_pool_id?`、`runtime_budget_profile_id`、`cost_budget_profile_id`、`estimated_cost_units`、`actual_cost_units?`、`decision`、`reason_codes`、`consumed_slots` 和 `source_message_id / artifact_ref`；不得只在运行日志里临时决定。
- `budget_arbitration_record` 不得只是自然语言结论；凡命中共享池、same-run 关键路径或 claim-level 高成本预算的动作，都必须能反查 machine-readable `CapacityReservation.v1`。
- 上述要求同样适用于 `reserved_cost_units_for_publication_and_p0`。public packaging、public-safe 阻断修复和 `P0` blocking review 若继续占用保留预算，也必须留下 `CapacityReservation.v1`，不得只在 run summary 中汇总一个数字。

### `shared-capacity-policy.v1`

axis budget 和 claim budget 仍不足以表达“多个 claim 争抢同一稀缺资源池”的现实。当前设计补充冻结 `shared-capacity-policy.v1`，统一管理 high-cost canonical fetch、registry review、audit slot 和人工复核这类共享产能。

共享资源池至少包括：

- `finance_official_fetch_pool`
- `policy_official_fetch_pool`
- `registry_review_pool`
- `audit_pass_pool`
- `manual_review_pool`

每个 pool 至少必须定义：

- `pool_id`
- `capacity_per_run`
- `reserved_for_critical_headline`
- `admission_priority`
- `preemption_rule`
- `degradation_on_exhaustion`
- `arbitration_record_policy`
- `cost_weight_policy`

默认共享池容量地板冻结如下。ExecPlan 可以收紧，但不得在未说明影响范围、降级语义和审计方式时放宽：

| `pool_id` | `capacity_per_run` | `reserved_for_critical_headline` | 默认含义 |
| --- | ---: | ---: | --- |
| `finance_official_fetch_pool` | `4` | `2` | 同一 weekly run 中 finance canonical fetch 的共享上限 |
| `policy_official_fetch_pool` | `4` | `2` | 同一 weekly run 中 policy / regulatory canonical fetch 的共享上限 |
| `registry_review_pool` | `6` | `3` | authority / registry material review 的共享上限 |
| `audit_pass_pool` | `8` | `4` | same-run material audit 的共享上限；该值有意低于 `admitted_claim_count_assumption` 的默认上界，表示热点周默认不承诺“所有 admitted claim 都能拿到 full same-run material audit” |
| `manual_review_pool` | `8` | `3` | 同一 weekly run 中可占用的人审槽位上限，其中 `P0` 仍受前文 same-run blocking 口径约束 |

执行约束：

- 共享池容量是 run 级硬约束，不得由各 axis 或各 claim 自行重复占用后再事后解释。
- 当多个 claim 同时命中同一共享池时，必须先按 `critical_headline > high_priority > deferred_followup` 与剩余 claim 预算联合仲裁，再决定谁获得 slot；不得按消息先到先得。
- `reserved_for_critical_headline` 不得被长尾 follow-up、watchlist 轮巡或非关键 supporting 补强提前耗尽。
- 共享池耗尽时，默认动作是暴露 `coverage_audit_state`、`decision_confidence`、`consumer_readiness_state` 或 `needs_review` 降级，而不是直接篡改事实 tier。
- 任何会消耗共享池的请求，必须先按 `claim_family_key`、`candidate_group_id`、`gap_scope` 或等价稳定聚合键完成合批后再仲裁；不得按单 event 粒度直接抢占稀缺槽位。
- 同一共享池的仲裁必须同时参考 `consumed_slots` 与 `estimated_cost_units`；不得让少量超高成本的 PDF / transcript / filing / human-exception 任务伪装成“只是几个 slot”。
- 共享池剩余额度只能由已落账的 `CapacityReservation.v1` 计算；worker、queue consumer 或工具 adapter 不得根据本地缓存、日志或推测的“空闲 worker”自行判断还有没有配额。
- 没有 `reservation_state="granted"` 的 `CapacityReservation.v1` 引用时，不得启动会实际消耗共享池的请求；不得先执行、后补记账。
- `manual_review_pool` 不仅管理“是否需要人审”，还管理“哪一条 review 正在占用多少人审槽位”；任何 active same-run review 都必须通过 `HumanReviewQueueItem.capacity_reservation_refs`、`occupied_slots` 和 `reservation_binding_state` 与 `CapacityReservation.v1` 建立 machine-readable 绑定。

### `run-total-budget-policy.v1`

只冻结 axis budget、claim budget、shared pool 和 micro-task cost 还不够；热点周里完全可能出现“每个 claim 都没超、每个池也没爆，但整轮 weekly 总成本已经穿透”的情况。当前设计补充冻结 run 级总预算闭环，用来约束 same-run admitted work 的总盘子。

每个 weekly run 至少必须定义：

- `max_run_cost_units`
- `soft_stop_cost_units`
- `reserved_cost_units_for_publication_and_p0`
- `max_same_run_high_cost_actions`
- `projected_run_cost_units_before_dispatch`
- `actual_run_cost_units_after_publication`
- `over_budget_default_action`

默认 run 级预算地板冻结如下：

| 项 | 默认值 | 含义 |
| --- | ---: | --- |
| `max_run_cost_units` | `60` | 单次 weekly run 允许消耗的总成本上限 |
| `soft_stop_cost_units` | `48` | 接近上限时开始主动收紧 same-run admitted work 的软阈值 |
| `reserved_cost_units_for_publication_and_p0` | `8` | 专门留给 public packaging、public-safe 阻断修复和 `P0` blocking review 的保留预算 |
| `max_same_run_high_cost_actions` | `10` | 单轮 weekly 允许真正启动的 high / exceptional micro task 上限 |
| `over_budget_default_action` | `defer_followup_or_downgrade_readiness` | 超预算时的默认系统动作 |

执行约束：

- 任何会触发 `cost_class in {"high","exceptional"}` 的 same-run 动作，在启动前都必须计算 `projected_run_cost_units_before_dispatch = 已 consumed 成本 + 已 granted 但未完成的估算成本 + 本次请求 estimated_cost_units`；不得只看当前 claim 或当前 pool 是否还有余额。
- 当 projected total 超过 `soft_stop_cost_units` 时，只有命中 `critical_headline`、`tier_blocking`、`public_output_only` 或 public packaging 保留预算的动作才允许继续申请 same-run；其余请求默认转 `defer_followup`、`needs_review`、下调 `decision_confidence` 或下调 `consumer_readiness_state`。
- 当 projected total 超过 `max_run_cost_units` 时，除占用 `reserved_cost_units_for_publication_and_p0` 的 public packaging / `P0` 阻断动作外，不得再启动新的 same-run 高成本任务；不得靠“单个 claim 还没超预算”继续加码。
- `reserved_cost_units_for_publication_and_p0` 不得被 supporting axis 补强、watchlist 扩张、长尾 narrative 美化或非关键 canonical fetch 预支。
- 任何命中 `reserved_cost_units_for_publication_and_p0` 的动作，都必须通过 `publication_and_p0_reserve_pool` 的 `CapacityReservation.v1` 落账；`run_budget_summary` 只做聚合展示，不得成为唯一扣减真源。
- `run_budget_summary` 必须显式输出 `estimated_run_cost_units`、`actual_run_cost_units`、`remaining_run_cost_units`、`run_cost_status` 和 `cost_deferred_claim_count`；否则用户无法判断当前 weekly 是“预算受控地保守”还是“无上限地烧完了预算”。
- `run-total-budget-policy.v1` 解决的是总盘子封顶，不替代 claim budget 或 shared pool；固定仲裁顺序仍必须保持为 `fold -> admission -> claim budget -> shared capacity -> axis expansion -> run total budget check before dispatch`。

### `same-run-review-availability-policy.v1`

`manual_review_pool` 只表达“槽位”，不表达“30 分钟内到底有没有 reviewer 真能响应”。如果不把 reviewer availability 单独冻结，same-run 人审会在设计上看似可调度、现实里却无法兑现。当前设计补充冻结 reviewer availability 口径如下：

每个 weekly run 至少必须定义：

- `same_run_review_mode`
- `on_duty_reviewer_count`
- `p0_review_response_slo_minutes`
- `availability_snapshot_at`
- `availability_reason_codes`

默认 `same_run_review_mode` 仅允许以下取值：

- `staffed_human`
- `service_account_only`
- `async_only`

执行约束：

- `manual_review_pool` 的 slot 只有在 reviewer availability gate 通过后才有意义；不得把“有 8 个槽位”直接解释成“有 8 个 reviewer 能在当前 30 分钟窗口内完成复核”。
- 只有当 `same_run_review_mode in {"staffed_human","service_account_only"}`，且 `required_resolution_by` 仍落在 `publication_snapshot_at` 之前，相关 `P0` review 才允许被当作 same-run 可完成事项；否则必须按不可 same-run 完成处理。
- 当 `same_run_review_mode="async_only"` 时，系统不得把 pending `P0` review 当成“本轮稍后会补齐”的隐式前提；必须立刻执行 `default_system_action`，并把缺口显式体现在 `consumer_readiness_state`、`blocked_public_output`、`decision_confidence` 或必要的 tier 降级中。
- 对 `impact_scope="public_output_only"` 的事项，若当前 run 只有 `async_only` reviewer，可保留 internal ledger，但 public output 必须阻断或 redaction；不得为了赶发布把 public review 缺口写成已通过。
- 对 `impact_scope="tier_blocking"` 的事项，若当前 run 没有 same-run reviewer，可保留 internal candidate 或 lower-confidence 记录，但不得依赖“未来有人会审”来维持或升级 public `core` 结论。
- `run_snapshot` 与 `run_budget_summary` 必须把 same-run review availability 显式输出给 consumer、治理面和 replay；否则 replay 无法区分“规则要求人审但没人值班”与“有人值班但流程跑挂了”。

### `runtime-sizing-assumptions.v1`

当前设计已经冻结了 shared pool、claim budget 和 queue 并发上限，但这些数字不能只是经验常量。为避免“参数很多、负载模型没有”的假精细化，当前设计补充冻结 `runtime-sizing-assumptions.v1`。

每个 weekly run 至少必须显式声明：

- `candidate_group_count_assumption`
- `admitted_claim_count_assumption`
- `critical_headline_count_assumption`
- `high_priority_count_assumption`
- `avg_material_audit_passes_per_admitted_claim`
- `avg_same_run_gap_count_per_critical_claim`
- `finance_or_policy_deep_check_activation_ceiling`
- `manual_review_p0_ceiling`
- `run_total_cost_units_ceiling`
- `same_run_review_mode_assumption`
- `same_run_reviewer_on_duty_assumption`

默认 sizing 地板冻结如下：

| sizing item | 默认假设 | 设计含义 |
| --- | --- | --- |
| `candidate_group_count_assumption` | `<= 40` | 单次 weekly run 中，进入 claim family fold / overlap collapse 的候选族默认不应无限膨胀 |
| `admitted_claim_count_assumption` | `<= 9` | 与 `critical_headline <= 3`、`high_priority <= 6` 对齐 |
| `critical_headline_count_assumption` | `<= 3` | 与 same-run headline 预算和 headline display capacity 对齐 |
| `high_priority_count_assumption` | `<= 6` | 与 same-run admission budget 对齐 |
| `avg_material_audit_passes_per_admitted_claim` | `<= 1` | 默认不允许同一 admitted claim 在本轮反复 full re-audit |
| `avg_same_run_gap_count_per_critical_claim` | `<= 1` | 同一 critical claim 默认只允许一次关键缺口闭环 |
| `finance_or_policy_deep_check_activation_ceiling` | 每类 pool 默认不超过其 `capacity_per_run` | 与 `finance_official_fetch_pool`、`policy_official_fetch_pool` 的共享池设计联动 |
| `manual_review_p0_ceiling` | `<= 3` | 与前文 same-run blocking 人审容量一致 |
| `run_total_cost_units_ceiling` | `<= 60` | 与 `run-total-budget-policy.v1` 的总预算上限对齐，防止局部预算都合规但整轮 weekly 透支 |
| `same_run_review_mode_assumption` | 默认至少显式声明为 `staffed_human` 或 `async_only` | 不允许把 reviewer availability 留给实现或值班同学临时口头判断 |
| `same_run_reviewer_on_duty_assumption` | `0` 或 `>= 1`，不得留空 | 用于把“无人值班时的保守消费路径”变成运行时硬契约，而不是事后解释 |

执行约束：

- `shared-capacity-policy.v1`、`runtime-concurrency-control-policy.v1`、`claim-admission-budget-profile.v1`、`run-critical-path-budget.v1`、`run-total-budget-policy.v1` 和 `same-run-review-availability-policy.v1` 的数值，必须能回溯到同一份 sizing assumption；不得各章各自独立拍数。
- `admitted_claim_count_assumption`、`avg_material_audit_passes_per_admitted_claim` 与 `audit_pass_pool.capacity_per_run` 必须联读解释，而不是各自孤立成立。按当前默认值，系统只保证“热点周最多 9 条 admitted claim 进入 same-run 编排面”，不保证 9 条都能获得 full same-run material audit；在 `audit_pass_pool=8` 的默认地板下，至少有一条 admitted claim 必须走“复用已完成有效 audit 结果”或“`coverage_audit_state=partial` / `consumer_readiness_state!=ready` / defer follow-up”的保守路径，除非本轮已有 audit slot 释放。
- 任何试图让 admitted claim 数、headline ready 数和 full same-run material audit 数同时按同一上界理解的实现，都视为违反容量口径；`critical_headline` / `ready headline core` 的可兑现数量必须优先受 `audit_pass_pool`、`registry_review_pool`、`manual_review_pool` 与 run-total budget 的交集约束，而不是只看 claim admission 条数。
- 若某次 weekly run 的预估负载超出 sizing 假设，系统默认动作应是收紧 same-run admission、下调 `decision_confidence` / `consumer_readiness_state`、转 backlog 或显式 rerun，而不是静默突破 pool / queue / timeout 上限。
- sizing assumption 是运行治理契约，不是实现备注；回放、压测和热点周复盘必须能直接对照这些假设判断“是参数不合理，还是负载已超设计窗口”。

### 评测、回放与质量指标

本设计必须建立可回放的评测闭环。设计阶段冻结以下评测对象：

| 评测对象 | 必须覆盖的质量问题 | 最低产物 |
| --- | --- | --- |
| gold claims | 典型核心趋势、观察趋势、风向探针、项目热度簇、证据不足方向 | `eval/gold-industry-claims.jsonl` 或等价 fixture |
| negative fixtures | 泛 AI 新闻、纯资本热度、纯政策信号、宣传稿、来源重复、低相关 vertical automation | `eval/negative-industry-signals.jsonl` |
| replay windows | 历史 weekly 输入窗口和 daily evidence pack | replay 命令或测试 fixture，能重建 claim ledger |
| citation accuracy | `source_trace_refs` 是否能追溯到 event/source/tool/agent | citation accuracy 指标和失败样例 |
| tier accuracy | decision tier 是否符合规则 profile | false positive / false negative 计数 |
| downgrade correctness | 反证、缺失、stale、tool failure 是否触发正确降级 | downgrade fixture 和 snapshot |

评测指标定义：

- `core_trend_false_positive`: 被升为 `core_industry_trend`，但缺少必需跨轴证据、Agent relevance、source authority 或存在阻断反证。
- `core_trend_false_negative`: gold set 中应为核心趋势的主张被降到观察、风向探针、项目热度或证据不足，且不是由真实缺失 / 反证 / stale 导致。
- `citation_trace_accuracy`: weekly 中可见 source trace 能成功反查 canonical event/source/tool/agent 的比例。
- `axis_completeness_rate`: 每条 claim 输出十轴状态且无隐式省略的比例。
- `downgrade_explainability_rate`: 每次降级都有 reason code、受影响轴和用户可读说明的比例。

评测地板冻结如下：

- gold claims 至少 `40` 条，且必须覆盖 `core_industry_trend`、`observing_industry_trends`、`wind_probe`、`project_heat_cluster`、`insufficient_evidence_directions` 五类结果。
- negative fixtures 至少 `80` 条，且必须覆盖泛 AI 新闻、纯资本热度、纯政策信号、宣传稿、来源重复和低相关 vertical automation。
- replay windows 至少 `8` 个，建议从最近 `26` 周中选取高密度周、低密度周、政策周、会议周和工具失效周。
- `citation_trace_accuracy >= 0.98`，其中核心趋势关键引用必须 `1.00` 可解析。
- `axis_completeness_rate = 1.00`；任何 claim 不得隐式省略 axis。
- `downgrade_explainability_rate >= 0.95`。
- `core_trend_false_positive <= 0.10`，`core_trend_false_negative <= 0.15`；若样本量不足或未达通过线，必须在评测/发布治理产物中明确标记为“评测证据不足”或“未达发布门槛”，不得在主设计文档里再引入 `shadow_eval`、`pilot` 或版本化“可用/完成态”阶段话术。

没有 gold set、negative fixtures、replay、最低样本量或上述通过线的实现，不得宣称设计已被充分验证，也不得宣称达到发布门槛。

### 人工复核、审批与覆盖

系统必须支持人工复核，但人工复核不得变成不可追溯的后台改文案。

本节只补充人工复核与覆盖在运行治理上的消费语义；`HumanReviewQueueItem`、`OverrideAudit` 的完整结构真源仍以 [03-数据模型契约](03-数据模型契约.md) 为准，下面只摘录本章最需要强调的治理字段。

`HumanReviewQueueItem` 治理语义摘录如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `review_id` | string | 复核任务 ID | 必须全局唯一并可追溯到 claim/event/artifact |
| `trigger` | `high_counter_evidence` / `source_conflict` / `public_safe_failure` / `authority_promotion` / `manual_flag` / `tier_override_request` | 进入复核的原因 | 不得使用无语义的 `other` 替代常见触发原因 |
| `review_priority` | `P0` / `P1` / `P2` | 复核优先级 | `P0` 表示 same-run blocking；`P1` 表示 `24h` 内处理；`P2` 允许进入 backlog。 |
| `blocking_output_scope` | `public_output` / `tier_upgrade` / `none` | 未关闭时阻断的输出范围 | `P0` 默认不得为 `none`；未关闭 `P0` 且 scope 命中时不得 public 输出或不得升级 tier。 |
| `review_execution_mode` | `same_run_human` / `same_run_service_account` / `async_deferred` | 当前 review 计划以哪种执行模式完成 | 它必须与本轮 `review_availability_snapshot` 对齐；不能把“有槽位”偷换成“有人值班” |
| `required_resolution_by` | ISO datetime | 最晚完成时间 | `P0` 必须落在当前 run 或显式 rerun 窗口内；`P1` 默认 `24h`；`P2` 可为空。 |
| `source_message_id` | string | 触发该 review 的 canonical 消息 | 必须能反查触发 review 的请求、失败或治理动作；不得由后台静默补造 |
| `queue_pool_id` | `manual_review_pool` optional | 该 review 若占用人审共享池，对应的 pool | 占用 same-run 人审产能时必填；纯 backlog 项可为空 |
| `capacity_reservation_refs` | string[] | 绑定的人审容量 reservation | 任何 active same-run review 都必须显式绑定；没有 `granted` reservation 的项不得计入人审容量 |
| `occupied_slots` | number | 当前 review 实际占用的人审槽位 | 必须与 reservation 的 `granted_slots` 对齐；不得只靠 queue_state 估算 |
| `reservation_binding_state` | `not_reserved` / `reserved` / `released` / `expired` | review 与人审容量的绑定状态 | 只有 `reserved` 才表示真实占槽；`released/expired` 后不得继续计入 same-run 容量 |
| `target_ref` | object | 被复核对象引用 | 必须包含 kind、id、artifact_ref |
| `queue_state` | `open` / `assigned` / `in_review` / `closed` / `expired` | 当前队列状态 | 只有 `closed` 才算“已关闭 review”；`expired` 需保留 backlog 和降级影响。 |
| `current_state` | string | 当前系统状态 | 必须可还原复核前状态 |
| `requested_action` | `approve` / `reject` / `downgrade` / `promote_authority` / `redact` / `rerun` | 期望动作 | 不能直接修改 canonical artifact，必须生成审计记录 |
| `reviewer_id` | string | 复核人或服务账号 | 自动复核也必须有主体 |
| `decision` | `approved` / `rejected` / `needs_more_evidence` / `expired` | 复核结论 | `queue_state!="closed"` 时不得被当作通过；`expired` 不等于通过。 |
| `reason_cn` | string | 复核理由 | 必须可被 weekly 或治理台摘要引用 |

`OverrideAudit` 冻结字段：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `override_id` | string | 覆盖记录 ID | 必须全局唯一 |
| `actor_id` | string | 执行覆盖的主体 | 不允许匿名覆盖 |
| `target_ref` | object | 被覆盖对象 | 必须指向 canonical artifact |
| `before_value` / `after_value` | JSON | 覆盖前后值 | 必须保留完整差异 |
| `reason_code` | string | 覆盖原因 | 必须来自冻结枚举或 ExecPlan 扩展枚举 |
| `expires_at` | string? | 覆盖过期时间 | 非永久修正必须有过期时间 |
| `created_at` | string | 覆盖时间 | 必须用于审计排序 |

Trend tier、source authority、public-safe 状态、registry promotion 和 claim suppression 都属于高影响覆盖，必须写入 `OverrideAudit`。

执行约束补充：

- `run_budget_summary.review_backlog_p1_or_higher` 必须由 `review_priority in {P0,P1}` 且 `queue_state!="closed"` 的 review item 聚合得出，不得人工手填。
- same-run active 人审占用必须由 `HumanReviewQueueItem.queue_pool_id="manual_review_pool"`、`capacity_reservation_refs`、`occupied_slots` 和 `reservation_binding_state="reserved"` 联合反查；不得把“已入 backlog”直接当成“已占用人审池”。
- 当本轮 `same_run_review_mode="async_only"` 时，任何 `P0` review 都不得被解释成“同轮可补齐”；系统必须立即执行 `default_system_action`，并把保守消费结果写回 weekly。
- `P0` review 的 `blocking_output_scope="public_output"` 时，public weekly 不得消费相关 artifact；internal weekly 可保留，但必须显式标注 `needs_review`。
- `P0` review 的 `blocking_output_scope="tier_upgrade"` 时，相关 claim 在 review 关闭前不得升级到更高 `decision_tier`。

### 治理与控制面

本设计至少需要一个逻辑上的治理面，即使实现阶段先用 CLI / JSON artifact 承载，也必须覆盖以下对象：

治理术语解释：

更多专用名词统一以 [术语与审计词汇表](09-术语与审计词汇表.md) 为准；本节只解释治理面最容易让审核者误读的对象。


| 术语 | 含义 | 为什么需要它 |
| --- | --- | --- |
| `message lineage` | 同一 `run_id` 或同一 claim 在多 Agent 之间流转的消息链路，至少包括谁发送、谁消费、依赖了哪些前置消息、产出了哪些 artifact。 | 用来证明 claim-builder、audit、tier-decider 的先后关系真实发生，而不是事后补写。 |
| `artifact manifest` | 每个 canonical artifact 的登记记录，至少包含 artifact kind、schema version、producer、input refs、storage path 和 content hash。 | 用来让下游解析 `*_ref`，也用来审计“这个结论到底读了什么、写了什么”。 |
| `replay 状态` | 某个历史窗口在当前规则、schema 和工具快照下能否被重新执行和对比的状态。至少区分 `not_started`、`running`、`passed`、`failed`、`drifted`、`blocked`。 | 用来判断历史 weekly 是否可重建，以及差异是规则漂移、数据缺失还是工具失效。 |
| `schema version` | message、event、ledger、review、override 等结构契约的版本号。 | 用来判断 artifact 是否兼容，以及变更是否属于 breaking change。 |
| `gold set` | 人工冻结的高质量期望样本集合，描述“哪些 claim / tier / evidence pattern 应该被命中”。 | 用来验证系统没有把真正的重要趋势漏掉。 |
| `negative fixtures` | 人工冻结的反例样本集合，描述“哪些噪声、宣传、泛 AI 热点或单轴热度不应被升级”。 | 用来验证系统不会把热闹误写成趋势。 |
| `replay result` | 对历史窗口执行 replay 后产生的结果摘要，至少包括命中率、误报/漏报、citation 准确性和与 baseline 的差异。 | 用来定位指标下降到底是规则改坏了、数据变了，还是工具链退化了。 |

| 治理对象 | 必备能力 | 审计要求 |
| --- | --- | --- |
| registry | 查看 entity/source 状态、authority tier、stale、promotion request | 所有新增、降级、提升、排除必须有 audit |
| tools | 查看 route level、成本、授权状态、最近失败、fallback 使用 | 工具状态变化必须可追溯到运行和负责人 |
| agents | 查看 agent 版本、职责项、输入输出、失败状态 | Agent 输出缺失不能被综合 Agent 静默补写 |
| runs | 查看 daily / weekly run、message lineage、artifact manifest、replay 状态 | 每次 run 必须有 run_id 和 schema versions |
| schemas | 查看 message、event、ledger、review、override schema version | schema 变更必须有兼容性说明 |
| evals | 查看 gold set、negative fixtures、replay result、质量指标 | 指标下降必须能定位到规则、数据或工具变更 |

治理面可以复用现有中间件或 CLI，但 canonical 状态仍以本设计定义的 artifact、message、audit 和 ledger 为准。
