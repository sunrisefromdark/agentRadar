# 行业级 Agent 趋势判断：数据模型契约

> 本文档拆自 [行业级Agent趋势判断设计文档.md](../行业级Agent趋势判断设计文档.md)，是行业级 Agent 趋势判断设计文档包的一部分。

## 数据模型

### Event / Source Chain / Fact / Claim 四层约定

为避免把单条材料、传播链、底层事实和趋势主张混成一个“证据对象”，V1 冻结以下四层：

| 层级 | 代表对象 | 解决的问题 | 典型字段 / 产物 |
| --- | --- | --- | --- |
| Event 层 | 单条 `IndustrySignalEvent` | “系统看到了什么材料” | `event_id`、`axis`、`source`、`actor`、`target` |
| Source Chain 层 | 转载链 / 同源链 | “这些材料是不是同一传播链” | `source_chain_dedupe_groups`、`same_source_chain` |
| Fact 层 | 底层事实及其后续确认 | “这些事件是否围绕同一事实” | `fact_id`、`provisional_fact_group_id`、`fact_resolution_state`、`relation_edges` |
| Claim 层 | 趋势主张与证据关系 | “这些事实如何支撑当前 claim” | `IndustryClaimEvidenceLink`、`CounterEvidenceAudit`、`IndustryTrendDecision` |

执行约束：

- 同一层的归一结果不得偷换另一层语义；例如同源去重不等于事实归一，事实归一也不等于 claim 成立。
- `source independence` 主要在 Source Chain 层判断，`fact independence` 主要在 Fact 层判断；二者不得混用。
- 脏数据处理默认先保留 Event 层信息，再通过 Source Chain / Fact 层建立关系，最后在 Claim 层做升级限权。

### Topic / Entity Canonicalization 最小契约

多语言 topic、品牌别名、会议简称和产品代号不是后续可选优化，而是当前归一主链路的最小前置契约。当前设计至少冻结以下最小对象：

```ts
interface TopicEntityCanonicalizationEntry {
  canonical_topic_id: string;
  canonical_entity_id?: string;
  canonical_label: string;
  alias_set: string[];
  language_variants: string[];
  abbreviation_map: string[];
  related_brand_product_or_codename_keys: string[];
  resolution_state: "canonical" | "provisional";
}
```

执行约束：

- `canonical_topic_id` 解决“这是不是同一个方向话题”，`canonical_entity_id` 解决“这是不是同一个主体”；二者不得混写。
- `alias_set`、`language_variants`、`abbreviation_map` 和 `related_brand_product_or_codename_keys` 必须可被 normalization、claim-builder、audit 和 replay 共同消费，不能只存在于某个 Agent 的 prompt 或 notes 中。
- 当中英混写、简称、品牌名、产品代号尚未完全归一时，可以保留 `resolution_state="provisional"`；但对应事件不得被当作稳定独立交叉确认直接补足 `core` 门槛。
- 长尾词表可以持续扩充，但最小 canonicalization 契约必须在当前设计内成立；实现阶段不得把这部分退回为“之后人工理解即可”。

### `IndustrySignalEvent`

### 全局字段约定

以下约定适用于本文所有 interface，ExecPlan 不得为同名字段另行解释：

| 字段模式 | 含义 | 执行约束 |
| --- | --- | --- |
| `*_id` | 稳定机器 ID。 | 必须跨同一运行稳定；用于 artifact 之间引用时不得使用展示名、标题或随机 UUID 替代可归一 ID。 |
| `*_ref` / `*_refs` | artifact、source、event、tool 或 registry 的引用。 | 必须能在本次运行产物、registry snapshot 或 source trace 中解析；不可解析时必须进入缺口或 rejected audit。 |
| `reason_code` / `reason_codes` / `missing_reason_codes` / `degradation_reason_codes` | 稳定原因码。 | 必须使用 kebab-case 或 snake_case 的短码，可被测试 fixture 断言；自然语言解释应放入 `summary_cn` 或 notes。 |
| `summary_cn` / `*_summary_cn` / `notes_cn` | 中文可读解释。 | 只能总结结构化字段或引用事实，不得新增未在 event/source/audit 中出现的新事实。 |
| `*_at` | ISO datetime。 | 必须包含时区或采用统一 UTC 存储；展示层再转换为用户时区。 |
| `date` | `YYYY-MM-DD` 运行日期。 | 本设计默认按 Asia/Shanghai 的业务日解释。 |
| `public_safe` | 是否可进入公开 artifact。 | false 的对象不得被 weekly、visual console 或公开 JSON 消费，除非先经过 redaction 并生成新 safe artifact。 |
| `schema_version` | artifact schema 版本。 | breaking change 必须新版本；不得在同一版本下改变字段语义。 |

全局 rule：任何字段如果无法按上述约定生成，必须显式进入 `missing_reason_codes`、`rejected_reasons`、`unavailable_state.reason_code` 或对应 audit，不得静默省略。

`IndustrySignalEvent` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `event_id` | stable string | 行业事实事件的唯一 ID。 | 必须可被 claim、axis summary、audit 反向引用；不得每次运行随机变化。 |
| `observed_at` | ISO datetime | 系统首次观察到该事件的时间。 | 用于 freshness 和运行审计；不能替代来源发布时间。 |
| `source_published_at` | ISO datetime optional | 来源自身发布或更新该事实的时间。 | 有一手来源时间时必须填写；缺失时 freshness 必须降级或标注原因。 |
| `ingested_at` | ISO datetime | 事件进入行业证据包的时间。 | 用于 pipeline 审计，不参与事实新鲜度判断。 |
| `freshness_anchor_kind` | `FreshnessAnchorKind` | 该 event 计算 freshness 时所锚定的事件类型。 | 必须先识别 freshness anchor，再计算 freshness；不能把所有论文、政策、产品发布或社区事件套用同一时间窗。 |
| `freshness_profile_id` | string | 该 event 命中的 freshness profile。 | 必须能映射到 `freshness-decay-profile.v1`；不得留给 trend-agent 临时猜测。 |
| `freshness_reset_basis_event_ids` | string[] optional | 使旧事件 freshness 被刷新或重置的依据事件。 | 只有 revision、录用、benchmark 更新、复现、代码发布等真实刷新动作才可填写；不得因重复转述而刷新 freshness。 |
| `fact_id` | stable string optional | 底层事实 ID，用于把同一事实的跨轴投影、后续确认和评论型事件归到同一事实组。 | 同一底层事实被拆成多个 axis event 时应共享 `fact_id`；缺失时 normalization-agent 必须在 merge audit 中解释为何无法建立事实组。 |
| `provisional_fact_group_id` | stable string optional | 未能 canonical 归一时的临时事实组 ID。 | 当事件只能进入 provisional fact group 时必填；不得拿它伪装成 `fact_id`。 |
| `fact_resolution_state` | `canonical` / `merged_strong` / `merged_provisional` / `singleton_unresolved` / `conflicted` optional | 当前事件在事实归一层的状态。 | 进入 accepted normalized events 的 event 必须可落到该状态之一；`merged_provisional`、`singleton_unresolved`、`conflicted` 必须进入 `FactResolutionAudit`。 |
| `resolution_basis_codes` | string[] optional | 事实归一时使用的依据码。 | `fact_resolution_state!="canonical"` 时应填写；不得只写长段自然语言。 |
| `requires_fact_review` | boolean optional | 是否需要人工或高优先级审计复核该事实归一。 | true 时对应 unresolved group 必须能在 `FactResolutionAudit` 或 review queue 中反查。 |
| `derivation_type` | `direct_fact` / `cross_axis_projection` / `commentary` / `follow_on_confirmation` optional | 当前 event 与底层事实的关系。 | 同一事实的原始一手事件应优先标 `direct_fact`；由同一事实拆出的跨轴 event 必须标 `cross_axis_projection`；评论、转述和后续核验不得伪装成 `direct_fact`。 |
| `axis` | `IndustryEvidenceAxisKey` | 事件所属证据轴。 | 一个 event 只能有一个主 axis；跨轴证据必须拆成多个 event 并用 dedupe/source chain 关联。 |
| `source_polarity_cue` | `supporting` / `counter` / `missing_marker` / `context` | 事件在采集阶段表现出的来源级证据方向。 | 它只表示 source-level cue，不是最终 claim 裁决角色；claim 级 supporting / counter / context 必须由 `IndustryClaimEvidenceLink` 重新绑定。 |
| `source` | structured object | 来源本身的信息。 | `authority_tier` 必须按 `SourceAuthorityContextProfile` 解释。 |
| `actor` | structured object optional | 发出、发布或代表该事件的主体。 | 有明确主体时必须填写；没有主体的媒体转载不得伪装成 actor。 |
| `target` | structured object optional | 事件指向的 topic、repo、paper、product、policy 或 entity。 | 至少应提供一个可归一字段；否则只能进入低置信观察或 rejected。 |
| `agent_relevance` | structured object | Agent relevance gate 的结果。 | 必须包含 state、score、matched_reasons，并能映射到 `agent-relevance-profile.v1`。 |
| `authority_review` | `ProvisionalAuthorityReview` optional | 未入 registry 主体的临时权威审查。 | 只有临时权威桥接时填写；不能替代 registry 治理。 |
| `evidence` | structured object | 可公开消费的证据摘要、链接、引用和指标。 | `summary_cn` 必须是归一后的摘要，不得直接复制外部 Agent 自由文本作为事实。 |
| `collected_by_agent_id` | `IndustryAgentId` | 采集该事件的实际 Agent。 | 必须能在 `agent_contributions` 中找到对应贡献项。 |
| `responsibility_id` | `IndustryResponsibilityId` | 采集职责项。 | 必须与该 event 的 axis 匹配；跨职责复用需在 merge audit 中去重。 |
| `tool_route_id` | string optional | 产生该 event 的工具路线。 | 使用工具时必须可追溯到 `ToolRegistryEntry` 或 `AxisToolCoverageReport`。 |
| `audit` | structured object | public-safe、去重和 rejected 审计元数据。 | `public_safe=false` 的 event 不得进入公开 artifact；`dedupe_key` 必填。 |

约束：

- `url` 与 `raw_ref` 至少存在一个。
- `observed_at`、`source_published_at`、`ingested_at` 不得混写。
- `freshness_anchor_kind="unknown"` 时，该 event 不得作为 freshness 主导证据；必须降级、补齐或进入 rejected / context audit。
- 若同一底层事实拆成多个 axis event，这些 event 应共享 `fact_id`，并在 `derivation_type` 中区分原始事实、跨轴投影、评论和后续确认。
- `cross_axis_projection` event 可以参与对应 axis 的评分，但不得自动视为新的独立交叉确认来源；是否独立必须由 merge audit 和 claim link 审计共同确认。
- `merged_provisional` 与 `singleton_unresolved` 事件不得因为缺少 canonical `fact_id` 就默认 rejected；应保留进入 claim candidate、axis summary、counter evidence 或观察态的能力，但其独立性交叉确认能力必须受限。
- `conflicted` 事件不得用于正向升级；必须优先进入 counter/context/audit 路径。
- `authority_tier="excluded"` 的事件只能进入 rejected / audit，不参与评分。
- `primary_source_distance="rumor"` 的事件只能作为低置信观察或反向检索线索。
- 外部 Agent 的自由文本不能直接写成事实，必须经 adapter 映射到结构化字段。

### `fact-resolution-profile.v1`

为避免把事件简单分成“有 `fact_id` / 没 `fact_id`”，V1 冻结以下事实归一状态口径：

| `fact_resolution_state` | 含义 | 是否要求 `fact_id` | 是否允许 `provisional_fact_group_id` | 对 axis 评分的影响 | 对 `core` 交叉确认的影响 |
| --- | --- | --- | --- | --- | --- |
| `canonical` | 通过稳定 canonical identifier 或官方锚点确认的事实。 | 必须 | 可选 | 可全量参与 | 可作为完整事实单位 |
| `merged_strong` | 没有单一 canonical ID，但通过高置信规则确认是同一事实。 | 应有 | 可选 | 可全量参与 | 可作为完整事实单位 |
| `merged_provisional` | 很可能属于同一事实组，但仍存在结构不确定性。 | 可无 | 必须 | 可参与，但独立性和升级能力受限 | 不能单独补足 `core` 所需的唯一交叉确认 |
| `singleton_unresolved` | 暂时无法高置信并入其他事实组，只能保留为单点候选。 | 可无 | 可选 | 可参与，但独立性上限更低 | 不得单独补足 `core` 所需的事实独立性缺口 |
| `conflicted` | 归并过程中发现事实方向矛盾或无法统一解释。 | 可有 | 可有 | 进入 counter/context/audit 优先通道 | 不得用于正向升级 |

执行约束：

- `merged_provisional`、`singleton_unresolved`、`conflicted` 不得被实现层偷偷压回 rejected 默认路径。
- 同一 claim 若其主支撑大量停留在非 `canonical` / `merged_strong` 状态，系统应优先保留 claim 并在决策层降 tier、降 `decision_confidence` 或升级审计，而不是直接删除候选。

### `freshness-decay-profile.v1`

freshness 不是“按 axis 给一个天数”就能正确表达的公共货币。V1 先识别 event 的 `freshness_anchor_kind`，再按对应 profile 判断 high / medium / stale 窗口，并决定旧证据何时可以被 revision、录用、benchmark 更新、复现或代码发布刷新。

```ts
interface FreshnessDecayProfile {
  profile_id: string;
  anchor_kind: FreshnessAnchorKind;
  high_window_days: number;
  medium_window_days: number;
  stale_after_days: number;
  reset_allowed_by: FreshnessAnchorKind[];
  stale_usage: "background_only" | "supporting_only" | "can_support_if_revalidated";
}
```

V1 冻结如下：

| anchor_kind | high_window_days | medium_window_days | stale_after_days | reset_allowed_by | stale_usage |
| --- | ---: | ---: | ---: | --- | --- |
| `first_release` | 30 | 90 | 180 | `major_revision`、`code_or_replication_release`、`benchmark_or_dataset_update`、`accepted_or_proceedings` | `can_support_if_revalidated` |
| `major_revision` | 45 | 120 | 240 | `accepted_or_proceedings`、`code_or_replication_release`、`benchmark_or_dataset_update` | `can_support_if_revalidated` |
| `accepted_or_proceedings` | 90 或当前会议周期内 | 240 | 365 | `benchmark_or_dataset_update`、`code_or_replication_release` | `can_support_if_revalidated` |
| `benchmark_or_dataset_update` | 60 | 180 | 365 | `benchmark_or_dataset_update`、`code_or_replication_release` | `supporting_only` |
| `code_or_replication_release` | 90 | 365 | 540 | `code_or_replication_release`、`benchmark_or_dataset_update` | `supporting_only` |
| `official_product_release` | 30 | 90 | 180 | `official_product_release` | `supporting_only` |
| `filing_or_policy_effective_date` | 90 | 180 | 365 | `filing_or_policy_effective_date` | `supporting_only` |
| `community_thread_activity` | 7 | 21 | 45 | `community_thread_activity` | `background_only` |
| `unknown` | 0 | 0 | 0 | none | `background_only` |

执行约束：

- freshness 必须先按 `freshness_anchor_kind` 命中 profile，再映射到 axis scoring；不得把所有论文、政策、产品发布或社区讨论重新压成统一天数。
- 旧论文、旧政策或旧产品材料可以保留为历史上下文，但 stale evidence 不得单独主导核心趋势。
- 只有真实刷新动作才允许重置旧证据的 freshness；新闻转载、摘要复述或二次解读不得刷新 freshness。
- `research_paper` 与 `conference_academic` 的 freshness 计算必须显式区分预印本初版、major revision、accepted/proceedings、benchmark 更新和复现/代码发布。
- `freshness_profile_id` 必须进入 audit 或 contribution，可被测试 fixture 断言；不得只在代码里隐式推断。

### `SourceAuthorityContextProfile`

`authority_tier` 不是跨轴通用货币。`core / proven / watch / excluded` 必须在 `axis + source_type + primary_source_distance` 的上下文中解释；同一主体可以在一个证据轴是 `core`，在另一个证据轴只能是 `watch`。

V1 冻结规则：

| evidence axis | 可作为 `core` 的典型来源 | 不得替代的来源 |
| --- | --- | --- |
| `project_open_source` | 官方 repo / org、package registry、benchmark 原始记录、issue / PR 原链、依赖生态原始数据 | star 榜单、媒体项目清单、二手 awesome list |
| `research_paper` | 论文原文、arXiv / OpenReview / proceedings、作者机构页面、数据集 / 复现材料 | 论文解读、社媒摘要、无引用综述 |
| `conference_academic` | 官方 accepted list、proceedings、workshop / challenge / leaderboard / schedule | 媒体榜单、个人观后感、未核验议程截图 |
| `product_vendor_release` | 官方 blog、release notes、API docs、客户案例、官方 repo / org | PR 转述、媒体采访摘要、渠道商宣传 |
| `developer_studio` | 明确身份主体的 GitHub、个人博客、Substack、talk、podcast transcript、repo discussion | 搬运号、二创剪辑、无来源摘要 |
| `community_discussion` | 高质量社区原帖、GitHub Discussions、HN / Reddit 明确 thread、Hugging Face community 原帖 | 平台整体热度、转帖、泛问答或低质量评论区 |
| `capital_finance` | SEC / 财报 / 公司公告 / 投资方确认 / 专业数据库 | 未核验融资新闻、市场传闻、二手估值榜 |
| `policy_regulatory` | 政府、监管、标准组织、公共采购的一手文件 | 新闻解读、智库观点、企业合规宣传 |
| `policy_research_thinktank` | OECD.AI、CSET、Stanford AI Index、RAND、Brookings 等原始报告 | 媒体摘编、政策评论、无来源图表 |
| `news_pr_narrative` | 可追溯一手来源链的新闻、官方媒体、行业媒体、官方 PR | SEO 内容、搬运号、无法追溯来源的宣传 |

趋势升级时，`core / proven` 证据只能在其适配的 evidence axis 内推动升级；不得用一个轴的高权威来源替代另一个轴的一手证据。

`SourceAuthorityContextProfile` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `evidence axis` | `IndustryEvidenceAxisKey` | 该权威上下文适用的证据轴。 | 每个 axis 必须有独立上下文；不得把媒体、社区、政策、金融、论文等来源混用同一权威解释。 |
| `可作为 core 的典型来源` | source type / source pattern list | 在该 axis 中可以被解释为 `authority_tier="core"` 的来源形态。 | 只有同时满足 source type、primary source distance 和 registry tier 的来源，才能作为该 axis 的 core 推动证据。 |
| `不得替代的来源` | source type / source pattern list | 即使来源主体有名，也不能替代该 axis 一手证据的来源形态。 | 这些来源最多作为辅助、观察或反向检索线索；不得被 adapter 提升为该 axis 的 core/proven 一手证据。 |

该 profile 不新增 `authority_tier` 枚举值；它限定现有 `core / proven / watch / excluded` 在不同 axis 中如何解释。实现时必须先确定 `axis` 与 `source_type`，再解释 `authority_tier`，不能先给主体全局权威再套到所有 axis。

### `IndustryEntityRegistryEntry`

Seed Registry 是行业层的可维护事实底座。需求文档中的 Seed Registry 冻结基线是目标态覆盖基线，而不是最小可行版本或可被实现阶段继续裁剪的起步清单；设计和落地阶段均不得缩减、抽样实现或改写为少数热门主体。它不是永久闭集，也不能阻断对新兴高价值主体的前沿发现；新增主体只能在完整基线之上扩展，不能作为替代完整基线的理由。完整 materialize 指完整入库、可追溯和可治理，不等于每个 seed 都必须进入同频率、同预算的默认主动扫描。

| `source_urls` | URL[] | 主体可信入口。 | 至少包含一个可核验入口；空列表不能作为 active entry。 |

| `monitoring_tier` | `core_monitor` / `watchlist` / `cold_archive` | 该主体的默认巡检层级。 | 完整 seed registry 必须全部 materialize；但只有 `core_monitor` 默认进入每周主动扫描，`watchlist` 由触发信号或轮巡进入，`cold_archive` 仅用于低频复核、历史归档和实体对齐。 |
| `axis_monitoring_overrides` | object[] optional | 针对多轴主体的分轴巡检覆盖。 | 同一主体在不同 axis 上若需要不同频率、不同触发方式，必须在此覆写；没有 override 时才回退到全局 `monitoring_tier`。 |
| `maintenance_agent_id` | `IndustryAgentId` | 负责巡检该 entry 的 Agent。 | 必须是实际 Agent，不得填职责项或自由文本。 |
| `approval_agent_id` | `IndustryAgentId` | 批准新增、删除、降级的 Agent。 | 不能与 trend-agent 临时判断混同；高影响变更需 audit-agent 参与。 |
| `access_mode` | enum | 该主体主要访问方式。 | 成本、授权或不可用状态必须用该字段表达，不能写进散文。 |
| `review_status` | enum | registry entry 当前维护状态。 | `deprecated/unavailable` entry 不能作为 core/proven 推动证据。 |
| `lifecycle_status` | enum | 主体生命周期状态。 | rename/merge/退场必须显式落到该字段，不能靠删表或改展示名隐式处理。 |
| `lifecycle_effective_at` | ISO datetime optional | 生命周期状态生效时间。 | `lifecycle_status!="active"` 时应填写。 |
| `merge_into_entity_id` | string optional | 被合并或改名后指向的新 canonical 主体。 | `merged/renamed` 时必填；旧 ID 不能直接消失。 |
| `human_exception_required` | boolean | 是否需要人工例外处理。 | 只能用于争议、授权、法律风险或高影响删除，不得作为常规维护方式。 |

`ProvisionalAuthorityReview` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `state` | `ProvisionalAuthorityState` | 临时权威审查状态。 | 只有 `provisional_authority` 可在当周有限替代一个 core/proven 推动证据。 |
| `reviewed_by_agent_ids` | `IndustryAgentId[]` | 参与审查的 Agent。 | 必须包含 `registry-agent` 和 `audit-agent`；缺任一方不得成为 provisional authority。 |
| `basis_event_ids` | string[] | 支撑临时权威判断的事件。 | 必须是一手或近一手事件，或 core/proven 主体交叉引用事件。 |
| `required_registry_action` | enum | 后续 registry 动作。 | 不能为临时使用后静默消失；必须生成候选、更新或保留 watch 决策。 |
| `registry_candidate_ref` | string optional | registry 候选引用。 | `create_registry_candidate` 时必填。 |
| `expires_at` | ISO datetime optional | 临时权威过期时间。 | `provisional_authority` 必填；过期未入库自动回落。 |
| `limitations_cn` | string[] | 临时权威限制。 | 必须说明不能替代哪些证据轴、门槛或反证审计。 |

冻结规则：

- 新增来源必须写 `change_reason`。
- 删除来源必须写 `change_reason` 与 `replacement_entity_ids`，没有替代时必须写 `unavailable` 原因。
- `human_exception_required=true` 只用于争议项、付费授权项、法律风险项或高影响删除项。
- registry 不允许把“组织 / 研究组 / 品牌 / 产品线 / 个人 / 社区表面 / 会议系列”混成同一个 entry；若其来源表面、authority 语义或监控策略不同，必须拆成独立 entry，并通过 `parent_entity_id` / `related_entity_ids` 建立关系。
- `aliases` 只解决命名归一，不解决主体边界；例如 `OpenAI`、`OpenAI Research`、`ChatGPT`、`OpenAI DevDay` 若治理语义不同，必须是不同 entry，而不是放进同一 alias 列表。
- rename、merge、退场和失活只能通过 `lifecycle_status`、`merge_into_entity_id`、`replacement_entity_ids` 和生效时间表达；不得直接删除旧 entry，避免历史 replay 与引用断链。
- 同一 seed family 可以同时 materialize 父主体和子主体，但每个 event 只能命中一个最贴近事实语义的 canonical entry；父子主体不得双计为两个独立 authority 信号。
- `monitoring_tier` 必须表达扫描优先级，而不是主体重要性排名；降到 `watchlist` 或 `cold_archive` 不等于从 V1 覆盖基线移除。
- 多轴主体如在产品、研究、社区、开源等 axis 上需要不同扫描策略，必须使用 `axis_monitoring_overrides`；不得因为一个主体全局是 `watchlist` 就让其所有 axis 都失去主动覆盖。
- 高成本或授权受限来源必须用 schema 字段组合表达状态，不得引入未定义状态名：
  - 可选付费来源：`access_mode="optional_paid"`。
  - Agent 异步补证或待审来源：`review_status="needs_review"`，并在 `change_reason` 或后续审核记录中说明原因。
  - 人工授权例外：`access_mode="human_exception"` 且 `human_exception_required=true`。
  - 不可用或未覆盖来源：`access_mode="unavailable"` 或 `review_status="unavailable"`，并写明原因。
- 任何未进 registry 的主体默认最多只能被当作 `ordinary / watch` 处理，不能推动核心趋势升级；唯一例外是通过 `ProvisionalAuthorityReview.state="provisional_authority"`。
- 临时权威必须同时满足：
  1. 由 `registry-agent` 和 `audit-agent` 双方审查，`trend-agent` 不得自授权。
  2. 证据来自一手或近一手来源，或至少被两个独立 `core / proven` registry 主体交叉引用。
  3. `agent_relevance_score` 满足对应 `agent-relevance-profile.v1.core_claim_min`，且不是纯资本、政策、新闻或宣传热度。
  4. 必须生成 `registry_candidate_ref` 或明确 `reject_and_keep_watch`，不能只在当周趋势中临时使用后消失。
  5. 必须设置 `expires_at`；过期前未入库则回落为 `ordinary / watch`。
- 临时权威最多只能替代一条 claim 中的一个 `core / proven` 推动证据，不能替代三轴覆盖、反证审计、Agent relevance gate 或资本/政策/新闻降级规则。

每个证据轴必须有四级工具保障链路。

`ToolRegistryEntry` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `tool_id` | stable string | 工具 registry 唯一 ID。 | 必须可被 `tool_route_id`、`active_tool_ids`、coverage report 引用。 |
| `covered_axes` | `IndustryEvidenceAxisKey[]` | 工具可覆盖的证据轴。 | 工具只能服务列出的 axis；跨轴使用必须更新 registry。 |
| `route_level` | `primary_tool` / `secondary_toolset` / `fallback_tools` / `last_resort_mode` | 工具在四级保障链路中的层级。 | 不得因为工具可用就自动提升为 primary；primary 必须按 axis 评估。 |
| `source_class` | enum | 该工具默认访问的来源类型。 | 高权威轴的 primary route 必须优先命中 `official_structured_api` 或 `official_owned_feed_or_doc`；`general_web_search` 和 `manual_or_local_only` 不得直接成为政策、金融或官方发布轴的 primary。 |
| `retrieval_role` | enum | 该工具在链路中的职责。 | `canonical_fetch` 可直接产生可审计引用；`discovery/enrichment` 只能用于找线索或补元数据，除非后续命中 canonical fetch；`manual_verification` 只能进入 last resort 或人工例外。 |
| `access_mode` | enum | 调用或接入方式。 | `manual_drop` 只能作为补录或人工例外，不得成为自动链路默认路线。 |
| `cost_tier` | enum | 调用成本层级。 | `high` 或 `unknown` 不能作为 V1 硬依赖，除非有 fallback。 |
| `license_risk` | enum | 授权、抓取或使用风险。 | `high/unknown` 必须触发降级或人工例外说明。 |
| `freshness_sla` | `daily` / `weekly` / `event_driven` / `best_effort` | 工具理论新鲜度承诺。 | 低于证据轴需求时，只能作为 fallback 或 last resort。 |
| `failure_mode` | string[] | 已知失败模式。 | ExecPlan 必须映射为 reason code，不能只写自然语言。 |
| `availability_state` | `ToolAvailabilityState` | 当前可用状态。 | `partial/rate_limited` 产出的证据必须标记 degraded；`failed/unavailable/not_configured` 不得产出 supporting evidence。 |
| `replacement_tool_ids` | string[] | 替代工具。 | primary 失败时必须优先检查替代工具，再进入 last resort。 |
| `unavailable_state` | object optional | 不可用原因与影响轴。 | `failed/unavailable/not_configured` 时必填。 |

`ToolAvailabilityState` 语义冻结：`ok` 表示可正常用于当前 route；`partial` 表示覆盖不完整但可弱参与；`rate_limited` 表示受限可用且需要降级；`failed` 表示本次运行失败；`unavailable` 表示来源或工具当前不可用；`not_configured` 表示 V1 尚未配置该工具。后三者不得生成 supporting evidence。高风险轴如果只命中 `general_web_search`、`specialized_research_or_discovery` 或 `manual_or_local_only`，即使工具状态为 `ok`，也只能作为发现、补证或弱观察，不得跳过官方 canonical fetch 直接提升为 primary supporting evidence。

| `adjudicated_claim_archetype` | `IndustryClaimArchetype` optional | tier-decider 最终采纳的证据结构类型。 | 进入最终 `IndustryClaimLedger` 时必须存在；若缺失，只能把该 claim 当候选，不能当最终裁决对象消费。 |
| `archetype_basis_event_ids` | string[] | 支撑 archetype 判断的关键事件。 | `proposed` 与 `adjudicated` archetype 都必须能追溯到这些 event；不得只留自然语言解释。 |
| `archetype_revision_reason_code` | stable string optional | 从 `proposed` 改到 `adjudicated` archetype 的原因。 | 仅当二者不一致时可填写；不一致但缺该字段视为契约错误。 |
| `claim_scope` | enum | 主张与 Agent 的关系范围。 | 必须由 Agent Relevance Gate 结果导出，不能由 trend-agent 自由选择。 |
| `source_event_ids` | string[] | 参与生成候选的全部事件。 | 包含 supporting、counter、context、missing marker，不得只保留正证。 |
| `supporting_event_ids` | string[] | 支撑主张的事件。 | 它是 `IndustryClaimEvidenceLink.role in {leading_support, supporting}` 的派生摘要；只能引用通过 gate、归一、public-safe 和去重的 event。 |
| `counter_event_ids` | string[] | 反证事件。 | 它是 `IndustryClaimEvidenceLink.role = counter` 的派生摘要；必须进入 `CounterEvidenceAudit`。 |
| `claim_evidence_link_ids` | string[] | claim 与 event 的关系链接。 | 每个 supporting / counter / context event 都必须在 link 中声明 role 与依赖强度；不得只靠 `source_polarity_cue` 推断。 |
| `missing_axis_keys` | `IndustryEvidenceAxisKey[]` | 当前主张缺失的证据轴。 | 不能省略缺失轴；weekly 必须可见。 |
| `related_project_refs.role` | enum | 项目与 claim 的关系。 | `project_heat_only` 不得推动核心行业趋势；`landing_sample` 只是落地样本。 |

`IndustryClaimEvidenceLink` 是 claim 级证据绑定层。它负责把“事实事件”映射成“该 claim 当前如何使用这条事件”，从而避免多 claim 复用同一 event 时发生 supporting / counter 语义冲突。

`IndustryClaimEvidenceLink` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `link_id` | stable string | 单条 claim-event 关系唯一 ID。 | 同一 claim、event、role 和依赖强度在同一运行中必须稳定。 |
| `claim_id` | string | 被绑定的 claim。 | 必须指向当前窗口内已生成的 `IndustryClaim`。 |

### `IndustryClaimBuilder`

`IndustryClaimBuilder` 负责从多源行业证据生成方向级主张。它是 weekly 行业层摆脱旧项目聚类的关键边界，不能被实现为“旧 tag cluster 加证据挂载”。

输入冻结为：

- 最近 7 日 `DailyIndustryEvidencePack[]` 中已通过 `normalization-agent` 的 `IndustrySignalEvent[]`。
- 现有 `WeeklyEvidenceProject[]`，只能作为 `project_open_source` 轴和落地样本输入。
- `DailyExternalAggregate[]` 与 observer / mission discovery summaries，只能先转为 `IndustrySignalEvent` 或 rejected audit 后再参与。
- registry snapshot 与 tool registry snapshot，用于主体权威、来源归属、工具可用性和成本授权判断。

主张生成流程冻结为：

1. 先按 `Agent relevance gate` 排除 `generic_ai_background` 与 `out_of_scope`，保留 rejected reason。
2. 对剩余事件按 `topic_key`、canonical URL / DOI / repo URL / official domain、主体、机制语义、适用边界和证据轴聚合为 `claim_candidate_group`，并为候选生成稳定的 `claim_family_key` 与 `claim_granularity_key`。
3. 非 repo 证据可以独立触发 `claim_candidate_group`；不得要求必须存在 repo 或 supporting project。
4. 项目聚类只能触发 `project_heat_cluster_candidate`，除非至少存在一个非项目轴或高权威非 repo 事件与其合并。
5. `trend-agent` 的 claim-builder pass 只能在已归一事件、registry review、tool coverage 和 claim-builder 可见的反证候选上生成 `IndustryClaim` 与 `IndustryClaimEvidenceLink`，不得临时搜索原始来源补齐 claim；最终 tier decision 必须在 `audit-agent` 输出 `audit_result` 之后完成。
6. claim builder 必须为每个 claim 冻结唯一 `proposed_claim_archetype`；它必须反映主导证据结构，而不是最终等级判断。
7. claim 命名必须表达行业方向主张，而不是复用项目标签；`claim_statement_cn` 必须包含方向、适用边界和成立假设。
8. 每个生成的 claim 必须保留 `source_event_ids`、`supporting_event_ids`、`counter_event_ids`、`claim_evidence_link_ids` 和 `missing_axis_keys`，不得只保留摘要文案。
9. event 的 `source_polarity_cue` 只能作为 claim-builder 的初始 cue；最终 supporting / counter / context 归属必须落到 `IndustryClaimEvidenceLink.role`。
10. claim builder 必须为每条 `IndustryClaimEvidenceLink` 明确写出 `materiality_class`、`is_tier_material` 和 `materiality_reason_codes`；后续 audit 与 tier-decider 只能在显式 revision 留痕下修订，不能各自重建一套 material 口径。

### Claim 生成语法与粒度冻结

`IndustryClaim` 不是“某个 topic 最近很热”的松散聚类，而是一个最小可裁决主张。每条 claim 至少要同时回答四件事：

1. `direction`：行业中到底是哪一种 Agent 方向在变化。
2. `mechanism`：变化靠什么能力、工作流、运行时、协作模式或落地路径发生。
3. `scope`：这条主张成立于什么适用边界，是否只限研究前沿、产品落地、builder 生态、特定场景或地区。
4. `windowed judgment`：在当前周窗口中，它是“本周新形成”“历史延续被再次确认”，还是“只是前置信号”。

拆分规则：

- 若两个候选在 `main pillar`、关键机制、适用边界或证据结构上不同，即使 topic 接近，也必须拆成不同 claim。
- 若一个候选表达“技术成立/研究突破”，另一个表达“商业落地/采用扩散”，且二者依赖的 leading axes 或升级门槛不同，必须拆成相邻 claim family，而不是揉成一条大 claim。
- 若同一材料同时含有技术、产品、资本或政策多层叙述，但这些叙述进入 core 所需的结构条件不同，claim-builder 必须先拆再判，不能先合并后靠文案解释。

折叠规则：

- 若多个候选只是在措辞、来源包装、媒体叙事角度或同一材料的切片方式上不同，而主方向、主机制、适用边界和 material links 实际相同，必须折叠进同一 `claim_family_key`。
- 同一 `fact_id` / 同一 `claim_evidence_link` 组合被不同来源重复触发时，不得生成多条平行 claim 抢占审计队列；应保留一个 canonical candidate，其余作为 folded alternatives。

canonical candidate 选择规则：

- 同一 `claim_family_key` 内，优先保留主支柱最明确、`is_tier_material=true` links 最完整、`high_impact_unresolved_groups` 更少、关键独立交叉确认更强、且 source-chain 重复更低的候选作为 canonical candidate。
- 被 folded 的候选必须保留 audit 留痕和折叠原因，但不得在同一 run 中继续并发竞争 headline、same-run 高优先级审计或 same-run 补证容量。
- canonical 选择只能改变“同一语义簇中谁代表这条主张继续向前”，不能改变任何 tier 门槛，也不能把本该拆分的不同机制主张粗暴并成一个大 claim。

最低候选生成义务：

- 每个非项目证据轴中达到 `core / proven` 且满足对应 `agent-relevance-profile.v1.scoring_min` 的事件，必须至少尝试进入一个 `claim_candidate_group` 或 rejected audit。
- 每个职责项输出的 accepted events 都必须被 claim builder 统计为 used / rejected / deferred，不得静默丢弃。
- 若 7 日窗口中只有项目轴形成强信号，claim builder 必须生成 `project_heat_cluster` 或 `insufficient_evidence` 候选，而不是把它升级为行业主张。
- 每个生成的 claim 至少要有一条 `leading_support` link；如果没有形成明确主支柱 role，就必须进入 `wind_probe`、`project_heat_cluster` 或 `insufficient_evidence` 候选。

| --- | --- | --- | --- |

| `trigger_axis_keys` | `IndustryEvidenceAxisKey[]` | 触发候选生成的轴。 | 不能全为空；项目轴单独触发时只能生成项目热度或证据不足候选。 |
| `proposed_claim_archetype` | `IndustryClaimArchetype` optional | claim-builder 对该候选的 archetype 初判。 | `generated` 状态下必须存在；`rejected/deferred` 可为空。 |
| `archetype_basis_event_ids` | string[] | 支撑 archetype 初判的关键事件。 | `generated` 状态下不能为空；不得只凭趋势文案猜 archetype。 |
| `archetype_reason_codes` | string[] | archetype 初判依据。 | 必须是稳定短码，便于 fixture 与 diff audit 对比。 |
| `overlap_cluster_id` | stable string optional | 语义重叠候选折叠簇 ID。 | 命中候选折叠时必须填写；同一 overlap cluster 内的候选在同一运行中必须稳定。 |
| `canonical_candidate_group_id` | stable string optional | 被保留进入 audit / tier-decider 的 canonical candidate。 | 当前记录若属于 overlap cluster，则必须填写；canonical 自身应指向自己，folded 候选应指向被保留对象。 |
| `folded_candidate_group_ids` | string[] optional | 与当前候选一起被折叠的其他候选组。 | canonical 记录应列出全部 folded 候选；folded 记录可为空或只保留 canonical 指针，但不得完全丢失重叠关系。 |
| `fold_reason_codes` | string[] optional | 触发候选折叠的原因。 | 命中候选折叠时不能为空；必须使用稳定短码，如 `same-candidate-group`、`same-material-links`、`high-source-overlap`、`same-claim-family`。 |
| `trigger_reason` | enum | 候选被触发的原因。 | 必须使用枚举值；不能自由文本绕过项目热度限制。 |
| `claim_generation_state` | `generated` / `rejected` / `deferred` | 候选生成结果。 | `generated` 必须有 `generated_claim_id`；`rejected/deferred` 必须有可解释 `reason_code`。 |
| `reason_code` | stable string | 生成、拒绝或暂缓原因。 | 必须可被测试 fixture 断言，不得只写自然语言。 |

执行补充：

- claim builder 可以保留所有 accepted events 的 accounting，但不得要求所有候选 claim 都进入同等深度的十轴聚合和审计；真正进入最终 tier 竞争的 claim 必须经过可追溯的候选收敛。
- 候选收敛只能影响“进入后续阶段的 claim 数量”和“本轮预算吞吐”，不得改变任何 tier 规则门槛，也不得让未审计 claim 越级进入最终 ledger。
- 若大量 `merged_provisional` / `singleton_unresolved` 事件形成候选，claim builder 应优先保留候选并在 audit / decision 层限权，而不是在 candidate generation 阶段大面积丢弃。

防缩水规则：

- 不得用旧 weekly tag / paradigm cluster 直接作为 `IndustryClaim`，除非它通过上述候选生成流程重新生成并留下 audit。
- 不得把单个 Agent 的自由文本主题建议直接写成 claim；必须能追溯到结构化 event。
- 不得因为缺少 repo 而丢弃论文、会议、政策、融资、产品发布、社区讨论或智库报告。
- 不得只输出最终 claim 列表而不保留 candidate audit；否则无法验证哪些行业信号被忽略。
- 不得把 `capital_policy_attention` 或 `project_heat_cluster` claim archetype 在没有显式 claim builder audit 的情况下改写成 `research_frontier`、`product_adoption` 或 `builder_ecosystem`。

轴评分不采用全轴统一权重。六个子分是共同审计语言，但每个 evidence axis 必须使用更适合其证据形态的 `AxisScoringProfile`。所有 profile 的权重和为 `1.00`，`axis_score` 的计算公式为：

```text
axis_score =
  weight.authority * authority_score
+ weight.primary_source * primary_source_score
+ weight.independence * independence_score
+ weight.freshness * freshness_score
+ weight.continuity * continuity_score
+ weight.agent_relevance * agent_relevance_score
```

V1 `axis-scoring-profile.v1` 冻结如下。下表是每轴的初始 prior weight，不是可以绕过 profile cap 的万能补偿器；任何 axis 都不得靠单个子分过高把低质量、低一手度或低相关性的证据硬顶进 core trend。

| axis_key | authority | primary_source | independence | freshness | continuity | agent_relevance | 评分重点 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |

`axis-subscore-rubric.v1` 执行约束：

- `authority_score` 必须先经过 `SourceAuthorityContextProfile`；同一主体在非适配 axis 中最高只能按 `watch` 或更低处理。
- `primary_source_score` 的上限由 `primary_source_distance` 决定：`primary / near_primary` 可高分，`secondary` 原则上不得超过 60，`rumor / unknown` 不得超过 25，除非进入 rejected / counter audit。
- `independence_score` 必须先应用 `IndustryMergeAudit` 的 source-chain、repeated-actor 和 dedupe 结果；不得以原始材料条数计算。
- `freshness_score` 可以按 axis 曲线细化，但 `freshness_state` 也必须单独输出；`stale` evidence 不能作为核心趋势主导证据，除非有更新来源复核。
- `continuity_score` 必须表示跨时间、跨主体或跨证据链的持续性；单条高权威材料不能自动得到高 continuity。
- `agent_relevance_score` 必须先满足 `agent-relevance-profile.v1` 的 profile 门槛；不允许用其他子分补偿低于 `auxiliary_min` 的 Agent 相关性。
- `primary_source_score < 50` 时，当前 axis 最高只能为 `medium`；若同时缺少独立 corroboration，最高只能为 `weak`。
- `research_paper` 若 supporting evidence 只来自单篇未复核预印本，且不存在 accepted/proceedings、benchmark 更新、复现或代码发布，则该轴最高只能为 `medium`。
- `news_pr_narrative` 不得作为 `IndustryTrendDecision.leading_axes`；即使该轴 `axis_score` 达到 `strong`，也只能作为 supporting 或 narrative signal。
- `capital_finance`、`policy_regulatory` 和 `policy_research_thinktank` 可以各自成为 strong axis，但不得借高 authority 或高 freshness 单独补偿 technical / landing / builder / adoption 类证据缺失。

实现可以在 ExecPlan 中细化每个子分的计算方式，但不得删除六个子分，不得让任一 evidence axis 回退到统一权重公式或统一子分 rubric，也不得把轴评分改成材料数量相加。权重或 rubric 如需调整，必须新开 scoring design，版本化为新的 `score_formula_version` 或 `axis-subscore-rubric` 版本，并用 fixture 证明不会产生项目热度吞没、资本/政策/宣传泡沫或泛 AI 漂移。

| --- | --- | --- | --- |

| `strong_min` | `0-100` number | 该 axis 被判为 `status="strong"` 的最低 `axis_score`。 | `axis_score >= strong_min` 时可判为 `strong`，但仍受反证、工具降级和缺失状态约束。 |
| `medium_min` | `0-100` number | 该 axis 被判为 `status="medium"` 的最低 `axis_score`。 | `medium_min <= axis_score < strong_min` 时可判为 `medium`；低于 `medium_min` 不能算核心趋势所需的 medium 轴。 |
| `early_signal_min` | `0-100` number | 该 axis 可作为早期方向信号的最低分。 | 只用于 `wind_probe`、观察或补证触发；达到它不等于可进入核心趋势。 |
| `project_heat_min` | `0-100` number 或 `n/a` | 开源项目热度簇的专用门槛。 | 仅 `project_open_source` 可为数字；其他 axis 必须为 `n/a`，不得用它生成项目热度簇。 |
| `core_upgrade_role` | `technical_support` / `landing_support` / `builder_support` / `adoption_support` / `attention_signal` / `narrative_signal` | 该 axis 在核心趋势升级中的角色。 | `attention_signal` 和 `narrative_signal` 不能单独推动核心趋势；必须与 technical、landing、builder 或 adoption 类证据交叉确认。 |
| `阈值口径` | 文本约束 | 该 axis 的状态判定注意事项。 | ExecPlan 必须转成测试 fixture 或 reason code，防止只按数字跳级。 |

核心升级角色语义冻结如下：

| role | 含义 | 常见轴 | 执行约束 |
| --- | --- | --- | --- |
| `technical_support` | 证明该方向有明确技术方法、研究突破或学术确认。 | `research_paper`、`conference_academic` | 能回答“技术上是否站得住”，但不能替代产品、采用或政策事实。 |
| `landing_support` | 证明该方向已进入产品能力、接口、交付或可用落地样本。 | `product_vendor_release`、部分 `project_open_source` | 能回答“是否开始真正用起来”，但不能只靠 PR 或概念演示。 |
| `builder_support` | 证明一线 builder、开发者、工作室或 maintainer 持续投入。 | `developer_studio`、部分 `project_open_source` | 强调持续建设者网络，避免单次爆红或个人观点替代行业趋势。 |
| `adoption_support` | 证明外部用户、开发者或社区开始独立讨论、复现、采用或迁移。 | `community_discussion`、部分 `project_open_source` | 强调扩散与采用，不等于单平台热度。 |
| `attention_signal` | 证明资本、政策、监管或智库开始配置资源、形成制度注意或产业关注。 | `capital_finance`、`policy_regulatory`、`policy_research_thinktank` | 在风向探针阶段属于高优先级主证据；在核心趋势成立阶段通常只作增强或交叉确认。 |
| `narrative_signal` | 证明行业叙事、媒体传播或 PR 放大正在升温。 | `news_pr_narrative` | 可帮助发现与解释方向，但不得替代技术、落地或采用支柱。 |

| `coverage_audit_state` | `full` / `partial` / `degraded` / `unavailable` | 关键证据、归一和审计的完成状态。 | 必须与实际 audit / tool coverage 对齐；不得被折叠进 `decision_confidence` 或 `decision_tier`。 |
| `consumer_readiness_state` | `ready` / `provisional` / `needs_review` / `blocked_public_output` | 下游默认应如何消费该裁决。 | 下游必须先读取它，再读取 `decision_tier`；禁止只凭 tier 把 claim 当成已成立核心趋势。 |
| `consumer_display_priority` | `headline_candidate` / `secondary_candidate` / `watchlist_only` / `internal_only` | 下游展示和排序优先级。 | 周报、卡片和 API 默认按它排序；不得只按 `decision_tier` 排序。 |
| `decision_reason_cn` | string | 等级裁决理由。 | 必须引用 leading/supporting/missing/counter axes，不得只写概括判断。 |
| `leading_axes` | `IndustryEvidenceAxisKey[]` | 主要推动等级裁决的轴。 | 只能包含达到对应 status profile 门槛且未被强反证阻断的轴。 |
| `supporting_axes` | `IndustryEvidenceAxisKey[]` | 辅助支撑轴。 | 不能替代 leading axes；attention/narrative 轴默认只能 supporting，除非规则允许 wind probe。 |
| `material_claim_evidence_link_ids` | string[] | 当前 claim 的 tier material links。 | 必须与 `IndustryClaimEvidenceLink.is_tier_material=true` 的 links 一致；`full` 审计至少要覆盖这些 links。 |
| `key_independent_confirmation_link_ids` | string[] | 被认定为关键独立交叉确认的 links。 | 不得只在解释文案中出现；缺它们会直接影响 core 判定。 |
| `unaudited_material_link_ids` | string[] | 尚未完成审计的 material links。 | 非空时 `coverage_audit_state` 不得为 `full`；若这些 links 命中主支柱、关键独立交叉确认或 blocking path，必须触发降 tier 或保守消费。 |
| `missing_axes` | `IndustryEvidenceAxisKey[]` | 缺失或不可用轴。 | 必须与 `AxisEvidenceSummary.status=missing/unavailable` 对齐。 |
| `counter_axes` | `IndustryEvidenceAxisKey[]` | 存在反证或冲突的轴。 | 必须与 `CounterEvidenceAudit.counter_event_ids/conflict_groups` 对齐。 |
| `not_complete_unless` | string[] optional | 完成态缺口条件。 | 用于说明进入更高等级仍缺什么；不能替代 `missing_axes`。 |
| `claim_evidence_links` | `IndustryClaimEvidenceLink[]` | claim 级证据关系图。 | 最终 tier decision、counter audit 和 explainability 都必须基于它，而不是直接读取 `source_polarity_cue`。 |
| `ledger_id` | stable string | 单条 claim ledger 唯一 ID。 | 必须可追溯到窗口、claim 和 schema version。 |
| `window_start/window_end` | date / datetime | 周级判断窗口。 | 所有 included event 必须可解释为何落入或影响该窗口。 |
| `fact_resolution_audit` | `FactResolutionAudit` | 事实归一、未决组和关系边审计。 | tier-decider、audit-agent 和下游人工复核都必须能从 ledger 反查它；不得只看 merge winner。 |
| `public_safe` | boolean | ledger 是否可公开消费。 | false 时不得进入公开 weekly 或 visual console。 |

执行补充：

- `decision_tier`、`decision_confidence`、`coverage_audit_state` 是三元裁决语义，必须同时存在；任何 consumer 只读取其中一个都属于契约违背。
- `consumer_readiness_state` 与 `consumer_display_priority` 不是前端装饰字段，而是强制消费顺序：下游必须先判 readiness，再判 display priority，最后才可用 `decision_tier` 做排序或文案。
- 当 `decision_tier="core_industry_trend"` 但 `consumer_readiness_state!="ready"` 时，该 claim 只能进入内部 ledger、provisional watchlist 或 needs-review 分桶，不得直接进入 headline core output。

下游消费优先级矩阵冻结如下：

| 顺序 | 判断对象 | 默认动作 |
| --- | --- | --- |
| 1 | `public_safe` | `false` 时只允许 internal / blocked public consumption，不进入公开 headline 选择 |
| 2 | 未关闭的 `P0` review、`blocking_output_scope`、authority hold | 先执行阻断或限权，再决定是否还能进入公开分桶 |
| 3 | `consumer_readiness_state` | 先决定 `ready / provisional / needs_review / blocked_public_output` 可落入哪些桶 |
| 4 | `consumer_display_priority` | 在同一 readiness 桶内决定 headline / secondary / watchlist / internal 排序 |
| 5 | `decision_tier` | 只回答“这是什么趋势等级”，不得越过前四步直接驱动公开展示 |
| 6 | `decision_confidence` | 只在同 tier 或相邻候选之间参与排序与文案强度控制 |
| 7 | `coverage_audit_state` | 作为告警、tie-break 和解释约束，不得反向篡改前序 gating 语义 |

合法组合示例：

- `core_industry_trend + ready + headline_candidate` 才允许进入 public headline core。
- `core_industry_trend + provisional` 只能进入 provisional watchlist，不得伪装成已确认 core。
- `observing_industry_trend + needs_review` 可以保留在内部 ledger 或 needs-review bucket，但不得跨过 review gate 直接公开强化表述。

### 唯一 Surface 映射矩阵

为避免“内部是 core，外部却像 observing”这类实现分叉，当前设计补充冻结两层映射：

1. `tier section`：只由 `decision_tier` 决定，一张卡必须且只能落入一个主分区。
2. `display bucket`：只由 `public_safe`、blocking governance、`consumer_readiness_state` 和 `consumer_display_priority` 决定，一张卡必须且只能落入一个显示桶。

`display bucket` 唯一映射如下：

| 条件 | 唯一 bucket | 强制动作 |
| --- | --- | --- |
| `public_safe=false` | `suppressed_card_ids` | 只允许 internal consumption；不得进入任何公开分桶。 |
| `consumer_readiness_state="blocked_public_output"`，或存在未关闭的 `P0` 且 `blocking_output_scope="public_output"` | `blocked_public_output_card_ids` | 可保留内部 tier，但公开消费必须阻断。 |
| `consumer_readiness_state="needs_review"` | `needs_review_card_ids` | 允许 internal / needs-review 消费，不得进入公开核心分桶。 |
| `decision_tier="core_industry_trend"` 且 `consumer_readiness_state="provisional"` | `provisional_core_watchlist_card_ids` | 保留 core tier 语义，但只能作为 provisional watchlist。 |
| `decision_tier="core_industry_trend"` 且 `consumer_readiness_state="ready"` 且 `consumer_display_priority="headline_candidate"` | `headline_core_card_ids` | 允许进入公开 headline core。 |
| 其余组合 | 隐式 `tier_native_only` | 只保留在其 `decision_tier` 对应主分区；不得被额外塞进其他 `display_index` 列表。 |

执行约束：

- `display_index` 中的显式数组是对主分区的二级消费索引，不是另一套 tier。
- 同一 `card_id` 在同一次 weekly 中不得同时出现在两个显式 display bucket 中。
- 若某卡命中更高优先级 bucket，如 `suppressed` 或 `blocked_public_output`，则下位 bucket 不得再收录它；禁止“既 blocked 又 headline”的冲突状态。

| --- | --- | --- | --- |
| `review_id` / `override_id` | stable string | review / override 全局唯一 ID。 | 必须可被 weekly、治理面和 replay 反查。 |
| `schema_version` | literal string | review / override 结构版本。 | breaking change 必须升级版本；不得在同一版本下改语义。 |
| `trigger` | enum | 进入复核的触发原因。 | 不得以自由文本 `other` 代替常见治理触发。 |
| `review_priority` | `P0` / `P1` / `P2` | 复核优先级。 | `P0` 表示 same-run blocking；`P1` 表示 `24h` 内处理；`P2` 允许进入 backlog。 |
| `impact_scope` | `tier_blocking` / `public_output_only` / `confidence_only` / `authority_only` | 当前问题会影响哪一层决策。 | 只有 `tier_blocking` 默认要求 same-run 人工兜底；其余 scope 优先自动降级或限权。 |

| `blocking_output_scope` | `public_output` / `tier_upgrade` / `none` | 未关闭 review 时阻断的输出范围。 | `P0` 默认不得为 `none`；命中 scope 时 weekly 和 public projection 必须执行阻断或降级。 |
| `default_system_action` | enum | 人工结论未返回前，系统默认先怎么处理。 | 必须与 `impact_scope` 一致；例如 `confidence_only` 只能保 tier 降置信，不能偷偷改 tier。 |
| `required_resolution_by` | ISO datetime optional | 最晚完成时间。 | `P0` 必须落在当前 run 或显式 rerun 窗口内；`P1` 默认 `24h`；`P2` 可为空。 |
| `target_ref` | object | 被复核或被覆盖的 canonical 对象。 | 必须至少包含 `kind`、`id` 和 `artifact_ref`。 |
| `queue_state` | `open` / `assigned` / `in_review` / `closed` / `expired` | review 队列状态。 | 只有 `closed` 才算已关闭；`expired` 必须继续影响 backlog 或降级状态。 |
| `current_state` | string | review 前的系统状态。 | 必须足以还原 review 前判断。 |
| `requested_action` | enum | 希望执行的治理动作。 | 不得直接修改 canonical artifact；必须通过 audit 或 rerun 落账。 |
| `reviewer_id` / `actor_id` | string | 执行 review / override 的主体。 | 不允许匿名主体。 |
| `decision` | enum | review 结论。 | `queue_state!="closed"` 时不得被当作通过；`expired` 不等于通过。 |
| `reason_cn` / `reason_code` | string | 治理理由。 | 必须可被 weekly、治理台或 audit snapshot 摘要引用。 |
| `before_value` / `after_value` | JSON-like | override 前后值。 | 必须保留完整差异，不得只写摘要。 |
| `expires_at` / `created_at` | ISO datetime | override 生命周期时间。 | 非永久修正必须有过期时间；`created_at` 用于审计排序。 |

执行补充：

- `run_budget_summary.review_backlog_p1_or_higher` 必须由 `review_priority in {P0,P1}` 且 `queue_state!="closed"` 的 `HumanReviewQueueItem[]` 聚合得出，不得人工手填。
- Trend tier、source authority、public-safe 状态、registry promotion 和 claim suppression 都属于高影响治理动作；相关人工变更必须写入 `OverrideAudit`。
- `DailyExternalAggregate[]` 与 observer / mission discovery summaries 只能先转为 `IndustrySignalEvent` 或 rejected audit 后，才可通过 `HumanReviewQueueItem`、`CounterEvidenceAudit` 或 claim-builder 输入参与 weekly 判断。
- 当 claim 处于 `decision_state="contested"` 且争议尚未关闭时，若需要继续发布，最高只能以下调 tier 或降置信的形式保留，不得维持 `core_industry_trend` 的公开输出。
- `queue_state="expired"` 不等于默认通过；若 `blocking_output_scope` 仍命中，则 weekly/public projection 必须继续阻断、降级或 rerun。
- `impact_scope="confidence_only"` 且 `auto_resolution_allowed=true` 的事项，默认不应进入 same-run blocking 人工复核；系统应先执行 `default_system_action`，人工只做抽检、追责或后补治理。

| `snapshot_id` | stable string | 当前 run 关闭后的事实快照 ID。 | claim-builder、audit、weekly、eval 和 replay 必须引用同一快照；不得在快照关闭后静默改写本轮记账结果。 |
| `event_fact_assignments` | object[] | 事件到事实状态的映射。 | 所有 `merged_provisional`、`singleton_unresolved`、`conflicted` 事件都必须留痕。 |
| `relation_edges` | object[] | 事件两两间的事实关系边。 | 不能只保留 merge winner；必须能区分同一事实、多轴投影、后续确认、传播链和矛盾关系。 |
| `high_impact_unresolved_groups` | object[] | 会影响 tier 或 blocking judgement 的未决事实组。 | 非空时 audit-agent 和 tier-decider 不得静默忽略；必须影响置信度、降级、人工复核或 rerun。 |
| `impacted_link_ids` | string[] | 该未决组影响到的 claim links。 | 必须显式指出是否命中主支柱、关键独立交叉确认或 blocking path，避免各 Agent 各自脑补。 |
| `impact_scope` | `tier_blocking` / `public_output_only` / `confidence_only` / `authority_only` | 未决组会影响哪一层裁决。 | 这是自动/人工边界的机器可执行依据，不能只写在自然语言备注里。 |
| `auto_resolution_allowed` | boolean | 是否允许系统先自动降级或限权。 | `false` 时才默认升级到人工复核或同 run rerun。 |
| `default_system_action` | enum | 未决组尚未解决时的系统默认动作。 | 必须与 `impact_scope` 对齐，且可直接映射到 tier/`decision_confidence`/public output 行为。 |

执行补充：

- `normalization-agent` 必须先完成 Source Chain 层去重，再做 Fact 层归并；不得跳过传播链判断直接把 event 条数当成事实条数。
- 事实归一的输出不仅是“最后合并成什么”，还包括 `relation_edges` 和 `high_impact_unresolved_groups`；实现不得只保留 merge winner。
- `snapshot_id` 标识当前 run 已结算的 fact snapshot。`claim-builder` 只能消费快照关闭后的 `FactResolutionAudit`；owner transfer、attestation 合并或主语义改写若晚于该快照，只能进入下一 run 或显式 rerun。
- 当同一事实既可能被解释为 `follow_on_confirmation`，也可能是新的 `distinct_but_related` 事实时，必须进入 `high_impact_unresolved_groups` 或人工复核队列，不得静默择一。
- `high_impact_unresolved_groups` 不是“默认全部进人工”的同义词；只有 `impact_scope=tier_blocking` 或 `auto_resolution_allowed=false` 时，才默认要求 same-run 人工复核或 rerun。其余情况应先按 `default_system_action` 自动处理，并把影响体现在 `decision_confidence`、`coverage_audit_state` 或 public output 限制上。

`IndustryTrendCard` 与 `WeeklyIndustryTrendSection` 执行约束冻结如下：

- `IndustryTrendCard` 必须直接镜像 ledger 中的 `decision_tier`、`decision_confidence`、`coverage_audit_state`、`consumer_readiness_state` 和 `consumer_display_priority`；不得在卡片层重新脑补“更积极”的展示状态。
- `freshness_summary` 必须由已归一 event 的 freshness anchor 与 freshness profile 计算得出；不得把 run date、`observed_at` 或抓取时间伪装成 freshness 结论。
- 任一 consumer 在排序和分桶时，必须先执行 `public_safe` 与 blocking governance gate，再使用 `consumer_readiness_state`、`consumer_display_priority`、`decision_tier`、`decision_confidence` 和 `coverage_audit_state`。只按 tier 排序视为契约违背。
- `WeeklyIndustryTrendSection` 的 tier 分区和 `display_index` 必须来自同一份 ledger snapshot；前者表达“这是什么趋势”，后者表达“当前能如何消费与展示”，二者不得各自重算。
- `WeeklyIndustryTrendSection` 必须保留 `lineage_refs`、`run_budget_summary` 和 `run_snapshot`，确保下游能反查 claim lineage、fact snapshot、审计覆盖、窗口预算和 same-run snapshot 边界，而不是只看到展示结果。
- `evidence_window_status`、`publication_readiness_status` 和 `governance_load_status` 分别回答“证据窗口是否足够”“公开消费是否可放行”“治理负载是否过高”；三者不得再被单一 `industry_window_status` 偷换。
- `industry_window_status` 是对上述三类状态的聚合摘要，只用于用户总览和回退提示；任何阻断逻辑都必须回读更具体的三类状态，而不是只看聚合值。
- `decision_tier="core_industry_trend"` 且 `consumer_readiness_state="ready"` 的 card，才允许进入 `display_index.headline_core_card_ids`。
- `decision_tier="core_industry_trend"` 但 `consumer_readiness_state="provisional"` 的 card，必须进入 `display_index.provisional_core_watchlist_card_ids`，不得伪装成已确认 headline core。
- `consumer_readiness_state="needs_review"` 的 card 不得进入公开核心趋势分桶；最多进入 `display_index.needs_review_card_ids` 或内部 watchlist。`consumer_readiness_state="blocked_public_output"` 的 card 必须进入 `display_index.blocked_public_output_card_ids` 或 `display_index.suppressed_card_ids`。
- `warning_badges` 至少应覆盖 `partial_audit`、`low_confidence`、`public_blocked`、`human_review_pending`、`main_pillar_gap` 等稳定短码，确保下游不会忽略关键缺口。
