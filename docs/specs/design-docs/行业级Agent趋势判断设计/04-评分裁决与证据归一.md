# 行业级 Agent 趋势判断：评分裁决与证据归一

> 本文档拆自 [行业级Agent趋势判断设计文档.md](../行业级Agent趋势判断设计文档.md)，是行业级 Agent 趋势判断设计文档包的一部分。

## 趋势等级裁决

### `claim-archetype-decision-profile.v1`

趋势裁决先看 `claim_archetype`，再看十轴状态与反证。当前设计不允许把所有行业主张都压回同一套“至少 3 轴 + 至少 1 个 core/proven”门槛，否则研究前沿、产品落地、builder 生态、资本/政策注意力和项目热度簇会被误判成同一种东西。

当前设计冻结以下 archetype：

| `claim_archetype` | 含义 | 进入 core 时最关键的证据结构 |
| --- | --- | --- |
| `research_frontier` | 研究、方法、benchmark 或会议方向正在形成稳定技术信号。 | `research_paper` 或 `conference_academic` 至少一个 strong，且存在复现、benchmark、产品、开源或 builder 侧确认。 |
| `product_adoption` | 厂商、平台或产品能力正在形成真实落地采用。 | `product_vendor_release` 至少 medium，且有社区、开源、builder、客户或采用信号交叉确认。 |
| `builder_ecosystem` | 开发者、工作室、maintainer 与 OSS 生态正在形成持续 builder 方向。 | `developer_studio` 或 `project_open_source` 至少一个 strong，且社区采用与独立主体数量足够。 |
| `capital_policy_attention` | 资本、政策、监管、智库或新闻叙事构成前置信号，但未天然等于技术成熟或落地。 | attention / narrative 轴可以触发观察或风向探针；进入 core 仍需技术、产品、社区或开源侧交叉确认。 |
| `project_heat_cluster` | 多个独立项目正在形成热度簇，但尚不足以证明行业方向成立。 | 必须证明它真的是“簇”，而不是单一爆款 repo。 |

`claim-archetype-axis-applicability.v1` 冻结如下，用于决定十轴完整输出时哪些轴构成主义务、哪些轴只作补强、哪些轴不应被伪装成“待补齐主债务”：

| `claim_archetype` | 默认 `required` | 默认 `supporting_optional` | 默认 `not_material_for_archetype` |
| --- | --- | --- | --- |
| `research_frontier` | `research_paper`、`conference_academic`，以及 `project_open_source` / `developer_studio` / `product_vendor_release` / `community_discussion` 中至少一个能承担独立交叉确认的轴 | `capital_finance`、`policy_regulatory`、`policy_research_thinktank`、`news_pr_narrative`，以及未承担主支柱的其他技术/落地轴 | 与当前研究方向没有直接落地关系、且只会制造伪缺口的长尾叙事轴 |
| `product_adoption` | `product_vendor_release`，以及 `project_open_source` / `developer_studio` / `community_discussion` 中至少一个交叉确认轴 | `research_paper`、`conference_academic`、`capital_finance`、`policy_regulatory`、`policy_research_thinktank`、`news_pr_narrative` | 与当前采用判断无直接关系的长尾研究或政策评论轴 |
| `builder_ecosystem` | `developer_studio` 或 `project_open_source`，以及 `community_discussion` 交叉确认轴 | `research_paper`、`conference_academic`、`product_vendor_release`、`capital_finance`、`policy_regulatory`、`policy_research_thinktank`、`news_pr_narrative` | 与 builder 生态形成无直接关系的纯政策或纯资本长尾轴 |
| `capital_policy_attention` | 至少一个 `capital_finance` / `policy_regulatory` / `policy_research_thinktank` / `news_pr_narrative` lead 轴，以及至少一个 `research_paper` / `conference_academic` / `product_vendor_release` / `developer_studio` / `community_discussion` / `project_open_source` 技术或落地交叉确认轴 | 其余未承担主支柱的 attention / narrative / technical / landing 轴 | 与当前注意力方向无直接关系的长尾轴 |
| `project_heat_cluster` | `project_open_source` | `developer_studio`、`community_discussion`、`product_vendor_release` | 大部分政策、资本、智库和新闻轴默认不构成主缺口，只保留为上下文观察 |

`claim-archetype-decision-profile.v1` 执行约束：

- `claim-builder` 必须先产出 `proposed_claim_archetype`，`tier-decider` 必须产出 `adjudicated_claim_archetype`；二者都必须在 `IndustryClaimBuilderAudit` / decision lineage 中可追溯。
- 若 `tier-decider` 不采纳 `proposed_claim_archetype`，必须显式写入 `archetype_revision_reason_code`、对应证据依据和 revision actor；不得静默改 archetype 以满足更高等级门槛。
- `capital_policy_attention` 与 `project_heat_cluster` 这类 archetype 默认不是核心行业趋势的捷径；它们必须满足额外交叉证据要求。
- archetype 只定义“该看哪类证据结构”，不绕过十轴、authority、freshness、counter evidence 或 Agent relevance gate。
- `AxisEvidenceSummary.axis_applicability_state` 必须先根据 `claim-archetype-axis-applicability.v1` 判定，再计算 `missing_axes`、same-run gap priority 和 weekly 缺口账本；不得把所有负状态都写成主缺口。

### 裁决输出语义分离

趋势裁决必须并行输出三组语义，禁止再用单一“降 tier”同时表达证据不足、流程未跑完和判断本身不成立：

- `decision_tier`：只回答“这条行业主张按证据语义属于什么等级”。
- `decision_confidence`：只回答“在当前证据与审计覆盖下，我们对该 tier 判断有多确信”。
- `coverage_audit_state`：只回答“本轮关键证据、归一和审计完成到了什么程度”。

执行约束：

- `decision_tier` 只能由主支柱是否成立、关键独立交叉确认是否成立、以及 `blocking_counter_evidence` 是否命中来改变；不得把一般性的工具缺失、补证超时或 supporting axis 未覆盖直接写成 tier 降级。
- `decision_confidence` 必须吸收非阻断性缺口，包括 partial audit、supporting axis 降级、freshness 变弱、high-impact unresolved group 和补证未完成。
- `coverage_audit_state` 至少应区分 `full`、`partial`、`degraded`、`unavailable`；它反映运行态完整度，不等价于趋势是否存在。
- 下游消费必须额外读取 `consumer_readiness_state` 与 `consumer_display_priority`；`decision_tier` 不是 headline 排序与公开呈现的唯一依据。
- `missing_axes` 只聚合 `axis_applicability_state="required"` 的缺失；`supporting_optional` 和 `not_material_for_archetype` 的负状态只能影响 `decision_confidence`、`coverage_audit_state` 或 explanatory notes，不得制造伪主债务。
- 除非本文特别说明，下文中的 `claim_archetype` 均指 `adjudicated_claim_archetype`。

### 裁决质量契约

趋势裁决的首要目标不是最大化规则数量、消息完备度或审计材料体积，而是稳定地产出“分得对、讲得清、不过度升级、对用户有决策价值”的判断。设计评审、规则修改和后续实现，必须优先证明裁决质量改善，而不是只证明协议更完整。

`Trend Decision Quality Contract` 冻结如下：

1. `能分对`：系统必须把 `core_industry_trend`、`observing_industry_trend`、`wind_probe`、`project_heat_cluster`、`insufficient_evidence` 清楚区分，不能长期依赖人工语感补 tier。
2. `能解释`：每条裁决都必须回答“为什么是这个 tier、为什么不是上一级、为什么不是下一级、主支柱是什么、独立交叉确认是什么、哪些缺口只该降置信不该降 tier”。
3. `能稳定`：非关键 supporting evidence 的增减、补证顺序变化、或不改变主支柱/关键交叉确认的局部修订，不应引发大幅 tier 抖动。
4. `能校准`：`decision_confidence` 必须和实际正确率有可验证对应关系；高置信不能只是更强语气。
5. `能服务决策`：输出必须能支持“本周该关注什么、补什么、忽略什么”的用户决策，而不是只给出漂亮标签。

执行约束：

- 任何裁决 profile、反证 profile、独立性 profile、freshness profile 或 authority profile 的变更，都必须通过专门的裁决质量评测与差异审计证明“判断变好了”，而不只是“规则更细了”。
- 任何实现不得以 message/envelope、artifact manifest、schema registry 或 tracing 完整度替代裁决质量验证；这些治理对象只能证明“可追溯”，不能证明“分得好”。
- 若某条规则提高了协议完备度，却显著降低了 tier discrimination、稳定性、置信校准或 anti-overpromotion 表现，则该规则变更不得视为正向完成。

### 裁决准入与争议边界

多 Agent 架构下，真正稀缺的不是 claim 数量，而是 `full` 审计、same-run 高优先级补证和人工 adjudication 容量。设计必须避免“任何看起来像方向的候选都进入重审计队列”，否则系统会在争议风暴和长尾候选中失去吞吐稳定性。

执行约束：

- 只有在 `claim-builder pass` 已完成 overlap fold、主支柱假设明确、且至少存在一条 `is_tier_material=true` 的主支柱或关键独立交叉确认路径时，候选才允许申请 `audit_priority=high/critical`、same-run 补证或 same-run adjudication。
- 在进入高优先级审计前，claim-builder 必须先做 `claim family fold`：同一运行窗口内，共享主支柱、关键事实组、archetype 或同一语义簇的相邻候选，必须先归并为一个 `primary claim candidate`，其余候选只能作为 folded alternatives、watchlist 或缺口上下文保留，不得并发抢占同一高优先级队列。
- 仅靠 `attention_signal` / `narrative_signal`、尚未形成稳定主支柱、或 material links 仍大面积缺失的候选，不得默认占用 `full` 审计与人工优先级；它们应先留在 `observing_industry_trend`、`wind_probe` 或 `insufficient_evidence`，并显式暴露缺口。
- `audit-agent`、`registry-agent` 和人工复核队列的高优先级产能，必须优先服务可能改变 `core_industry_trend`、`headline core`、`public_output_blocking` 或 `tier_blocking` 结论的候选；不得让长尾边界 claim 与 headline claim 无差别抢占同一关键队列。
- `headline core` 候选必须受容量预算约束。超过预算的候选不得继续争抢 same-run `critical/high` 审计或人工 adjudication；它们应转入 `secondary_candidate`、`watchlist_only`、`internal_only` 或 `needs_review` 分桶，等待后续窗口或异步治理。
- 当高优先级裁决容量不足时，系统默认动作是限制消费范围，而不是修改事实判断：应通过 `decision_confidence`、`coverage_audit_state`、`consumer_readiness_state` 和 `consumer_display_priority` 显式暴露，而不是把所有边界候选一律静默压回低 tier，或让 weekly 无限等待。

### 核心行业趋势

必须同时满足：

1. `Agent relevance gate` 为 `agent_core`，或为 `agent_adjacent` 且存在明确 Agent 使用场景绑定证据。
2. 必须存在与 `claim_archetype` 对应的主支柱证据结构；主支柱必须来自 `technical_support`、`landing_support`、`builder_support`、`adoption_support` 中与该 archetype 匹配的角色，而不是为了凑轴数临时补低价值 supporting evidence。
3. 必须至少存在 `1` 个与主支柱不同的独立交叉确认事实单位；该交叉确认必须满足 `fact_independence_credit=1.00`，除非对应 archetype 的结构规则另有更严格要求。
4. 至少 `1` 个推动升级的主证或关键交叉确认来自 `core` 或 `proven` 来源。
5. 不存在 `blocking_counter_evidence`。
6. 若 `leading_axes` 只包含 `attention_signal` / `narrative_signal` 对应轴，则不得进入 `core_industry_trend`；若主支柱角色仅靠 `coverage_state=degraded` 或 `stale_but_usable` 维持，默认先降低 `decision_confidence`，只有在缺少可替代主支柱时才阻断 `core_industry_trend`。
7. 必须满足对应 `claim_archetype` 的额外要求；archetype 表定义的是进入 `core` 的结构门槛，不得再被一个统一的“至少 3 轴 + 2 role”总门槛覆盖：

| `claim_archetype` | 额外 core 要求 |
| --- | --- |
| `research_frontier` | `research_paper` 或 `conference_academic` 至少 `1` 个 axis=`strong` 作为主支柱；且存在 `project_open_source`、`developer_studio`、`product_vendor_release`、`community_discussion` 中至少 `1` 个 axis=`medium` 作为独立交叉确认。单篇未复核预印本不得单独进入 core。 |
| `product_adoption` | `product_vendor_release` 至少 `1` 个 axis=`medium` 作为主支柱；且 `project_open_source`、`developer_studio`、`community_discussion` 中至少 `1` 个 axis=`medium` 作为独立交叉确认。仅 PR / 媒体转述 / vendor 营销不得进入 core。 |
| `builder_ecosystem` | `developer_studio` 或 `project_open_source` 至少 `1` 个 axis=`strong` 作为主支柱；`community_discussion` 至少 `1` 个 axis=`medium` 作为独立交叉确认；且至少存在 `2` 个独立主体或 `3` 个独立项目/包/maintainer 信号。 |
| `capital_policy_attention` | `capital_finance`、`policy_regulatory`、`policy_research_thinktank`、`news_pr_narrative` 可以参与 supporting，但若要进入 core，仍必须额外存在 `research_paper`、`conference_academic`、`product_vendor_release`、`developer_studio`、`community_discussion`、`project_open_source` 中至少 `2` 个 axis=`medium`，且其中至少 `1` 个必须能承担主支柱、至少 `1` 个必须能承担独立交叉确认。 |
| `project_heat_cluster` | 不得进入 `core_industry_trend`。 |

### 观察中行业趋势

满足任一条件：

1. 至少 `2` 个证据轴按 `axis-status-threshold-profile.v1` 判为 `strong` 或 `medium`，且不存在强反证。
2. 已形成主支柱角色，但跨角色交叉确认仍不足 `core_industry_trend` 门槛。
3. 一个 `core / proven` 高权威信号叠加持续社区讨论，其中 `continuity_score >= 50`。
4. `claim_archetype` 为 `capital_policy_attention`，且至少存在 `1` 个 attention / narrative 轴达到 `medium`，同时存在 `1` 个 technical / landing / builder / adoption 轴达到 `early_signal_min`。

观察中趋势不得使用“已经形成”“行业正在全面转向”等确定语气。

补充冻结：

- 当主张的大部分 supporting evidence 仍停留在 `merged_provisional` 或 `singleton_unresolved`，但来源权威、新鲜度和连续性已经足以说明“方向存在”，系统应优先保留该 claim，并将其裁决为 `observing_industry_trend`、`wind_probe` 或 `insufficient_evidence`，而不是在 claim 层面直接丢弃。
- 未完全归一的事实可以推动“保留与降级”，不能默认推动“删除与消失”。
- `observing_industry_trend` 的多轴门槛不绕过事实独立性：若推动升级的多个 axis 全部落在同一 `fact_id`、同一 `cross_axis_projection_groups` 或同一 `source_chain_dedupe_groups`，且没有独立 follow-on fact、独立主体确认或跨时间连续性支撑，则它们只能证明“单事实可见度增强”，最高只能进入 `wind_probe` 或 `insufficient_evidence`。

### 风向探针

必须满足：

1. `capital_finance`、`policy_regulatory`、`policy_research_thinktank`、`news_pr_narrative` 中至少 `1` 个高优先级探针轴达到各自 `early_signal_min`，并作为 probe lead 写入裁决理由。
2. 上述高优先级探针轴之外，至少还有 `1` 个证据轴达到各自 `early_signal_min`；该辅助轴可以来自 `capital_finance`、`policy_regulatory`、`policy_research_thinktank`、`research_paper`、`product_vendor_release`、`news_pr_narrative`。
3. 至少 `1` 个信号来自 `core / proven` 来源。
4. 产品、社区、开源或落地证据不足以进入核心趋势。
5. 若 `claim_archetype="capital_policy_attention"`，允许由 `1` 个 strong 或 `2` 个 medium` 的 attention / narrative 轴触发，但必须至少有 `1` 个技术、产品、builder 或 community 侧信号达到 `early_signal_min`，否则只能进入 `insufficient_evidence`。

风向探针必须写成“可能方向 / 前置信号 / 值得观察”，不得写成成熟趋势。
当资本、政策、智库或新闻轴主导形成 probe 时，它们在“发现方向、触发补证、提升选题优先级”上属于主证据，而不是边角辅助证据。
用于满足 probe 的“第二个轴”不得只是 probe lead 的同一传播链回声；若它与 probe lead 共享同一 `fact_id`、同一 `source_chain_dedupe_groups` 或只是媒体/社区对同一公告的转述，默认只能增强可见度，不能单独补足 probe 所需的辅助确认。

### 项目热度簇

满足：

1. `project_open_source.axis_score >= project_open_source.project_heat_min`。
2. 至少存在 `3` 个独立 repo / package / benchmark 记录，或 `2` 个独立 repo / package 加 `1` 个 downstream adoption 信号。
3. 这些项目不得全部来自同一 org、同一 maintainer、同一模板 fork 链或同一宣传传播链。
4. star / fork / 热榜只能作为热度辅助，不能单独构成“独立项目单位”。
5. 其他行业轴不足 `2` 个达到各自 `early_signal_min`。

项目热度簇只能进入项目分区或补证触发器，不得进入行业主叙事。

### 证据不足方向

出现任一情况：

1. 只有单一来源或单一主体。
2. `agent_relevance_score` 低于对应 `agent-relevance-profile.v1.auxiliary_min`。
3. 核心证据来自 `watch / ordinary / excluded` 且无可追溯一手来源。
4. 工具失败导致关键轴不可用，且无法通过备用链路补证。
5. 证据冲突未解决。

证据不足方向必须保留缺口说明和下一步观察建议。

## 正常裁决与异常降级

当前设计默认以“正常模式”裁决。只有工具失败、授权缺失、速率限制、上游 Agent `partial/failed/unavailable` 或最近窗口只能复用已审计快照时，才允许进入“异常降级模式”。

冻结规则如下：

1. 正常模式下，目标是让关键 leading/supporting 证据达到 `coverage_audit_state=full`；`degraded` 是异常保护，不是常态运行策略。
2. 每个 `coverage_state=degraded` 的轴都必须写 `degradation_reason_codes`，并能追溯到 `tool_status_report`、`failure_notice` 或上游 contribution。
3. 每个轴都必须同时输出 `freshness_state`：`fresh` 为目标常态，`stale_but_usable` 只用于最近可信快照或已复核存量证据，`stale` 表示该证据不能再独立承担核心升级主证据。
4. 若主支柱角色对应的 `leading axis` 处于 `coverage_state=degraded`、`freshness_state=stale_but_usable`，或关键审计只达到 partial，默认先降低 `decision_confidence`、把 `coverage_audit_state` 记为 `partial/degraded`，并把缺口写入 `not_complete_unless`；不得仅因流程完整度不足就自动降 tier。
5. 只有当主支柱本身失效、缺失关键 `leading axis`、最后一个可用独立交叉确认失效、或主支柱只剩 `stale` 证据支撑时，才允许直接下调 `decision_tier`。
6. 若只有 supporting axis 降级、supporting axis 为 `stale_but_usable`、或部分补证未完成，trend-agent 可以保留原 tier 候选，但必须显式下调 `decision_confidence`，且禁止 `decision_confidence=high`。
7. 连续运行反复出现同一 `degradation_reason_code` 时，不再视为“意外情况”，而是 pipeline 能力缺陷，必须进入 registry / tool coverage 治理。

## 证据归一与合并

当前设计的合并规则冻结如下：

1. 实体对齐优先使用 registry `entity_id`，其次使用 normalized URL / DOI / repo URL / official domain。
2. 同一主体多渠道发布只能算一个主体信号，但可以增强 `continuity_score`。
3. 同一新闻转载链只算一个来源链，不得重复提高 `independence_score`。
4. 同一公司通稿被多家媒体转述，不构成跨来源独立证据。
5. 同一作者在 X、Substack、GitHub discussion 多处复述同一观点，只能算一个 actor signal。
6. 高权威反证优先级高于低权威正证。
7. 若多个 Agent 对同一证据给出冲突解释，`audit-agent` 的 `blocking/strong` 降级结论优先于 `trend-agent` 的升级结论；`medium/weak` 冲突允许在显式解释后保留 tier，但必须降置信。
8. 合并后的每条趋势必须保留原始 `event_id`、来源类别、参与 Agent 和工具 route。
9. 脏数据不是合并阶段 rejected 的默认理由；只要来源可追溯、axis 可归属、时间可落点且 topic/target 至少有一个可解释锚点，就应进入事实归一与限权链路。

`IndustryMergeAudit` 至少包含：

```ts
interface IndustryMergeAudit {

  fact_groups: string[][];

    group_id: string;

    resolved_by_agent_id: "normalization-agent";
    needs_manual_review: boolean;

    event_ids: string[];

```

`IndustryMergeAudit` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `merged_event_groups` | string[][] | 被归并为同一事实/主体/来源链的事件组。 | 每组至少 2 个 event；不得把未合并事件塞入空组。 |
| `fact_groups` | string[][] | 共享同一 `fact_id` 的事实组。 | 同一底层事实被拆成多个 axis event 时必须记录在同一 fact group；缺失事实组时不得把这些 event 当成天然独立确认。 |
| `cross_axis_projection_groups` | string[][] | 同一底层事实在多个 axis 上的投影组。 | 这些组中的 event 可以分别参与各轴评分，但不能同时充当“主支柱 + 独立交叉确认”的两个独立事实来源。 |
| `source_chain_dedupe_groups` | string[][] | 同一转载链、同一公告传播链或媒体转述链。 | 这些组只能算一个独立来源，不能重复提高 independence。 |
| `repeated_actor_groups` | string[][] | 同一 actor 多渠道复述的事件组。 | 只能算一个 actor signal，可增强 continuity 但不能增强 independence。 |
| `merge_resolution_notes` | object[] | 归并时的 canonical winner 与依据。 | 每个 merged group 都必须能映射到一个 canonical event 和明确 merge basis；低置信归并必须显式标记。 |
| `rejected_event_ids` | string[] | 合并阶段拒绝的事件。 | 每个 rejected event 必须在 `rejected_reasons` 中有稳定 reason code。 |
| `rejected_reasons` | Record<string,string> | rejected event 的原因。 | key 必须是 event_id，value 必须可被测试断言，不能只写长段说明。 |
| `unresolved_conflicts` | object[] | 归一后仍无法解决的冲突。 | 每个冲突必须写 `required_next_action`；未解决强冲突必须影响趋势等级。 |

`CounterEvidenceAudit` 是需求 9 的硬契约，负责证明每条趋势不是只保留正向叙事。

`CounterEvidenceAudit` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `audited_by_agent_id` | literal `"audit-agent"` | 执行反证审计的 Agent。 | 必须固定为 audit-agent；trend-agent 不能自审。 |
| `audited_at` | ISO datetime | 审计时间。 | 必须晚于或等于被审计 supporting events 的 ingestion。 |
| `audit_mode` | `light` / `standard` / `full` | 本次审计覆盖深度。 | `core_industry_trend` 候选必须为 `full`；`observing_industry_trend` 至少为 `standard`；`wind_probe` 与 `project_heat_cluster` 可用 `light`。 |
| `audit_priority` | `critical` / `high` / `normal` | 本次审计的优先级。 | 进入 tier decision 前必须已确定优先级；高优先级 claim 不得长期排队而无结果。 |
| `blocking_counter_evidence` | boolean | 是否存在阻断核心趋势的反证。 | true 时 `decision_tier` 不得为 `core_industry_trend`。 |
| `counter_evidence_severity` | `CounterEvidenceSeverity` | 整体反证严重度。 | 必须等于 conflict_groups 中最高有效 severity，或在 reason 中解释差异。 |
| `blocking_scopes` | enum[] | 本次审计影响的是哪一类输出域。 | `audit-agent` 只能填写 `tier_blocking`、`public_output_blocking`、`followup_required`；不得越权表达 authority promotion 结论。 |
| `supporting_event_ids_reviewed` | string[] | 审计过的正证事件。 | 不能只审反证；核心 supporting events 必须全部覆盖。 |
| `reviewed_claim_evidence_link_ids` | string[] | 审计过的 claim 级证据关系。 | 审计必须基于 `IndustryClaimEvidenceLink` 的 role 与 dependency，而不是只看 `source_polarity_cue`。 |
| `unchecked_supporting_event_ids` | string[] | 尚未被本轮审计覆盖的 supporting events。 | 非空时必须与 `audit_mode`、`sampling_reason_codes` 和最终 `decision_confidence` 对齐；`full` 审计默认应为空。 |
| `sampling_reason_codes` | string[] | 非全量审计时的覆盖限制原因。 | `audit_mode!="full"` 时必须填写；必须是可测试 reason code，不能写散文。 |
| `counter_event_ids` | string[] | 反证事件。 | 必须出现在对应 axis summary 的 `counter_event_ids` 或 rejected/counter audit 中。 |
| `missing_axis_keys` | `IndustryEvidenceAxisKey[]` | 审计发现的关键缺失轴。 | 回写到 decision/card 的 `missing_axes` 时，只能进入 `axis_applicability_state="required"` 的主缺口；其他缺失应保留在矩阵或 explanatory notes 中。 |
| `source_bias_notes` | object[] | 来源偏置说明。 | 只记录偏置，不等同于反证；但可触发降级 reason。 |
| `conflict_groups` | object[] | 事实、解释或来源冲突组。 | 每组必须有 `conflict_type`、`severity` 和 `required_next_action`。 |
| `downgrade_recommendation` | object optional | 审计建议降级结果。 | 存在 strong/blocking 或关键缺口时应填写；trend-agent 不得忽略。 |
| `decision_state` | `clear` / `contested` / `escalated` | 当前 claim 在审计层的裁决状态。 | 默认应为 `clear`；存在结构化异议时必须转为 `contested`；跨轮未解或高影响争议必须升级为 `escalated`。 |
| `contested_by_agent_ids` | `IndustryAgentId[]` | 对当前审计结论提出异议的 Agent。 | `decision_state=contested/escalated` 时不能为空；不得用自由文本代替 Agent ID。 |
| `escalation_reason_codes` | string[] | 进入争议或升级态的原因。 | `decision_state=contested/escalated` 时必填；必须是稳定 reason code。 |
| `adjudication_note_cn` | string optional | 争议裁决说明。 | 只能解释结构化争议状态和现阶段结论，不得替代 reason codes。 |
| `unresolved_questions` | string[] | 尚未解决的问题。 | 非空时 `decision_confidence` 最高只能为 `medium`，除非 decision reason 明确解释。 |

反证 severity 不得全类型统一。`counter-evidence-severity-profile.v1` 冻结如下：

| conflict_type | 默认最高影响轴 | default_severity | 升级为 `blocking` 的条件 |
| --- | --- | --- | --- |
| `replication_failure` | `research_paper`、`conference_academic`、`project_open_source` | `strong` | claim 的技术成立主要依赖该论文、benchmark 或复现结果，且无独立替代证据。 |
| `maintenance_decline` | `project_open_source`、`developer_studio` | `medium` | claim 主要依赖单一 repo / maintainer，且项目停止维护、归档或核心能力撤回。 |
| `regulatory_negative` | `policy_regulatory`、`capital_finance`、`product_vendor_release` | `strong` | 监管否定、禁令、处罚、审批失败或公共采购撤回直接否定 claim 的落地假设。 |
| `funding_unverified` | `capital_finance`、`news_pr_narrative` | `medium` | 资本信号是 wind probe 或观察趋势的主证据，且融资 / 并购无法被一手来源核验。 |
| `vendor_claim_retracted` | `product_vendor_release`、`news_pr_narrative`、`developer_studio` | `strong` | 官方撤回、文档删除、能力下线或客户案例被否认，且 claim 依赖该产品落地证据。 |
| `source_disagreement` | 所有关联轴 | `medium` | 两个以上 `core / proven` 一手来源对同一事实冲突，且 audit-agent 无法解决。 |
| `agent_interpretation_conflict` | 所有关联轴 | `weak` | 多个专责 Agent 对同一证据解释冲突；若影响趋势等级裁决且无法归一，升级为 `medium`。 |

`counter_evidence_severity` 必须结合 `conflict_type`、受影响 evidence axis、`IndustryClaimEvidenceLink.role` / `dependency_strength`、以及是否存在独立替代证据计算；不得把所有反证统一按来源数量或文本情绪处理。

`counter-evidence-severity-profile.v1` 字段定义冻结如下：

| 字段 | 类型 / 取值 | 含义 | 执行约束 |
| --- | --- | --- | --- |
| `conflict_type` | `CounterEvidenceAudit.conflict_groups[].conflict_type` | 反证或冲突的类型。 | 必须使用 schema 中枚举值，不得用自由文本类型绕过 profile。 |
| `默认最高影响轴` | `IndustryEvidenceAxisKey[]` 或 `all` | 该反证类型默认最直接影响的证据轴。 | 如果实际受影响轴不在默认列表中，必须在 `required_next_action` 或 reason code 中解释原因。 |
| `default_severity` | `blocking` / `strong` / `medium` / `weak` / `none` | 该反证类型在常规情况下的初始 severity。 | 它不是最终 severity；最终 severity 必须结合 claim 依赖路径、来源权威和替代证据后确定。 |
| `升级为 blocking 的条件` | 文本条件 | 从默认 severity 升级为阻断级反证的条件。 | 条件命中时必须设置 `blocking_counter_evidence=true`，并把趋势阻断在 `core_industry_trend` 之外。 |

反证 severity 计算顺序冻结为：先识别 `conflict_type`，再确定受影响 axis，然后读取 `default_severity`，再根据 claim 是否依赖对应 `IndustryClaimEvidenceLink`、是否存在独立替代证据、反证来源是否为 `core / proven` 决定是否升级或降级。`blocking_counter_evidence` 只能由该流程生成，不得由 `trend-agent` 自行判断。

### 阻断域分离

反证审计、主体 authority 认定和 public 输出安全，必须分域处理，不能再用单一“阻断”语义笼统覆盖：

- `tier_blocking`：只表示该冲突足以改变 `decision_tier`。
- `public_output_blocking`：只表示该结论暂不允许进入 public / weekly 对外表面，但不自动否定内部 claim ledger 的 tier 判断。
- `followup_required`：表示需要后续补证、人工复核或规则治理，但当前不足以改变 tier。

执行约束：

- `audit-agent` 只负责 `tier_blocking`、`public_output_blocking` 和 `followup_required`；不得越权给出 authority 晋升或降级结论。
- 主体 authority 的 `core/proven/provisional_authority` 晋升、冻结或阻断，必须由 registry review 域单独表达，不能混进反证 severity。
- `contested` / `escalated` 只在其命中 `tier_blocking` 时改变 tier；否则默认只降低 `decision_confidence`，或阻断 public output。

反证审计冻结规则：

- `audit-agent` 必须独立输出 `CounterEvidenceAudit`；`trend-agent` 不得自审后直接升级趋势。
- 专责搜寻 Agent、normalization-agent 和 claim-builder pass 可以先产出反证候选或冲突分组，但最终 severity 只由 `audit-agent` 确认。
- `audit-agent` 必须先给每个候选 claim 设定 `audit_mode` 与 `audit_priority`，再执行审计；审计深度不得在结果阶段隐式变化。
- `material` 不是自由文本判断，必须使用 [03-数据模型契约.md](/home/adduser/AgentProjection/agentRadar/docs/specs/design-docs/行业级Agent趋势判断设计/03-数据模型契约.md) 中的 `IndustryClaimEvidenceLink.materiality_class` 与 `is_tier_material` 落账：`main_pillar`、`independent_confirmation`、`blocking_path`、`archetype_defining` 属于 tier material，`supplemental` 只影响置信度、解释与补证优先级。
- 对 `core_industry_trend` 候选，`full` 审计的可执行边界固定为：
  1. 所有 `is_tier_material=true` 的 claim-evidence links 已被审计；
  2. 所有 `leading_axes` 已有对应审计结论；
  3. 所有 `key_independent_confirmation_link_ids` 已确认独立性；
  4. 所有来自 `core / proven` 来源且可能改变 blocking 结论的 counter path 已被审计。
- 若未审计缺口只落在 `supplemental` links 或 `impact_scope=confidence_only` 的未决组，默认只降低 `decision_confidence` 并把 `coverage_audit_state` 记为 `partial/degraded`；不得直接改 tier。
- 若未审计缺口覆盖主支柱、关键独立交叉确认、`blocking_path` 或 `impact_scope=tier_blocking` 的未决组，最高才降为 `observing_industry_trend`；若连主支柱级审计都缺失，则最高只能为 `insufficient_evidence`。
- `observing_industry_trend` 候选至少走 `standard` 审计，必须覆盖 leading axes、所有 `core / proven` 主证和主要 claim links。
- `wind_probe`、`project_heat_cluster` 和明显低风险候选可走 `light` 审计，但仍必须检查高权威反证、source-chain 去重和“attention/narrative 是否误升成熟趋势”。
- 若 `unchecked_supporting_event_ids` 非空，必须显式写入 `sampling_reason_codes`；此时除非只是 `wind_probe` / `project_heat_cluster`，否则 `decision_confidence` 不得为 `high`。
- 若 `blocking_counter_evidence=true`，趋势不得进入 `core_industry_trend`。
- 若存在 `conflict_groups.severity="strong"` 且未解决，趋势最高只能进入 `observing_industry_trend`。
- 若只存在 `medium/weak` 反证，trend-agent 可以保留 tier 候选，但必须在 `decision_reason_cn` 中解释 surviving main pillar、替代证据或剩余缺口；此时 `decision_confidence` 最高只能为 `medium`。
- 若反证来自 `core / proven` 来源，必须优先于 `watch / ordinary` 正证。
- 没有反证也必须输出空审计结构，不能省略 `counter_evidence_audit`。
- `contested` 不是通用异议收纳箱。其他 Agent 只有在异议命中 `main_pillar`、`independent_confirmation`、`blocking_path`、`archetype_defining` 或会改变 `blocking_scopes` 时，才允许把 claim 升为 `decision_state=contested`；其余分歧默认进入 `followup_required`、coverage note 或后续 profile 治理。
- 结构化异议必须绑定明确的 `claim_evidence_link_ids`、`conflict_group_id`、`high_impact_unresolved_group_ids` 或新的 artifact refs；不得仅凭自由文本意见触发 `contested`。
- 同一 Agent 对同一 claim 在同一 `run_id` 内最多保留一个活动中的结构化异议记录；补充材料应 supersede 旧记录，而不是并发堆叠多个 contested 分支。
- 若其他 Agent 对审计结论提出满足上述 `contested` 准入条件的结构化异议，`decision_state` 必须转为 `contested`；只有当 `blocking_scopes` 包含 `tier_blocking` 时，争议才阻断 `core_industry_trend`，否则默认只降低 `decision_confidence`，且 `decision_confidence` 最高只能为 `medium`。
- 同一 claim 连续两个运行窗口仍处于 `contested`，或争议已影响关键升级/阻断结论时，必须升级为 `decision_state="escalated"`，并要求人工 review、规则修订或专项 adjudication。
- `agent_interpretation_conflict` 不得只停留在文本备注；若导致 `decision_state=contested/escalated`，必须产出稳定 `escalation_reason_codes`，并在后续 fixture / profile 治理中留痕。
- 若 `decision_state="escalated"` 且未完成人工复核，只有当 `blocking_scopes` 包含 `tier_blocking` 时才必须降级或 rerun；若只包含 `public_output_blocking`，则内部 ledger 可保留当前 tier，但 weekly/public output 不得直接沿用原始结论。
- 若 `decision_state="escalated"` 且争议尚未关闭，该 claim 不得在后续窗口中充当其他 claim 的独立交叉确认、主支柱替代证据或升级先例；它最多只能作为历史上下文、follow-up backlog 或 public hold reason 复用，直到争议被显式裁清。

### 交叉确认与事实独立性

为避免同一底层事实被拆成多个 axis event 后误算成“多角色共振”，当前设计对交叉确认补充冻结如下：

1. 同一 `fact_id` 下的多个 event 可以分别参与各自 axis 的评分与摘要。
2. 但在趋势等级裁决中，同一 `fact_id` 的事件不得同时充当“主支柱 + 独立交叉确认”的两个独立事实来源。
3. 只有当交叉确认来自不同 `fact_id`，且未落入同一 `source_chain_dedupe_groups`、`repeated_actor_groups` 或 `cross_axis_projection_groups` 时，才能算真正的独立交叉确认。
4. 若同一公司发布会、官方 release、政策公告或论文被拆成多个 axis event，这些 event 可以增强对应轴的 `continuity` 或 `coverage`，但不能直接提高跨角色独立性。
5. `trend-agent` 与 `audit-agent` 必须基于 `fact_groups` 和 `cross_axis_projection_groups` 共同判断交叉确认是否独立，不能只按 axis 数量判断。
6. `source independence` 与 `fact independence` 必须分开处理：多个独立来源可以证明“同一事实真实发生”，但不能自动证明“存在多个独立底层事实共振”。
7. `merged_provisional` 的事件或事实组可以参与 axis 评分、候选生成、观察态和反证审计，但不得独自补足 `core_industry_trend` 所需的唯一独立交叉确认缺口。
8. `singleton_unresolved` 事件可以增强方向可见性、连续性或补证优先级，但不得单独把 claim 从 `observing_industry_trend` 推进到 `core_industry_trend`。
9. `conflicted` 事实组不得作为正向独立交叉确认使用。
10. 同一事实被多个独立来源确认时，可提升 axis 内的可信度，但其 `fact independence` 仍视为单一事实单位，不得按材料条数累加。

#### `independence-credit-profile.v1`

交叉确认不得按“原始 event 数量”或“轴数量”累加，必须按下表聚合 `source_independence_credit` 与 `fact_independence_credit`：

| 关系情形 | `source_independence_credit` | `fact_independence_credit` | 使用说明 |
| --- | ---: | ---: | --- |
| 同一转载链 / 同一公告传播链 | `0.00` | `0.00` | 只能算一条来源链，不得重复记分 |
| 同一 actor 多渠道复述 | `0.00` | `0.00` | 只能增强 continuity，不得增强独立性 |
| 同一 `fact_id` 的跨轴投影 | `0.25` | `0.00` | 可增强对应轴可信度，但不是独立事实 |
| 同一事实的独立来源确认 | `0.50` | `0.00` | 可证明事实可信，但仍是同一事实 |
| `merged_provisional` 的相关但未定 distinct fact | `0.50` | `0.50` | 可弱参与交叉确认，但不能单独补足 `core` 缺口 |
| 不同 `fact_id` 且不同来源链的确认事实 | `1.00` | `1.00` | 完整独立事实单位 |
| `conflicted` 或方向相反的事实 | `0.00` | `0.00` | 进入 counter/context 与审计 |

执行约束：

- `independence_score` 不得按原始 event 数量累加，只能按 credit 聚合。
- `core_industry_trend` 所需的交叉确认，必须至少包含一个 `fact_independence_credit=1.00` 的事实单位。
- 若全部交叉确认都停留在 `fact_independence_credit<1.00`，最高只能进入 `observing_industry_trend`、`wind_probe` 或 `insufficient_evidence`。
- 若某条轴主要依赖 `merged_provisional` / `singleton_unresolved` 事件，`summary_cn` 必须显式写明“证据可见但事实归一仍不完全”。

#### 高影响未决组与人工复核

不是所有 unresolved / provisional group 都应直接推向人工。系统必须先基于 `FactResolutionAudit.high_impact_unresolved_groups.impact_scope` 与 `auto_resolution_allowed` 分流：

- `impact_scope=confidence_only`：默认自动执行 `keep_tier_lower_confidence`，保留 tier、降低 `decision_confidence` 或标记 `coverage_audit_state=partial`。
- `impact_scope=public_output_only`：默认自动执行 `keep_tier_hold_public_output`，内部 ledger 可保留 tier，但 weekly / public projection 必须限权。
- `impact_scope=authority_only`：默认自动执行 `authority_hold`，冻结 authority 晋升，不自动否定 claim 本身。

只有以下情况才必须进入人工复核或 same-run 高优先级专项 adjudication：

1. 同一个 unresolved / provisional group 的不同解释会改变 `decision_tier`，且 `auto_resolution_allowed=false`。
2. `blocking_counter_evidence` 与正证只在事实归并结论上分歧，且该分歧命中主支柱、关键独立交叉确认或 `blocking_path`。
3. 一个 `core` 候选缺的最后一个交叉确认，只来自 `merged_provisional`，且不存在已审计替代事实。
4. 高权威政策、资本、产品或学术事实的归并不确定性会改变 `leading_axes` 或 `adjudicated_claim_archetype`。
5. 同一事实既可能被判为 `follow_on_confirmation`，也可能被判为新的 `distinct_but_related` 事实，且两种解释会改变主支柱或独立交叉确认结构。

执行约束：

- 对自动裁决边界内的 unresolved groups，系统必须显式写出 `default_system_action`，不得口头说“待人工再看”却不落账当前默认处理。
- same-run 人工复核或专项 adjudication 只能保留给 `impact_scope=tier_blocking` 且当前确实参与 `headline core`、关键 public output 或核心升级竞争的 claim；其余事项默认跨 run 进入 backlog、follow-up 或降级投影，不得要求所有高价值争议都同步人工裁清。
- 若 same-run 人工容量耗尽，默认动作必须是保留内部 ledger、下调 `decision_confidence` / `consumer_readiness_state`、限制 public output，并把缺口显式挂账；不得为了追求“当场裁清”阻断整次 weekly。
- 人工复核是例外治理，不是所有跨职责高价值事实的常态出口；若某类 `confidence_only` 事项持续高频入队，说明应修 profile、materiality 规则或 attestation 归并规则，而不是继续堆人工。
