## Eval 术语解释

其余治理与验收名词统一以 [术语与审计词汇表](09-术语与审计词汇表.md) 为准；这里仅解释本章直接用来验收的评测词。


- `gold set`：人工冻结的正向基准样本，定义“系统应该识别出来的趋势、等级和证据结构”。它不是训练数据，而是验收基线。
- `negative fixtures`：人工冻结的反例样本，定义“系统不应升级的噪声、宣传、泛 AI 热点、单轴热度或低相关自动化内容”。
- `replay windows`：选定的一组历史时间窗口，用来重跑当时的 daily / weekly 输入并比较当前输出是否漂移。
- `replay result`：对某个 replay window 执行重放后的结果摘要，至少要能说明是否重建成功、和历史 baseline 的差异、误报/漏报、citation 准确性以及轴覆盖是否下降。
- `TrendDecisionEvalCase`：单条或成组冻结的裁决评测对象，不只断言最终 `decision_tier`，还断言主支柱、交叉确认、反证、缺口、置信度和“不应被误判成什么”。
- `DecisionDiffAudit`：任一裁决 profile、反证规则、独立性规则、freshness/authority 规则修改后的差异审计对象，用来说明哪些 claim 的 `decision_tier`、`decision_confidence`、`coverage_audit_state` 发生变化，哪些变化是预期修复，哪些是回归。

这些术语都是治理和验收对象，不是“最好有”的分析材料；没有它们，设计不能证明自己在历史窗口下稳定成立。

## 裁决质量验证对象

真正验证“趋势裁决是否好用”，不能只靠 schema 完整性和单条命中样本；必须把裁决质量本身做成可冻结、可 replay、可比较的评测对象。

`TrendDecisionEvalCase` 最小结构要求：

- `case_id`
- `case_family`
- `input_claim_or_events_ref`
- `expected_decision_tier`
- `expected_decision_confidence_range`
- `expected_main_pillar_axes`
- `expected_independent_confirmation_axes`
- `expected_missing_axes`
- `expected_counter_outcome`
- `must_not_be`
- `explanation_assertions`

`case_family` 至少冻结以下五类：

- `positive_canonical_case`：典型应进入 `core`、`observing`、`wind_probe` 的标准正样本。
- `near_boundary_case`：接近升级/降级边界，用来检验规则是否稳定、是否过拟合门槛。
- `anti_upgrade_case`：资本/政策/宣传/单轴热度很强，但不应误升为成熟趋势的样本。
- `coverage_vs_tier_case`：证据语义成立，但 coverage/audit 不完整，用来断言“该降 confidence，不该乱降 tier”。
- `counter_override_case`：正证很强，但反证足以阻断或下调 tier 的样本。

`DecisionDiffAudit` 最小结构要求：

- `audit_id`
- `profile_change_set`
- `compared_run_ids`
- `tier_changed_claim_ids`
- `confidence_changed_claim_ids`
- `coverage_state_changed_claim_ids`
- `expected_repairs`
- `unexpected_regressions`
- `anti_overpromotion_regressions`
- `stability_regressions`
- `adjudication_summary_cn`

执行约束：

- 任何 profile 变更，不得只跑普通单元测试；必须至少产出一次 `DecisionDiffAudit`。
- 任何 claim 的 tier 变化，都必须在 diff audit 中解释“为什么变了”以及“为什么这是改进而不是漂移”。
- 任何没有 `must_not_be` 断言的评测 case，都不能证明系统具有足够的判别力。

## 裁决质量指标

裁决质量不能只看 overall accuracy 或单一 tier 命中率，至少要同时跟踪以下指标：

- `tier_discrimination_accuracy`：不同 `decision_tier` 之间是否区分正确，尤其是 `core` 与 `observing`、`observing` 与 `wind_probe`。
- `anti_overpromotion_precision`：资本/政策/宣传/单轴热度类样本中，被误升到更高 tier 的比例。
- `confidence_calibration_error`：高/中/低置信区间与实际正确率之间的偏差。
- `tier_stability_under_non_material_changes`：非关键 supporting evidence 变化时，tier 是否异常抖动。
- `downgrade_correctness`：coverage/audit 不完整时，系统是否主要下调 `decision_confidence`，而不是错误下调 `decision_tier`。
- `decision_explanation_completeness`：裁决是否完整解释主支柱、交叉确认、反证、缺口和 surviving reason。

执行约束：

- `tier_discrimination_accuracy` 与 `anti_overpromotion_precision` 属于高优先级指标；不得被 overall accuracy 掩盖。
- 若 `confidence_calibration_error` 持续偏高，则不得继续扩大 `confidence=high` 的使用范围。
- 若 `tier_stability_under_non_material_changes` 下降，说明系统把非关键噪声当成了实质判断依据，必须回退或修正相关规则。
- 若 `downgrade_correctness` 不达标，说明系统仍在混写 tier、confidence 和 coverage 语义，视为设计回归。
- `decision_explanation_completeness` 不得只由自然语言长度衡量，必须能机判地断言“为什么是它、为什么不是相邻 tier”。

`priority_level` 解释：

- `A`：结论语义与用户表面硬契约，缺失时设计不可接受。
- `B`：运行、治理与可追溯硬契约，缺失时设计不可接受。
- `C`：覆盖与完成度硬契约，缺失时不得宣称设计闭环完成。

## 防偷懒约束

实现阶段不得用以下路径宣称完成：

1. 只把 AgentReach 或新闻摘要拼进 weekly prose，而不生成 `IndustrySignalEvent`。
2. 只给趋势卡增加“研究 / 产品 / 资本”标签，而不输出十轴评分和缺失轴。
3. 只跑一个综合搜索 Agent，而不输出 9 个实际 Agent 与 15 个职责项的贡献状态。
4. 只实现项目/开源、学术、社区三轴，省略资本、政策、智库、新闻/宣传。
5. 只在文案中说“证据不足”，但没有 `missing_axes`、`reason_codes` 和工具状态。
6. 用普通搜索结果替代学术源、政策源或金融源，并把它们当作同等权威证据。
7. 把 capital / policy / news 热度直接升级为核心行业趋势。
8. 行业层失败时静默回退为旧 weekly，而不显式标注行业证据不足。
9. 把 `audit-agent` 与 `trend-agent` 合并为同一不可区分输出，或让 Trend Agent 直接补采原始来源来绕过归一化与反证审计。
10. 把 Finance Agent 或 Policy Agent 降级成 Trend Agent 的临时搜索步骤、新闻摘要步骤或普通网页检索步骤。
11. 只实现 Agent 流程，不实现用户工作流、下钻、SLO / 成本预算、eval / replay、人工复核和治理审计。
12. 用日志、trace 或框架 dashboard 替代 `HumanReviewQueueItem`、`OverrideAudit`、eval fixture 和 canonical artifact。
13. 只定义统一 message envelope，不定义 payload schema registry、producer / consumer、required refs 和 missing behavior。
13a. 让多个职责项对同一事实重复产出 accepted event，再在后续阶段靠文案或人工理解去重。
14. 让 `trend-agent` 在反证审计前直接输出最终 `claim_ledger`，或把 audit 做成最终文案后的补充说明。
15. 十轴使用了不同权重，但六个子分仍采用同一套全局 freshness / independence / primary-source 映射，或把预印本、录用、benchmark 更新、代码 / 复现发布重新压回统一天数。
16. 只写有 timeout / budget / capacity 维度，不冻结 `task-timeout-profile.v1`、`axis-runtime-budget-profile.v1`、默认数值或用户可见降级语义。
17. 所有 claim archetype 仍按同一套“至少 3 轴 strong / medium”偷懒裁决，未区分研究前沿、产品落地、builder 生态、资本 / 政策注意力和项目热度簇。
18. 把综合搜索 Agent、研究 Agent 或新闻聚合结果直接当作政策、金融、官方产品发布轴的 primary supporting source，而不回到官方 canonical fetch。
19. 以“设计要求完整 seed registry”为由，默认高频扫描全部 seed，导致预算、超时和人工复核容量失真。
20. 在 `DailyIndustryEvidencePack` 里重新内嵌全量 accepted / rejected 事件，绕过 event batch 与 normalization lineage，把 daily pack 做回胖快照。
21. weekly 只输出 `claim_ledger` 或 prose，不输出 `lineage_refs`、`run_budget_summary`、`industry_window_status` 阈值输入或 `freshness_summary`。
22. 公开产物直接复用 internal artifact 路径或 hash，只是额外打一个 `public` 标记，而没有独立 redacted/public projection。
23. 为了节省存储把 messages/manifest 压缩成无法 replay 的摘要，丢掉 `run_id`、`correlation_id`、artifact refs 或 visibility 元数据。
24. 在不同章节分别维护冲突的 `industry_window_status`、review capacity 或 retention 数值，让实现按章节自行挑选规则。
25. 把没有稳定 canonical `fact_id` 的事件默认 rejected，或把 `merged_provisional` / `singleton_unresolved` 直接当成完整独立事实去补足 `core` 交叉确认。
26. 在交叉确认里按 event 条数、轴数量或“有几个来源提到”直接累加独立性，而不消费 `FactResolutionAudit`、relation edges 和 `independence-credit-profile.v1`。
27. 只保留 `180` 日日级包，却允许一年以上的 supporting / revalidation freshness 窗口，导致 replay 和审计断链。
28. 只验证 schema、artifact、message lineage 完整，而不验证 tier discrimination、anti-overpromotion、stability、confidence calibration 或 explanation completeness。
29. 只看 overall accuracy 或“最终 tier 命中率”，忽略边界样本、相邻 tier 区分能力和 anti-upgrade 表现。
30. 把 coverage/audit 不完整导致的降 `decision_confidence` 偷换成 `decision_tier` 降级，并把这种误降解释为“系统更保守”。
31. 修改裁决 profile 后，只给出“测试通过”或“规则更细”，却不产出 `DecisionDiffAudit` 说明哪些判断真的变好了。

## 设计完成定义

本章只定义目标态设计契约，不再在主设计文档中维护 `shadow_eval`、`pilot`、阶段 gate 或版本化“可用/完成态”宣称。此类发布、灰度、验收和外部说法应移入后续评测/发布治理文档，而不是写回主设计本身。

主设计文档在完成定义上只冻结三条原则：

1. 设计契约必须按高标准一次性完整定义，不能通过删减语义边界、偷换字段含义或引入阶段话术来回避硬问题。
2. 设计目标仍然是完整实现，而不是完整暴露缺失。运行中任何暂未满足的能力，必须以 `missing`、`partial`、`degraded`、`unavailable`、`needs_review` 等可审计状态显式暴露；这只是在运行态诚实暴露缺口，用来防止静默删减、伪装覆盖和错误结论，不构成对目标设计范围的删减，也不能替代“已经完整实现”的完成定义。不得伪装为已覆盖，也不得用“先这样上线”改写目标态。
3. 结论语义、运行治理、覆盖完整度应分别验证：趋势 tier、置信度、覆盖/审计完整度不得混写成单一状态。

补充说明：

- 本设计中的 `v1` 主要用于标记首个冻结的 schema / profile / contract 版本，不表示阶段性交付层级、最小子集或低标准版本。
- 设计标准应一次性按高要求冻结；允许分步推进的只能是实现顺序、产能爬坡和运行覆盖率，不能是把原本应存在的设计语义偷偷降成“后续再定义”。

设计完成的最低判据如下：

- 结论语义层：每条 claim 都能独立输出十轴矩阵、趋势等级、置信度、正证、反证/缺口、Agent contribution、tool route state 和 source trace refs。
- 运行治理层：多 Agent 输入输出、authority 认定、反证审计、补证、public projection、retention / replay 和 failure 语义都能被结构化验证。
- 覆盖完整度层：seed registry、tool coverage、eval / replay、人工复核和长窗口追溯具备闭环，不依赖口头说明补齐。
- 裁决质量层：存在覆盖 canonical / boundary / anti-upgrade / coverage-vs-tier / counter-override 的 `TrendDecisionEvalCase`，并能通过 `DecisionDiffAudit` 证明规则修改改善了判断质量而不是只增加了协议复杂度。

## 开放问题

当前仍有需要在设计层继续冻结、但不改变主原语成立性的开放问题：

1. multilingual canonicalization governance：最小 `TopicEntityCanonicalizationEntry` 契约已经冻结；仍待继续补的是长尾多语言规范词表的维护机制、冲突合并策略和生命周期治理，而不是是否需要这套契约本身。
2. external provider diversification：若未来引入多个外部发现 provider，如何在不破坏现有 ledger / replay 稳定性的前提下，冻结 provider conflict resolution 与 provenance credit。
3. long-window drift explainability：当 180-540 日 replay 中出现 schema 兼容但判断显著漂移时，是否需要独立的 drift taxonomy 来区分“语义升级”“coverage 扩大”“历史数据失真”和“规则回归”。

这些问题不允许由实现阶段临时补设计；但它们不再阻塞当前目标态设计契约的闭环成立。

以下属于后续扩展，不进入当前设计范围：

1. 是否把行业证据轴反馈到项目 `ScoreBreakdown`。
2. 是否为行业趋势建立独立 Web 工作台编辑/审批流。
3. 是否接入付费金融、咨询或行业数据库的自动授权流程。
4. 是否引入长期用户画像来调整行业趋势排序。

## 设计结论

本设计冻结了行业级 Agent 趋势判断的核心产品机制：

- 用 `IndustryClaimLedger` 建立行业主张账本，而不是继续项目聚类。
- 用十轴证据矩阵表达完整行业证据结构。
- 用五种趋势等级保护用户语义。
- 用 9 个实际 Agent 覆盖 15 个职责项，Finance Agent 与 Policy Agent 作为高复杂度独立 Agent，职责项用于 weekly 覆盖审计。
- 用工具四级保障链路处理成本、授权和失败。
- 用 Agent relevance gate 防止漂移为泛 AI 新闻平台。
- 用生产级产品与治理边界补齐用户工作流、SLO / 成本、eval / replay、人工复核、覆盖审计和控制面，避免设计只停留在 Agent 流程层。
- 用明确失败和降级状态保护现有 weekly 主产物。

文档已经把需求中的硬冻结项转成可执行设计契约。通过 design review 后，可以进入 ExecPlan。
