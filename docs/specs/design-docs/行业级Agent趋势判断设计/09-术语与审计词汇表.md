# 行业级 Agent 趋势判断：术语与审计词汇表

> 本文档拆自 [行业级Agent趋势判断设计文档.md](../行业级Agent趋势判断设计文档.md)，是行业级 Agent 趋势判断设计文档包的一部分。

本词汇表用于统一解释设计包中的专用名词。若局部文档有就近解释，而与本文存在冲突，以本文的冻结语义为准；局部文档只能补充上下文，不能改写这里的定义。

## 判断原语

| 术语 | 含义 | 不是什么 |
| --- | --- | --- |
| `industry evidence events` | 行业层最小事实单元，对应可追溯的方向级证据事件。 | 不是搜索结果列表，也不是 LLM 自由文本摘要。 |
| `evidence axes` | 用固定十轴组织 claim 证据结构的判断维度。 | 不是随实现增减的标签桶，也不是简单来源分类。 |
| `industry claim` | 某个方向的候选行业主张。 | 不是最终 weekly 结论。 |
| `industry claim ledger` | 针对单条 claim 的周级裁决总账本，记录证据、审计、等级和贡献。 | 不是 UI 卡片，也不是一段 prose。 |
| `counter-evidence audit` | 对反证、冲突、缺口和来源偏置的独立审计结果。 | 不是文案里的风险提示。 |
| `trend tier decision` | rules-first 的趋势等级裁决结果。 | 不是黑盒总分映射。 |
| `weekly industry narrative` | 从 ledger 派生出来的 weekly 可读消费面。 | 不是新的推理层，也不是跳过 ledger 直接拼出来的周报。 |
| `wind probe` | 前置信号成立、但还不能写成成熟趋势的方向。 | 不是核心趋势的弱化说法。 |
| `project heat cluster` | 开源/项目轴很强、但行业外部确认不足的方向簇。 | 不是行业主叙事。 |
| `insufficient evidence` | 有线索但不足以形成稳定行业判断的方向。 | 不是“没有信号”。 |

## 证据与权威

| 术语 | 含义 | 审计重点 |
| --- | --- | --- |
| `authority tier` | 来源或主体的默认权威层级，如 `core`、`proven`、`watch`、`ordinary`、`excluded`。 | 必须结合 evidence axis 和 source context 解释，不能全局通吃。 |
| `source authority context profile` | 同一 authority tier 在不同证据轴中的解释规则。 | 防止把媒体、政策、论文、社区来源混用成同一种“权威”。 |
| `provisional authority` | 未正式入 registry，但经双审允许当周有限桥接的临时权威状态。 | 只能有限替代一个推动证据，且必须带过期时间和入库动作。 |
| `promotion request` | 请求把某个主体或来源提升、纳入或更新 registry 的审查动作。 | 必须保留 basis events、审批人和结论。 |
| `stale` | registry、tool snapshot 或运行上下文过旧，不能再被当作当前可靠状态。 | stale 必须影响升级资格或运行状态，不能只记日志。 |
| `counter evidence` | 与当前 claim 相冲突、相削弱或要求降级的证据。 | 必须进入审计，不能只在 prose 里提一句。 |

## Agent 协作与产物

| 术语 | 含义 | 不是什么 |
| --- | --- | --- |
| `message envelope` | 跨 Agent 消息的统一外壳，冻结发送方、接收方、kind、payload schema、run context 等。 | 不是随手发一段 JSON。 |
| `payload schema` | 某类消息 payload 的具体结构契约。 | 不是 envelope 上的自由文本说明。 |
| `message lineage` | 同一 `run_id`、`thread_id`、`correlation_id` 下，从 request 到 result、再到 claim-builder、audit、tier-decider 的结构化依赖链。 | 不是普通日志时间线。 |
| `artifact manifest` | 对每个 canonical artifact 的登记条目，说明产物类型、schema version、producer、inputs、存储位置和 hash。 | 不是文件清单，也不是目录索引。 |
| `handoff` | 一个 Agent 产物被下一个 Agent 以 envelope、manifest 和 refs 的形式正式接管。 | 不是“我在文案里提到过你就算交接”。 |
| `run_id` | 单次 daily 或 weekly 运行的稳定 ID。 | 不是线程名或 artifact 文件名替代品。 |
| `thread_id` | 同一次工作流内消息线程的 ID。 | 不是 `run_id` 的重复字段。 |
| `correlation_id` | 请求、响应、重试或 supersede 链共享的关联 ID。 | 不是消息唯一 ID。 |
| `replay window` | 选定的一段历史输入窗口，用来重跑并比较当前系统输出。 | 不是任意挑一天做人工回看。 |

## 运行、回放与验收

| 术语 | 含义 | 审计重点 |
| --- | --- | --- |
| `replay status` | 历史窗口在当前规则、schema 和工具快照下的重放状态。V1 至少有 `not_started`、`running`、`passed`、`failed`、`drifted`、`blocked`。 | 要能区分“没跑”“跑挂了”“跑通但结果漂移”。 |
| `replay result` | 某次 replay 的结果摘要，至少包括是否重建成功、误报/漏报、citation 准确性和与 baseline 的差异。 | 指标下降必须能定位到规则、数据或工具变更。 |
| `gold set` | 人工冻结的正向基准样本，定义系统应该识别出的趋势、等级和证据模式。 | 不是训练数据。 |
| `negative fixtures` | 人工冻结的反例样本，定义系统不应升级的噪声、宣传、泛 AI 热点或单轴热度。 | 不是普通失败案例堆。 |
| `citation accuracy` | 结论中的引用链能否准确回指 event/source/artifact 的质量指标。 | 不是只看链接能否打开。 |
| `axis completeness rate` | 每条 claim 的十轴是否完整输出、缺失是否显式表达的比例指标。 | 不是“有几个轴非空”这么简单。 |
| `schema version` | message、event、ledger、review、override 等结构契约的版本号。 | breaking change 必须升级版本，不能偷偷改语义。 |

## 治理与控制面

| 术语 | 含义 | 审计重点 |
| --- | --- | --- |
| `registry` | 实体、来源、权威层级、状态和提升请求的 canonical 治理对象。 | 新增、降级、提升、排除都必须有 audit。 |
| `tools` | route level、成本、授权、故障和 fallback 状态的治理对象。 | 工具变化必须能追溯到运行和负责人。 |
| `agents` | Agent 版本、职责项、输入输出和失败状态的治理对象。 | 不能让综合 Agent 静默补写缺失输出。 |
| `runs` | daily / weekly 运行对象，承载 run context、lineage、manifest 和 replay 信息。 | 每次 run 都必须有 run_id 和 schema versions。 |
| `schemas` | message、event、ledger、review、override 等结构契约的版本治理对象。 | 变更必须说明兼容性。 |
| `evals` | gold、negative、replay、指标和结果基线的治理对象。 | 指标下降必须能定位成因。 |
| `override audit` | 人工或系统对高影响字段做覆盖时的 before/after 审计记录。 | 不允许匿名修改 canonical 状态。 |
| `human review queue` | 需要人工或服务账号复核的待办队列。 | 复核未完成不得被写成已通过。 |

## 使用规则

- 设计评审、ExecPlan、实现和测试如使用本词汇表中的术语，默认采用这里的语义。
- 如需新增术语，应先补充本词汇表，再在局部文档使用。
- 局部文档可以做“本章上下文解释”，但不能把这里定义过的术语改写成别的意思。
