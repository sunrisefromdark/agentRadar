## 一句话设计

不再给三个页面硬塞同一条总榜，而是复用现有项目搜索筛选体系，做成**`Overview / Projects` 共用 daily 候选池、`Observer` 使用独立 observer 候选池、不同默认入口、少量预设子榜切换**：

1. `首页` 用多语义前排回答“今天最值”。
2. `项目库` 用预设子榜回答“怎么找对自己有用的项目”。
3. `新兴潜力项目` 用预设子榜回答“哪些值得提前看，但还没变成头部共识”。

本设计不是独立重写三个页面，而是在既有页面骨架与既有发现产物之上补“默认入口与子榜分发规则”。

   - 本文只定义这些骨架之内的默认项目分发语义、子榜切换与降饱和规则。
2. Daily 双栈发现产物与字段语义：
   - `today_pulse_projects / mission_match_projects / explore_ribbon_projects / coverage_atlas / gap_ledger` 的 canonical 含义继续以 [project-search-system-redesign-design.md](./project-search-system-redesign-design.md#L1) 为准。

3. 个性化双模式边界：
   - `客观排序 / 偏好展示` 的私有重排边界继续以 [长期个性化记忆与隐式学习设计.md](./长期个性化记忆与隐式学习设计.md#L1) 为准。
   - 本文只规定子榜轴如何与该双模式组合，不改写个性化候选质量守门。

     - `preferenceMode=preference` 只允许对当前 `preset` 已确定的客观候选集做重排，不得扩候选、补候选或跨 `preset` 借位。

     - 当偏好信号不足、缺失或被关闭时，必须稳定回退到当前 `preset` 下的客观顺序；`Projects` 回退到现有 `objective + sort` 顺序，`Observer` 回退到现有客观顺序。
     - V1 不要求新增长期记忆字段、隐式学习状态或新的个性化 schema；ExecPlan 不得为了实现本文而补造一套个性化持久化契约。

1. 页面骨架冲突：以上游 UI 文档为准，本文必须让位。

因此本设计的真实范围冻结为：

1. `Overview`：在既有 `decision gate -> continuation -> research stream` 骨架内，定义首页项目流默认怎么组织。
2. `Projects`：在既有 `filter bench -> scan rows -> dossier dock` 骨架内，定义默认子榜与切换规则。
3. `Observer`：在既有 `ecosystem summary -> candidate evidence -> follow-up context` 骨架内，定义候选项目子榜与默认前排。

## 设计 Thesis

这次不是“再发明一个更高级的排序器”，而是把已有的搜索、筛选、客观排序、偏好展示这些能力组织对。

真正的问题不是“没有分数”，而是“同一批知名项目在所有入口都成了默认答案”。如果不拆页面职责，只调权重只会继续出现三个问题：

1. 首页像热榜。
2. 项目库像热榜存档。
3. 新兴潜力项目像另一种热榜投影。

因此本设计只做两件事：

1. 把三个页面的默认问题重新冻结。
2. 用现有筛选体系做少量预设子榜，而不是新造一套榜单基础设施。

## 现状校正

先把当前代码里已经存在、但文档之前写得不够准的几件事钉死：

1. `项目库` 当前已存在两条轴：
   - `sort=score|growth`
   - `preferenceMode=objective|preference`
2. 因此本次新增的不是“客观排序 / 偏好展示”这条轴，而是：
   - `子榜切换`
   - `子榜与现有排序模式的组合规则`
3. `Observer / 新兴潜力项目` 当前已存在：
   - 搜索
   - 分页
   - `客观排序 / 偏好展示`
   - 但没有稳定的子榜落桶字段

V1 必须按这个现状写方案，不能让实现误以为要同时新发明排序轴、偏好轴和子榜轴。

## 问题定义

### 当前不足

1. `Overview`、`Projects`、`Observer` 容易被同一批高名气项目重复占位。
2. 默认排序过度依赖 `final_rank / objective_score / radarScore / 热度代理指标`，但个人用户更需要“有帮助”“有信息增量”“可早关注”。
3. 通用基础设施项目既重要又高频，若没有降饱和规则，会长期吞掉默认首屏。
4. 新兴潜力项目页本应承担“提前发现”的职责，但很容易被熟悉的大项目投影成“又一个大家都知道的榜”。

### 为什么不该新造一套榜单系统

最短路径已经在代码里了：

1. 现有项目库已经有搜索与筛选体系。
2. 现有设计已经冻结了 `客观排序 / 偏好展示` 双模式。
3. 现有 `today_pulse / mission_match / explore_ribbon / observer entries` 已经提供了候选分层。

所以最懒也最稳的方案不是新建“榜单引擎”，而是把这些已有能力收敛成“预设子榜视图”。

## 用户心智与页面职责冻结

### 1. 首页 `Overview`

首页回答：

> 今天这轮结果可信的前提下，我先看什么最值。

它不是完整检索页，也不是所有名项目的展示面。

### 2. 项目库 `Projects`

项目库回答：

> 如果我想找有用项目，先切到哪个视图最省力。

它应该像发现工作台，不像单一排行榜。

### 3. 新兴潜力项目 `Observer`

新兴潜力项目回答：

> 哪些项目现在还不是共识头部，但值得我提前建立关注。

它不是周趋势页，也不是“冷门即正义”的反热榜页。

## 核心设计决策

### 决策 1：项目库和新兴潜力项目都建立子榜切换

是，应该做，但只做少量预设子榜。

原因：

1. 用户的问题不是“我想看一个万能总榜”。
2. 用户的问题是“不同目的下，我该先看哪一类项目”。
3. 现有搜索筛选体系已经足够承接预设子榜，不值得再建新排序框架。

### 决策 2：子榜切换复用现有搜索筛选体系

V1 不新增第二套数据流。每个子榜本质上都是：

> 一组冻结的筛选条件 + 一个已有排序模式 + 一段清晰说明文案

也就是说，子榜是“预设视图”，不是“新榜单类型”。

对用户展示的命名要求也一并冻结：

1. 只用白话中文。
2. 点开前就知道会看到什么。
3. 不用“样本”“前哨”“观察”这类需要二次理解的词做主标题。
4. 内部可以保留技术 `preset_key`，外显标题必须更直白。

### 决策 2.1：子榜轴与排序轴分开

V1 明确采用“两层切换”，不是把所有东西揉成一个大开关：

1. 第一层：`子榜`
   - 我想看哪类项目
2. 第二层：`排序模式`
   - `客观排序`
   - `偏好展示`
3. `客观排序` 下继续保留现有次级排序：
   - `按分数`
   - `按增速`

冻结后的含义是：

1. `客观排序` = 当前客观候选集上的现有 `score/growth` 排序。
2. `偏好展示` = 当前客观候选集上的现有偏好重排。
3. 本次新增的是 `子榜切换`，它先决定候选集，再把候选集交给现有排序模式。

### 决策 3：头部项目改为默认降饱和，不是彻底屏蔽

`codex`、`Claude Code`、`openclaw`、`hermes`、`langchain` 这类项目应当：

1. 可见。
2. 可搜。
3. 可进入对应基础设施子榜。
4. 不再默认统治首页、项目库默认不占第一页、新兴潜力默认不占第一页，除非有明确例外原因（如它的重大新变化）。

## 统一发现底座

三个页面不共用同一默认排序，但共用同一套**解释性消费术语**：

1. `帮助度`
   - 是否更接近真实工作流、真实任务、垂直场景。
2. `信息增量`
   - 是否带来新的样本、新的组合、新的认知。
3. `证据强度`
   - 是否有足够可信信号，不是为了多样性硬凑。
4. `潜力信号`
   - 是否虽然未成头部，但已显露方向价值、扩张可能或样本意义。
5. `曝光饱和度`
   - 是否已经被默认视图过度曝光。

冻结边界：

1. 上述五项在 V1 中**不是新的 canonical score，也不是新的 machine-score 字段**。
2. ExecPlan 不得为这五项单独发明新的评分器、排序器或持久化总分。
3. V1 里所有默认分发、落桶、降级与去饱和都必须回落到本文后续冻结的**字段级规则**。
4. 若某处文案提到“帮助度成立 / 信息增量成立 / 潜力信号成立”，仅表示命中了后文定义的结构化条件，不代表存在新的隐式打分。

## Canonical 输入与候选池冻结

这一节专门解决“项目库和首页到底吃哪批字段”“旧字段是兼容还是主来源”的问题。

### 1. Overview 的 canonical 输入

`Overview` 的项目消费面只允许读取以下 daily 字段：

1. `today_pulse_projects`
2. `mission_match_projects`
3. `explore_ribbon_projects`
4. `context_only_projects`

其中：

1. `today_pulse_projects / mission_match_projects / explore_ribbon_projects` 是 V1 正式主来源。
2. `context_only_projects` 只允许作为 `基础设施变化` 或历史补充上下文的候选补充，不得回流为 `今日最值得看` 或 `与你当前方向更相关`。
3. `today_star_projects` 在 Overview 中仅作为旧 artifact 兼容回退字段，不再作为新设计的主消费对象。

补充冻结：

1. `Overview` 页面中的 `8` 张 research stream 卡，仅表示页面层展示容量。
2. 它不等于上游 discovery 设计中的 `core exposure slots <= 8` canonical 曝光位定义。
3. 其中来自 `explore_ribbon_projects` 的展示卡，必须被实现为**核心 8 位之外的页面层补带消费**，而不是回写、替换或偷改 canonical core exposure。

### 2. Projects 的 canonical 候选池

Projects V1 的候选池冻结为两层：

1. 首选 canonical 输入：
   - `today_pulse_projects`
   - `mission_match_projects`
   - `explore_ribbon_projects`
   - `context_only_projects`
2. 兼容回退输入：
   - 当 daily artifact 缺少上述双栈字段时，才允许退回 `today_star_projects + context_only_projects`

这意味着：

1. 新 artifact 存在双栈字段时，Projects 不再把 `today_star_projects` 当作主输入。
2. `today_star_projects` 只承担旧 reader / 旧 artifact 的兼容职责。
3. `context_only_projects` 可以进入 Projects 候选池，但默认只能用于：
   - 搜索命中
   - 分页补位
   - 详情回流
   - `看底层工具` / `基础设施变化` 的非主 landing 补充
4. `context_only_projects` 不得直接占据 Projects 默认 landing 前排。

### 3. Observer 的 canonical 候选池

Observer V1 的候选池只允许来自 canonical observer artifact 的 `entries[]`。

不允许：

1. 直接把 `today_pulse_projects` 混入 Observer 候选池。
2. 直接把 `mission_match_projects` 混入 Observer 候选池。
3. 用 daily 页面字段替代 observer 自身证据链。

### 4. 三页是否“同一候选池”

本文开头的“同一候选池”在 V1 的准确含义冻结为：

1. `Overview` 与 `Projects` 共用同一份 daily discovery 结果池。
2. `Observer` 不与 daily 共用物理候选池，但共用同一套“帮助度 / 信息增量 / 证据强度 / 潜力信号 / 曝光饱和度”的消费判断维度。
3. 因此 V1 不是“三页同一物理数组”，而是“两套 canonical 候选池、同一套消费原则”。

## 字段来源与 Schema 边界冻结

这一节专门解决“本文引用的字段到底来自哪里、哪些已经存在、哪些是本文新增 view-model 字段、会不会和行业级趋势判断 canonical schema 打架”的问题。

### 1. 字段分层

V1 只允许使用三层字段：

1. `canonical artifact fields`
   - 已由上游设计冻结的 daily / observer artifact 字段
   - 例如：`today_pulse_projects`、`mission_match_projects`、`explore_ribbon_projects`、`context_only_projects`、observer `entries[]`
2. `existing project payload fields`
   - 当前项目条目中已可稳定读取、且本文仅消费不改义的字段
   - 例如：`direction_matches`、`project.category`、`ecosystems`、`labels`、`topics`、`why_today_cn`、`project_brief_cn`、`score.paradigm`
3. `new view-only projection fields`
   - 本文允许新增，但只存在于 `buildProjectsView()`、Observer build 或等价 server-side projection
   - 不回写 canonical score，不改写上游 artifact，不进入行业级趋势判断 canonical schema

补充冻结：

1. 本文出现的“同一范式”是页面消费层约束，不是新分类体系。
2. `Overview` 去饱和规则中的“范式”唯一真源固定为现有项目条目可读取的 `score.paradigm`。
3. 若 `score.paradigm` 缺失、为空或不可稳定读取：
   - 不允许前端或 ExecPlan 根据 `labels / ecosystems / 中文文案` 临时猜一个范式。
   - 该项目只跳过“同一范式最多 `2` 个”这条约束，继续参与其他已冻结规则。
4. 本文不得要求为“范式”新增第二字段、第二枚举或新的 canonical schema 定义。

### 2. 本文新增且必须冻结的 view-only 字段

| 字段 | 作用范围 | 是否必需 | 来源层级 | 备注 |
| --- | --- | --- | --- | --- |
| `preset_bucket` | Projects | `是` | `new view-only projection field` | 子榜唯一落桶结果 |
| `observer_preset_bucket` | Observer | `是` | `new view-only projection field` | 子榜唯一落桶结果 |
| `utility_hint` | Projects | `是` | `new view-only projection field` | `workflow / vertical / infra / exploratory` |

| `head_project_exception_reason` | Projects/Observer/Overview | `条件必需` | `new view-only projection field` | 仅头部项目破例前排时必需 |
| `hard_infra` | Projects | `是` | `new view-only projection field` | 由服务端按本文规则一次性产出 |

### 3. 只允许作为消费依据、但本文不新建 canonical 契约的字段

以下字段若当前实现可稳定提供，可被本文消费；若不可稳定提供，必须走本文定义的降级路径，ExecPlan 不得自由猜含义：

1. `appearance_reason_codes`
2. `qualification`
3. `judge_score_delta`
4. `freshness_label`
5. `breakout_label`
6. `related_direction`
7. `keywords`

这些字段在 V1 的地位冻结为：

1. 它们不是行业级趋势判断的 canonical schema 字段。
2. 它们不是本文强制要求新落到 `schemas/industry/` 的字段。
3. 若被引用，只能作为 Projects / Observer 页面分发的辅助 view-model 输入。
4. 若对应字段缺失，不允许实现层脑补；必须按本文降级规则退回只依赖已冻结字段的判定。

### 4. 与行业级趋势判断设计的边界

为避免与 [03-数据模型契约.md](./行业级Agent趋势判断设计/03-数据模型契约.md#L1) 的 canonical schema 治理冲突，V1 明确：

1. 本文新增的 `preset_bucket`、`observer_preset_bucket`、`utility_hint`、`repeat_exposure_state`、`head_project_exception_reason`、`hard_infra` 全部属于**页面消费投影字段**。
2. 它们的真源是 `buildProjectsView()`、Observer build 或等价 server-side projection，不是 `schemas/industry/`。
3. 本文不得要求行业级趋势判断文档包为这些页面消费字段扩展 canonical schema。
4. 只有当未来这些字段被第二个业务域、第二个 Agent 链路或第二个 canonical artifact 共同依赖时，才允许进入更高层 schema 治理评审。

## 首页排序与展示设计

### 1. 首页默认语义

首页项目流位于既有 `Hero / Rail / Strip` 之后的 `research stream` 中，不改写 UI v3 已冻结的首屏骨架。

首页项目流固定为四条语义带：

1. `今日最值得看`
2. `与你当前方向更相关`
3. `值得建立新认知`
4. `基础设施变化`

首页不做子榜切换优先面，它只做有限前排。

首页项目流总容量冻结为 `8` 张卡：

1. `今日最值得看`：`2`
2. `与你当前方向更相关`：`3`
3. `值得建立新认知`：`2`
4. `基础设施变化`：`1`

### 2. 首页排序机制

首页继续走最小机制：

1. 候选来自现有 daily 高质量项目池。
2. 先分配语义带，再在带内排序。
3. 对头部项目执行默认降饱和。

项目在首页四条语义带中的归属顺序冻结为：

1. `与你当前方向更相关`
2. `今日最值得看`
3. `值得建立新认知`
4. `基础设施变化`

同一项目在首页首屏只能出现一次。先命中高优先级语义带后，不再重复出现在后续语义带。

### 3. 首页映射到现有结构

1. `今日最值得看` 主要消费 `today_pulse_projects`
2. `与你当前方向更相关` 主要消费 `mission_match_projects`
3. `值得建立新认知` 主要消费 `explore_ribbon_projects`
4. `基础设施变化` 主要消费基础设施子集与 `context_only_projects`

这里与上游 discovery 设计的关系明确冻结为：

1. `today_pulse_projects + mission_match_projects` 仍是 daily 的 8 个核心曝光位来源。
2. `explore_ribbon_projects` 仍然不是 daily canonical 的核心曝光位。
3. 在 `Overview` 页面表现层中，允许把 `explore_ribbon_projects` 作为研究流中的独立语义带展示。
4. 这属于页面消费层重编排，不构成对上游 `core exposure slots <= 8` canonical 语义的改写。

### 4. 首页去饱和规则

1. 同一组织首页项目流最多 `1` 个。
2. 同一范式首页项目流最多 `2` 个。
3. `head_project=true` 默认不能占据首页项目流第一主位，除非有明确例外原因（如它的重大新变化）。

首页空态与降级规则也一并冻结：

1. `与你当前方向更相关` 缺候选时，显示明确空态，不允许拿头部通用项目硬补位。
2. `基础设施变化` 缺候选时，该带可以折叠。
3. `值得建立新认知` 缺候选时，允许保持空态，不允许直接回退成另一条热榜。
4. 任何降级都不能突破首页项目流 `8` 张卡上限。

## 项目库子榜设计

### 1. 设计原则

项目库不再默认是一条降序列表，而是“默认子榜 + 显式切换”。

V1 不建议做很多，`4` 个够了。

### 2. V1 子榜冻结

1. `更可能用得上`
   - 目标：优先找到更可能直接有用、且没有被过度曝光的项目。
   - 机制：现有筛选体系 + 帮助度优先 + 去饱和。
2. `按场景找`
   - 目标：集中看行业 / 职能 / 生活场景 agent。
   - 机制：复用方向命中、场景型标签、mission 类筛选。
3. `今天值得试试`
   - 目标：集中看高信息增量项目。
   - 机制：优先消费 `explore_ribbon_projects` 与探索型样本。
4. `看底层工具`
   - 目标：集中看 runtime / framework / memory / platform。
   - 机制：复用现有基础设施分类与客观排序。

### 3. 排序与模式

项目库子榜切换不改变大框架：

1. 子榜先确定候选集。
2. 候选集内继续保留 `客观排序 / 偏好展示` 双模式。
3. 默认进入 `更可能用得上 + 客观排序 + 按分数`。

这样既复用现有设计，也避免把“子榜”和“个性化”揉成一个黑盒。

这里的排序组合关系冻结为：

1. `子榜` 决定候选集。
2. `客观排序` 下，继续沿用现有 `按分数 / 按增速`。
3. `偏好展示` 下，先按偏好重排；同信号项目仍回退到现有客观顺序。

### 3.1 Projects 子榜的 URL 与交互契约

为避免实现阶段自行发明路由协议，Projects V1 先提出以下查询参数目标：

1. `preset`
   - 取值：`useful_first | by_scenario | worth_trying_today | infra_tools`
2. `preferenceMode`
   - 取值：`objective | preference`
3. `sort`
   - 仅当 `preferenceMode=objective` 时生效
   - 取值：`score | growth`
4. `q`
   - 显式搜索词
5. 现有分页参数继续保留

组合规则冻结如下：

1. 进入 `/projects` 无参数时，默认：
   - `preset=useful_first`
   - `preferenceMode=objective`
   - `sort=score`
2. 切换 `preset` 时：
   - 保留当前 `q`
   - 保留当前 `preferenceMode`
   - 若当前是 `objective`，保留当前 `sort`
3. 切换 `preferenceMode` 时：
   - 保留当前 `preset`
   - 若切到 `preference`，`sort` 仍保留在 URL 但不参与排序计算
   - 若切回 `objective`，恢复使用当前 `sort`
4. 显式搜索时：
   - 先按 `preset` 过滤候选集，再在该候选集内执行搜索与排序
   - 搜索结果不取消 `preset`，只缩小该 `preset` 下的结果集
5. 分页时：
   - 先确定 `preset` 候选集
   - 再执行 `search -> sort/rerank -> paginate`
   - 不允许先分页再分桶
6. 默认降饱和只影响默认 landing 排序，不影响：
   - 显式搜索命中集合
   - 指定 `preset` 内的正常浏览
   - 详情页直达

URL 边界补充冻结：

1. 本节定义的是 **目标 URL 契约**，用于避免 ExecPlan 在页面层自行发明状态机。
2. 由于 UI V3 文档把既有 URL / query 消费语义的最终所有权留在 reader/context 基线层，本文不得单独越权改写已有参数含义。
3. 因此实现落地时，`preset` 参数需要由后续 router/context 契约文档或实现评审正式接纳；在那之前，本节可作为页面消费目标，不得被理解为前端可绕开基线直接自定义解析。

### 4. 项目归组优先级

一个项目同时命中多类条件时，Projects V1 的**唯一机器落桶顺序**冻结如下，ExecPlan 只能实现这一套，不允许再保留第二套口语优先级：

1. `hard_infra=true`
   - `preset_bucket=infra_tools`
2. 否则若 `direction_matches` 非空，或 `project` 的场景标签命中 V1 must-cover 方向目录
   - `preset_bucket=by_scenario`
3. 否则若项目来自 `explore_ribbon_projects`，或命中本文定义的“信息增量成立”
   - `preset_bucket=worth_trying_today`
4. 否则若项目来自 `today_pulse_projects`，且不是 `hard_infra`
   - `preset_bucket=useful_first`
5. 否则
   - 不进入默认 landing 分发

`hard_infra=true` 的判定只允许来自：

1. `direction_matches` 为空，且
2. `utility_hint=infra`，且
3. `project.category / ecosystems / labels / topics` 明确命中 runtime、framework、memory、platform、tooling、observability、deployment 等基础设施语义

补充说明：

1. 若项目既有明确场景命中，又有基础设施能力，但其主价值面向垂直工作流或行业任务，则不算 `hard_infra`。
2. “基础设施项目默认先留在 `看底层工具`”只适用于 `hard_infra=true`。
3. 不是所有带 infra 标签的项目都强制进入 `看底层工具`。

### 5. 项目库 V1 必需字段

为了让子榜切换不是纯文案，V1 在项目库 view-model 中冻结以下字段要求：

1. `preset_bucket`
   - 必需
   - 取值：`useful_first | by_scenario | worth_trying_today | infra_tools`
2. `utility_hint`
   - 必需
   - 取值至少覆盖：`workflow | vertical | infra | exploratory`
3. `repeat_exposure_state`
   - 必需
   - 至少区分：`normal | decayed`
4. `head_project_exception_reason`
   - 条件必需
   - 仅当 `head_project=true` 且项目出现在默认 landing 或非基础设施子榜前排时必须提供

这些字段的计算位置冻结为：

1. `preset_bucket`
   - 必须在 `buildProjectsView()` 或其上游 server-side projection 中产出
   - 前端不得自行根据标签二次推导
2. `utility_hint`
   - 必须在 server-side projection 中产出
3. `repeat_exposure_state`
   - 必须基于已有 exposure history / recent daily reports 计算
4. `head_project_exception_reason`
   - 必须由 server-side rule 写出可审计原因码

没有 `preset_bucket` 的项目，不允许进入子榜首屏默认分发，只能停留在搜索结果或历史补位中。

### 6. 现有 bucket 到项目库子榜的映射

V1 必须显式维护一张映射表，不能只靠文案理解：

| 现有 bucket | 新子榜主去向 | 准入规则 | 默认是否可进 landing |
| --- | --- | --- | --- |
| `mission_match` | `按场景找` | 有方向命中或场景命中 | `是` |
| `today_pulse` | `更可能用得上` | 非头部通用基础设施，且帮助度成立 | `是` |
| `explore_ribbon` | `今天值得试试` | 信息增量成立 | `是` |
| `today_pulse` | `看底层工具` | 属于通用基础设施或头部基础设施 | `是` |
| `historical_context` | 无默认主去向 | 仅用于搜索命中、分页补位、详情回流 | `否` |

如果一个项目同时满足多条映射规则，按本节冻结的**唯一机器落桶顺序**确定唯一 `preset_bucket`。

### 6.1 Projects 落桶规则的确定性定义

ExecPlan 不允许再自己补“帮助度成立”“信息增量成立”的算法。V1 的最终落桶顺序以上一节为准，这一节只补充辅助定义与缺字段降级：

辅助定义也冻结如下：

1. `帮助度成立`
   - 至少满足一项：
     - `direction_matches` 非空
     - `utility_hint` 为 `workflow` 或 `vertical`
     - `why_today_cn / project_brief_cn` 明确描述真实任务流、工作流或垂直场景价值
2. `信息增量成立`
   - 至少满足一项：
      - 项目原本就在 `explore_ribbon_projects`
      - `appearance_reason_codes` 存在且包含探索/新样本语义原因码
      - `judge_score_delta`、`qualification`、`freshness_label` 中任一可用字段，明确说明“今天之所以值得看”来自新变化，而不是既有高名气
3. `头部通用基础设施`
   - `head_project=true`
   - `utility_hint=infra`
   - 无明确 `direction_matches`

`head_project_exception_reason` 只允许使用以下原因码：

1. `major_new_release`
2. `new_branch_or_mode`
3. `new_domain_adoption`
4. `critical_ecosystem_shift`

若需要新增原因码，必须回到设计文档升级，不允许 ExecPlan 自增。

缺字段降级冻结如下：

1. 若 `appearance_reason_codes / qualification / judge_score_delta / freshness_label` 均不可用：
   - `信息增量成立` 只允许由“项目来自 `explore_ribbon_projects`”这一条成立
2. 若 `project.category / ecosystems / labels / topics` 无法稳定读取：
   - 不允许把项目判成 `hard_infra=true`
   - 该项目只能继续走 `by_scenario -> worth_trying_today -> useful_first` 的剩余判定
3. 若 `direction_matches` 缺失：
   - 不允许前端或 ExecPlan 依据中文文案猜场景命中
   - `by_scenario` 只能由已冻结的场景标签映射命中

## 新兴潜力项目子榜设计

### 1. 页面目标

新兴潜力项目页要回答的不是“谁最火”，而是：

1. 哪些项目现在还不是头部共识。
2. 哪些项目已经露出值得提前关注的信号。
3. 哪些只是大项目的尾部投影，不应伪装成潜力发现。

### 2. V1 子榜冻结

1. `值得提前关注`
   - 目标：默认先看最值得提前关注的一批。
   - 机制：现有 observer 候选池 + 潜力信号优先 + 头部项目降饱和。
2. `新方向`
   - 目标：看新的能力组合、新实验路径、新范式样本。
   - 机制：优先信息增量与探索型证据。
3. `按场景找`
   - 目标：看垂直领域里尚未头部化、但已显露价值的项目。
   - 机制：复用场景/方向筛选。
4. `看底层新东西`
   - 目标：只在需要时看基础设施层的早期变化。
   - 机制：复用基础设施分类，但不让它回流统治默认 `值得提前关注`。

### 2.1 Observer 页面骨架与子榜的共存方式

Observer 不是被本文改造成“只有项目列表的页面”。

V1 页面消费顺序冻结为：

1. 顶部仍先展示 observer 自身的 `ecosystem summary / scope / watch guidance`
2. 中段才进入候选项目子榜切换
3. 下段保留 `candidate evidence / linked context / follow-up context`

也就是说：

1. `值得提前关注 / 新方向 / 按场景找 / 看底层新东西` 只作用于 observer candidate list
2. observer 作为 `catalog incubator`、方向观察台和 follow-up context 的职责全部保留
3. 本文不删除、不替代上游 Observer 的 summary / evidence / context 结构，只重写其项目候选默认入口

### 3. 默认去饱和规则

1. 已经是大众熟面孔的头部项目，默认不应进入 `值得提前关注` 前排。
2. 若一个项目的“潜力感”只来自名气延伸，而不是新信号，它只能进入 `看底层新东西` 或被降到后排。
3. 同组织、同家族项目不得占满潜力页前排。

### 4. 头部项目何时可破例进入潜力页前排

只在以下情况允许：

1. 该项目衍生出明显新分支、新用法或新场景。
2. 当前证据说明用户该关注的是“它的重大新变化”，不是“它很有名”。
3. 若移除它，会明显损失潜力页对新方向的解释力。

### 5. Observer V1 必需字段

Observer 当前没有稳定子榜字段，因此 V1 不能只写“也可以不加字段”。

V1 冻结两种做法，且必须二选一写死到实现：

1. 方案 A：在 Observer view-model 中新增必需字段 `observer_preset_bucket`
2. 方案 B：在 view build 阶段基于现有字段稳定派生 `observer_preset_bucket`

本设计选择 `方案 B` 作为 V1 默认：

1. 不改 canonical observer artifact。
2. 在页面 view-model / React props 层新增必需字段 `observer_preset_bucket`。
3. 该字段由现有数据稳定派生，而不是前端自由猜。

`observer_preset_bucket` 取值冻结为：

1. `early_watch`
2. `new_direction`
3. `by_scenario`
4. `infra_early`

### 6. Observer 落桶派生规则

`observer_preset_bucket` 必须在服务端或 build 层一次性算好，前端只消费结果。Observer V1 的**唯一机器落桶顺序**冻结如下：

1. 若 `labels / ecosystems / topics / related_direction` 明确命中垂直场景语义：
   - `by_scenario`
2. 否则若命中基础设施语义，且不存在更强场景命中：
   - `infra_early`
3. 否则若 `freshness_label / breakout_label / judge_score_delta / qualification` 体现出新变化、新冒头或新组合：
   - `new_direction`
4. 其余默认：
   - `early_watch`

这个顺序是冻结的，避免前端和服务端各算各的。

### 6.1 Observer 落桶规则的确定性补充

为避免实现层自行理解“新方向”“潜力信号”，V1 再补三条硬规则：

1. `infra_early`
   - 只有当基础设施语义是项目主价值面，且不存在更强场景命中时成立
2. `by_scenario`
   - 只有当 `related_direction`、`labels`、`ecosystems` 或主题映射到 V1 must-cover 方向目录中的场景方向时成立
3. `new_direction`
   - 只有当“新变化”来自结构化变化信号，而不是单纯高分或高星时成立

以下定义一并冻结：

1. `潜力信号成立`
   - 至少满足一项：
     - `breakout_label` 明确为 breakout / rising / early signal
     - `judge_score_delta > 0` 且原因来自新变化
     - `qualification` 体现新样本、新组合或新用法
2. `名气延伸而非新信号`
   - `head_project=true`
   - 且未命中上述任何 `潜力信号成立` 条件
3. `重大新变化`
   - 只允许复用与 Projects 相同的例外原因码集合：
     - `major_new_release`
     - `new_branch_or_mode`
     - `new_domain_adoption`
     - `critical_ecosystem_shift`

缺字段降级冻结如下：

1. 若 `related_direction / keywords / breakout_label / freshness_label / judge_score_delta / qualification` 缺失：
   - 只允许使用 `labels / ecosystems / topics` 与 observer entry 已有结构字段派生 bucket
2. 若连 `labels / ecosystems / topics` 都缺失：
   - `observer_preset_bucket` 默认回退为 `early_watch`
   - 不允许前端根据中文摘要、自然语言文案或自由标签猜 bucket

### 6.2 Observer 的 URL 与交互契约

Observer V1 先提出以下查询参数目标：

1. `preset`
   - 取值：`early_watch | new_direction | by_scenario | infra_early`
2. `preferenceMode`
   - 取值：`objective | preference`
3. `q`
   - 显式搜索词
4. 现有分页参数继续保留

组合规则冻结如下：

1. 进入 `/observer` 无参数时，默认：
   - `preset=early_watch`
   - `preferenceMode=objective`
2. 切换 `preset` 时，保留当前 `q` 与 `preferenceMode`
3. 切换 `preferenceMode` 时，保留当前 `preset` 与 `q`
4. 搜索时：
   - 先按 `preset` 过滤
   - 再在该候选集内搜索
   - 再执行客观排序或偏好重排
5. 分页时：
   - 先确定 `preset` 候选集
   - 再执行 `search -> rank/rerank -> paginate`
6. 默认降饱和不影响：
   - 显式搜索命中
   - 指定 `preset` 浏览
   - 详情直达

URL 边界补充冻结：

1. 本节定义的是 **目标 URL 契约**，用于约束 Observer 页面状态组合，不是对 reader/context 基线的单边改写。
2. `preset` 参数只有在后续 router/context 契约正式接纳后，才能成为既有 query 语义的一部分。
3. 在正式接纳前，ExecPlan 不得把这里理解为“前端自行新增一套不受基线约束的 query 解析”。

## 预设子榜与现有搜索筛选体系的结合方式

### 1. 最小实现原则

子榜切换不新增一套页面，不新增一套 artifact，不新增一套排序字段。

V1 只需要：

1. 一个 `preset_key`
2. 一组冻结筛选条件
3. 一个默认排序模式
4. 一段“为什么这个子榜存在”的说明

项目库与 Observer 的最小差异也冻结如下：

1. 项目库使用 `preset_bucket`
2. Observer 使用 `observer_preset_bucket`
3. 两者都只作为 view-only 字段，不回写 canonical score

### 2. 与现有双模式的一致性

现有设计里已经有：

1. `客观排序`
2. `偏好展示`

子榜切换是横轴，排序模式是纵轴。不要把两者合并成一个开关。

推荐的用户心智是：

1. 我先选“看哪类项目”
2. 再决定“按客观排序还是偏好展示”

### 3. 数量控制

V1 每页最多 `4` 个子榜。

原因很简单：子榜太多，用户又会回到“我该点哪个”的负担里。

## 兼容契约

### 1. 与现有产物的关系

本设计不推翻现有：

1. `today_pulse_projects`
2. `mission_match_projects`
3. `explore_ribbon_projects`
4. Observer `entries[]`
5. `客观排序 / 偏好展示`

它只重写这些结果的默认入口和默认解释。

### 2. 建议新增的最小字段

若要把子榜切换做得可执行，V1 至少补这几个 view-only 字段：

1. `preset_bucket`
   - 项目库必需
   - 当前项目命中的预设子榜
2. `observer_preset_bucket`
   - Observer 必需
   - 当前候选命中的预设子榜
3. `utility_hint`
   - `workflow / vertical / infra / exploratory`
4. `repeat_exposure_state`
   - 是否处于连续曝光衰减
5. `head_project_exception_reason`
   - 为什么这次允许头部项目冲进默认前排
6. `hard_infra`
   - 是否属于应优先沉到底层工具子榜的硬基础设施项目

这里不再写“没有这些字段也能做”。

V1 结论是：

1. `preset_bucket` 必需
2. `observer_preset_bucket` 必需
3. 其余字段至少要满足被规则引用时可读

### 3. 降级语义

1. 若缺少 `preset_bucket`，项目库不能开启子榜 landing，只能退回现有项目库客观列表。
2. 若缺少 `observer_preset_bucket`，新兴潜力项目不能开启子榜 landing，只能退回现有 Observer 客观列表。
3. 若缺少增强字段，必须优先使用仍可读取的最小去饱和规则，不能直接退回热榜。
4. 不允许因为字段不全，就把首页、项目库、新兴潜力项目重新做成同一条总榜。

最小去饱和兜底冻结如下：

1. 若 `head_project=true` 可读，但 `repeat_exposure_state / head_project_exception_reason` 不可读：
   - 仍执行基础去饱和
   - 基础规则仅包括：
     - 头部项目不得自动占据首页第一主位
     - 头部项目不得自动占据 `Observer / 值得提前关注` 前排
     - Projects 默认 landing 前排最多保留有限头部项目
2. 若连 `head_project` 都不可读：
   - 不执行强降权
   - 但也不允许实现层根据名字、星数或主观印象临时识别“头部项目”
3. 若 `head_project_exception_reason` 缺失：
   - 头部项目默认不得因“可能有新变化”而获得破例前排

若双栈字段缺失，需要按以下顺序降级：

1. Projects：
   - 先退回 `today_star_projects + context_only_projects`
   - 仍保留 `preset` UI，但只允许：
     - `useful_first`
     - `infra_tools`
   - `by_scenario / worth_trying_today` 必须明确标记为降级不可用
2. Observer：
   - 若缺少 `observer_preset_bucket`，直接退回现有 Observer 客观列表
   - 不允许前端临时根据中文文案猜 bucket
3. Overview：
   - 若缺少 `mission_match_projects`，`与你当前方向更相关` 显示空态
   - 若缺少 `explore_ribbon_projects`，`值得建立新认知` 允许折叠
   - 不允许拿 `today_pulse_projects` 补成另一条热榜

对外文案降级时，优先使用：

1. 项目库：`更可能用得上`
2. 新兴潜力项目：`值得提前关注`

## 验收口径

### 1. 首页

1. 首页首屏不再是同一条项目总榜。
2. 头部通用项目无额外理由时不能占据首页第一主位。
3. 用户能区分四条语义带，而不是只看到“排在前面”。
4. 首页首屏总卡数 `<= 8`。
5. 同一项目不得重复出现在多个语义带。
6. `与你当前方向更相关` 缺候选时必须显示空态，而不是拿头部项目补位。

### 2. 项目库

1. 项目库存在不超过 `4` 个预设子榜切换。
2. 默认进入 `更可能用得上`，不是 `全局热度`。
3. `看底层工具` 独立存在，且不再默认统治第一页。
4. 子榜切换与 `客观排序 / 偏好展示` 双模式可以共存。
5. `客观排序` 明确等于当前客观候选集上的 `按分数 / 按增速`，不是新发明的排序模式。
6. 默认 landing 前 `12` 个结果中，`head_project` 不超过 `2` 个，同一组织不超过 `2` 个。
7. 显式搜索、详情直达、指定子榜内浏览不受默认降饱和误伤。
8. `preset`、`preferenceMode`、`sort`、`q` 的组合行为与本文交互契约一致。

### 3. 新兴潜力项目

1. 新兴潜力项目存在不超过 `4` 个预设子榜切换。
2. 默认 `值得提前关注` 前排不再被知名头部项目统治。
3. 用户能区分“真正潜力样本”和“熟悉大项目的延伸投影”。
4. `看底层新东西` 是独立子榜，不回流吞掉 `值得提前关注`。
5. `observer_preset_bucket` 必须在 build 层稳定产出，前端不自行猜测。
6. observer 页面的 summary / evidence / follow-up context 结构仍然存在，未被子榜列表取代。

## 禁止事项

1. 不允许再造一套新的综合总分。
2. 不允许把“子榜切换”做成一堆难懂的小标签组合。
3. 不允许把头部项目一刀切隐藏。
4. 不允许把新兴潜力项目再次写成 `Weekly / 周趋势`。
5. 不允许默认入口的降饱和规则误伤显式搜索、详情直达和指定子榜浏览。
6. 不允许前端根据中文标题、自由标签或临时启发式自行推断 `preset_bucket / observer_preset_bucket`。
7. 不允许把 `context_only_projects` 重新伪装成 Projects 默认 landing 主来源。
