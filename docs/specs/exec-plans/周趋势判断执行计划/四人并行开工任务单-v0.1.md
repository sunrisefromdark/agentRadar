# 四人并行开工任务单 v0.1

## 用途

本任务单是对以下执行计划的派工摘录，目标是让 `1/2/3/4号执行人` 在收到任务后当天即可各自开工，而不是先等待别人把整条链打通：

- `docs/specs/exec-plans/周趋势判断执行计划/行业级Agent趋势判断-v0.1.exec-plan.md`
- 四份对应子计划

本任务单不是第二份设计真源，只负责把“谁今天先做什么、什么时点再接线、哪些事情不能互相等”说清楚。

## 总规则

1. 四个人都允许在 `Day-0/Day-1` 立即开工。
2. `Day-0/Day-1` 只做本组目录内 preparatory work，不把本地 stub 当成跨组正式契约。
3. 跨组正式 handoff、claim-critical payload 和 same-run 接线，等 `4号执行人` 完成 `Phase 1A` 后再收口。
4. 谁发现共享 helper 或旧共享模块需要改写，先提 `shared-runtime-note`，再在本组目录内保留临时 seam 继续推进；不允许因为等共享抽取而停工。
5. owner / attestation / unresolved group 争议只把高影响事项送进 same-run critical resolution；长尾争议默认走 provisional 或 post-weekly 治理。

## 先看这一段就能分工

### `handoff freeze` 用大白话解释

- 它的意思不是“冻结开发”，而是“冻结跨组交接格式”。
- 到了这个点之后，谁要把东西交给别人，就必须按正式 envelope、payload、manifest、artifact ref 来交。
- 在这个点之前，各组可以先在自己目录里用临时 seam、临时 fixture、临时 stub 把本组逻辑跑起来，但这些东西不能直接当正式交接件。

### 四个人的实际关系

- `1号`、`2号`、`3号` 是三个并行领域组，各做各的第一阶段，不互相等。
- `4号` 负责把交接格式、兼容规则、拼装入口定下来，再按谁先交齐就先接谁。
- 所以关系不是 `1 -> 2 -> 3 -> 4`，而是 `1/2/3 并行 -> 4 按组接入 -> 全量 weekly 拼装`。

### 一张表看清楚

| 执行人 | 先做到哪一步 | 先交给谁 | 什么时候必须等 | 等到什么再继续 |
| --- | --- | --- | --- | --- |
| `1号执行人` | source catalog、route 草稿、negative fixture、owner-boundary 样本、local seam、测试骨架先跑通 | `4号执行人` | 要做正式跨组 handoff、claim-critical payload、same-run 接线时 | `4号执行人` 发出 canonical schema、payload 正式名、artifact path |
| `2号执行人` | paper / conference source、citation / freshness 规则、replay window、boundary 样本、local seam、测试骨架先跑通 | `4号执行人` | 要做正式跨组 handoff、claim-critical payload、same-run 接线时 | `4号执行人` 发出 canonical schema、reason/state 真源、current fixtures |
| `3号执行人` | source catalog、owner-boundary / propagation / anti-upgrade 样本、coverage / contribution 草稿、local seam、测试骨架先跑通 | `4号执行人` | 要做正式跨组 handoff、claim-critical payload、same-run 接线时 | `4号执行人` 发出 canonical schema、payload 正式名、compatibility matrix |
| `4号执行人` | schema、payload registry、artifact path、structure tests、normalization / audit / weekly shell 先立起来 | 全员 | 要做最终 weekly 集成时 | 三个领域组至少分别交出正式 handoff；哪组先齐就先接哪组 |

### 推荐顺序

1. 四个人今天一起开工。
2. `1/2/3号执行人` 先把本组本地工作面打开，不等正式合同。
3. `4号执行人` 尽快把 `Phase 1A` 发出来。
4. 哪个领域组先把正式 handoff 补齐，`4号执行人` 就先接那个组做 contract test 和 dry-run。
5. 最后才是三组一起做 weekly 闭环。

## 按阶段走到完工

这一段只回答三件事：

- 你现在能做到哪一步
- 下一步要等谁
- 等到对方交出什么东西，你再继续做什么

### 第 1 步：四个人今天一起开工

- `1/2/3号执行人` 先做各自目录里的 source、规则、样本、测试骨架、本地 seam。
- `4号执行人` 同时开始做 schema materialization、artifact path、payload registry、structure tests、weekly shell。
- 这一步谁都不用等谁。

### 第 2 步：先过闸门 A

闸门 A 只要求四件事：

- 设计已批准
- 职责映射清楚
- 单写者边界清楚
- 目录模板清楚

到了这里，四个人就都能开工。不要把闸门 A 理解成“还要等中台先把 schema 发完”。

### 第 3 步：进入 `Phase 0.5`

- `1号执行人` 继续做政策金融组自己的 source、rules、fixtures、seam、tests 骨架。
- `2号执行人` 继续做学术组自己的 source、rules、fixtures、seam、tests 骨架。
- `3号执行人` 继续做产品生态组自己的 source、rules、fixtures、seam、tests 骨架。
- `4号执行人` 继续做 schema、artifact path、payload registry、structure tests、weekly shell。

这一步的目标不是“把全链路一次做完”，而是“每个人手里都有独立工作面，不被别人卡住”。

### 第 4 步：等 `4号执行人` 完成 `Phase 1A`

`Phase 1A` 是 `4号执行人` 的第一批关键交付，主要包括：

- canonical schema
- artifact path
- payload 正式名
- message / manifest 正式交接格式
- compatibility matrix

`1/2/3号执行人` 在等这一步的时候，不是停工，而是继续把本地 seam、fixture、event builder、writer 草稿做扎实。

### 第 5 步：谁先准备好，谁先进入 `handoff freeze`

- `handoff freeze` 不是三组一起进。
- 哪个领域组先把正式 envelope、payload、manifest、refs 补齐，哪个组就先 freeze。
- freeze 之后，这一组就可以先把正式交接件交给 `4号执行人`。

这一步开始后：

- `4号执行人` 先接已准备好的那一组做 contract test。
- `4号执行人` 先接已准备好的那一组做 normalization dry-run。
- 不等另外两组一起到齐。

### 第 6 步：`4号执行人` 再发布 `Phase 1B / 1C`

这两步主要是后接线能力，不是前三组早期开工前提，主要包括：

- activation
- stop
- budget
- review
- same-run runtime

也就是说：

- 前三组早先的 source / event 开发，不需要等这些东西齐了才开始。
- 只有当某组要把高成本拉取、same-run、budget/review 这些能力真正接上时，才回头消费这批产物。

### 第 7 步：`1/2/3号执行人` 继续并行做正式 producer

- `1号执行人` 不等 `2号`、`3号`。
- `2号执行人` 不等 `1号`、`3号`。
- `3号执行人` 不等 `1号`、`2号`。

这一步还是并行推进，不存在“谁必须排在谁后面”。

### 第 8 步：`4号执行人` 按组增量接入

- 哪一组先 freeze 正式 handoff，`4号执行人` 就先接哪一组。
- 哪一组先交齐 envelope / payload / manifest / refs，`4号执行人` 就先做哪一组的 dry-run、normalization、claim / audit 接线。
- 某一组没好，只影响那一组，不影响另外两组继续推进。

### 第 9 步：最后才进闸门 C

只有到了最终 weekly 集成，才需要等下面三类东西都齐：

- 三组 handoff 全量齐备
- cross-group replay / eval 资产齐备
- weekly internal / consumer / public 三层闭环验证通过

到了这一步，大家再一起做最后拼装和总验收。

### 一句话记住顺序

先四个人一起开工，再由 `4号执行人` 冻结正式边界，然后谁先准备好谁先交中台，最后才做全量 weekly 闭环。

## 三个明确的阶段闸门

### 闸门 A：允许当天开工

只要求：

- 已批准设计文档
- 总控职责映射
- 单写者边界
- 目录模板

### 闸门 B：允许正式 handoff freeze

要求：

- `4号执行人` 已完成 `Phase 1A`
- canonical schema、artifact path、payload 正式名已冻结
- 各组把本地 seam 收口到正式 contract

补一句白话：

- 这道闸门不是“到这里大家暂停”，而是“到这里开始不能再拿临时件跨组传递”。

### 闸门 C：允许最终 weekly 集成

要求：

- 三组 handoff 全量齐备
- cross-group replay / eval 资产齐备
- normalization / audit / tier / public projection 闭环验证通过

## 明确禁止的“等待理由”

- “等 4 号把 schema 全部发完我再开始 source/fixture”
- “等别组先把 owner-boundary 样本写完我再做 event builder”
- “等 shared runtime 抽出来我再写本组逻辑”
- “等三组全部交齐我才开始 normalization dry-run”
- “等所有长尾争议都 same-run 裁清我才继续 weekly”

## 明确允许的提前推进

- 本组目录内 local adapter seam
- 本组目录内 replay / eval / negative fixture
- 本组目录内 source catalog / route / freshness / owner-boundary 草稿
- 中台提前消费 preparatory artifact refs 做早期 contract review
- unresolved group 先按 provisional / post-weekly 路径挂账
