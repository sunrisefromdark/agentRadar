# 侧边助手自然语言搜索需求分析

## 文档状态

- 状态：`READY`
- 需求级别：`S2 - Medium Feature`
- 分析方法：依据 [需求分析_skill.md](需求分析_skill.md#L1) 输出
- 关联前置： [自然语言模糊搜索与推荐需求分析.md](自然语言模糊搜索与推荐需求分析.md#L1) 已冻结 `direct-search first` 与 `zero-result LLM routing`；本文在其之上冻结“侧边助手入口、多轮对话记忆与结果预览形态”的产品需求。
- 本文目标：明确“把自然语言项目搜索从隐式补救能力，升级为显式侧边助手入口”的用户价值、交互边界、会话记忆范围、结果展示口径与验收标准。

## Requirement Size

`S2 - Medium Feature`

判定原因：

- 本需求不重写项目库发现、评分、日报、周报或底层项目事实来源，但会改变用户进入自然语言搜索的主交互路径。
- 它同时影响入口可发现性、搜索流程、对话上下文、结果展示、详情打开路径和主列表状态切换。
- 它要求引入多轮会话记忆与新的用户可见状态，但不要求构建通用聊天系统、长期用户画像或跨设备记忆平台。

## 1. Background

### 需求来源

- 当前自然语言模糊搜索已经存在，但它主要作为“原搜索无结果时的补救逻辑”隐式触发，用户无法明确感知“这里可以用自然语言找项目”。
- 现有产品里，用户更容易把主搜索框理解成普通关键词搜索；即使系统支持模糊搜索，用户也未必知道应该尝试整句表达。
- 团队已经明确收口：保留原普通搜索不动，新增一个更显性的侧边助手入口，作为默认的自然语言搜索入口。

### 业务背景

- 项目库的核心价值仍然是“在站内项目库里找到值得看的 Agent / AI software 项目”，而不是做一个泛用知识问答机器人。
- 当前仓库已经冻结了自然语言搜索的底层原则：已有结果优先、零结果才走 LLM 解释、LLM 不直接生成项目事实、敏感领域只做站内项目关键词检索。
- 因此，这次需求的重点不再是“要不要做自然语言搜索”，而是“如何把这项能力以更容易被发现、更容易被理解的方式交付给用户”。

### 用户动机

- 用户希望有一个明确入口，可以直接输入“最近值得关注的金融 Agent”“有没有偏开源的客服 Agent”“再给我几个量化方向项目”这类自然语言请求。
- 用户希望系统先给少量精选线索，帮助自己快速判断方向是否对，再决定是否进入完整项目列表。
- 用户希望在连续追问时不必每次重写全部条件，而是让系统记住刚才的主题、方向和限制条件。

## 2. Goals

### 产品目标

- 把自然语言搜索从“隐式 fallback”升级为“显式侧边助手入口”，提高能力可发现性。
- 让用户在助手内先看到少量、轻量、可点击的结果预览，而不是直接面对完整项目列表。
- 支持围绕同一主题连续追问，让自然语言搜索具备基础多轮对话能力。
- 保持原有普通项目搜索的定位稳定，不把主搜索框变成混合模式入口。

### 用户价值

- 用户更容易意识到产品支持“自然语言找项目”，不必猜测主搜索框是否能理解整句请求。
- 用户能先看 3 条精选超链接和简短说明，快速判断方向是否对。
- 用户可以继续追问“再给我几个”“更偏开源一点”“换成金融投研方向”，而不用从头描述上下文。
- 用户仍然能在需要时进入完整主列表，查看这次自然语言查询的全部结果。

## 3. Users & Scenarios

### 用户角色

- 快速探索型用户：想先得到几个方向正确的项目，再决定是否展开完整浏览。
- 任务导向型用户：带着明确需求来找项目，例如金融投研、客服工单、导购、电商自动化、Browser Use 等方向。
- 连续追问型用户：希望在第一次结果基础上继续收窄或扩展条件，而不是重开搜索。
- 轻量浏览型用户：更愿意点击几个项目详情看看，而不是一开始就处理完整结果页。

### 使用场景

#### 场景 1：首次自然语言提问

- 触发：用户点击右侧侧边助手，输入“最近值得关注的金融 Agent 有哪些”。
- 目标：系统返回简短说明和 3 条项目超链接，让用户快速判断方向是否对。

#### 场景 2：沿着当前主题继续追问

- 触发：用户上一轮看过金融方向结果后，再输入“更偏开源一点”。
- 目标：系统不把这句话当独立查询，而是在“金融 Agent”上下文里继续收窄结果。

#### 场景 3：用户只想快速点项目详情

- 触发：助手给出 3 条链接预览，用户直接点击其中一条。
- 目标：系统直接打开对应项目详情介绍，而不是要求用户先进入完整结果页再找该项目。

#### 场景 4：用户需要完整结果集

- 触发：用户对预览方向满意，点击“查看全部结果”。
- 目标：主项目列表完全切换成这次自然语言搜索结果，并保留这是“AI 助手结果”的上下文提示。

#### 场景 5：查询模糊、无结果或失败

- 触发：用户输入过宽泛、歧义大或当前无合适项目的请求。
- 目标：系统返回可执行改写建议、热门项目回退或失败提示，而不是单纯空白。

### 关键用户路径

1. 用户在任意页面看到侧边助手入口并主动点击。
2. 用户输入自然语言请求，助手开始解释与检索。
3. 助手返回一段简短说明和最多 3 条项目超链接。
4. 用户选择：
   - 点击单条项目链接，直接打开项目详情介绍。
   - 点击“查看全部结果”，切换主列表到本次自然语言结果。
   - 继续追问，在当前会话上下文中细化条件。

## 4. Requirement Definition

### 需求 1：产品必须提供显式的侧边助手入口

- What：系统必须提供全局可见的侧边助手入口，作为自然语言搜索的主入口。
- Why：自然语言搜索不能继续只作为“零结果时的隐式补救能力”，否则用户无法主动发现和使用。
- Who：所有项目库用户。
- When：用户打开任意支持项目库浏览的页面时。
- Expected outcome：用户知道这里可以直接用自然语言找项目，而不是把它误认为普通搜索框的隐藏能力。

### 需求 2：原普通搜索与侧边助手必须分工明确

- What：原有项目搜索继续承担普通关键词搜索；侧边助手默认承担自然语言搜索。
- Why：如果普通搜索与自然语言搜索混在同一主入口里，用户难以理解系统何时按关键词匹配、何时按语义解释。
- Who：所有项目库用户。
- When：用户使用普通搜索框或侧边助手入口时。
- Expected outcome：用户不会因为“普通搜索偶尔触发语义扩展”而产生不可控或困惑的感受。

### 需求 3：侧边助手必须支持多轮会话记忆

- What：助手必须记住当前会话中的主题、子方向、用户限制条件、上一轮结果和最近几轮对话摘要，以支持连续追问。
- Why：用户的真实提问往往是“先找一个方向，再逐步收窄”，而不是每次完整重写查询。
- Who：连续追问型用户、快速探索型用户。
- When：用户在同一会话内继续输入“再给我几个”“更偏开源一点”“换成量化方向”等追问时。
- Expected outcome：用户输入“再给我几个”“更偏开源一点”“换成量化方向”时，系统能沿用前文上下文继续检索。

### 需求 4：多轮记忆必须是可控的会话记忆，而不是无边界长期记忆

- What：第一期多轮记忆只要求在当前浏览器会话内持续有效，并提供明确的“新对话”入口清空上下文；助手在面板再次打开时应继续展示当前对话历史，页面刷新后也应保留当前会话上下文。
- Why：本期目标是让连续追问成立，而不是提前引入长期用户画像、跨设备同步或不可感知的隐式记忆；同时用户不应因为轻微页面操作就丢失刚才的检索上下文。
- Who：连续追问型用户、轻量浏览型用户。
- When：用户关闭再打开助手面板、刷新页面、或点击“新对话”时。
- Expected outcome：用户能理解“当前对话在记什么”，能看到当前会话历史，并能随时主动重置，不会因为隐藏长期记忆而失控。

### 需求 5：助手成功态必须先展示轻量结果预览，而不是完整列表

- What：每轮成功查询后，助手必须先展示一段简短说明和最多 3 条项目超链接。
- Why：侧边助手的价值是“快速给方向感”，而不是在窄面板里复刻完整项目库浏览体验。
- Who：首次查询用户和连续追问用户。
- When：助手返回成功结果时。
- Expected outcome：用户能快速判断推荐方向是否正确，并通过点击链接继续深入。

### 需求 6：结果预览必须以超链接为主，不要求复杂卡片

- What：第一期结果预览以超链接列表为主；每条链接可附带一句极短理由，但不要求承载完整项目卡片信息。
- Why：当前目标是降低助手面板的信息密度，减少重复构建第二套项目浏览界面。
- Who：所有使用助手结果预览的用户。
- When：助手返回结果预览时。
- Expected outcome：助手看起来像“推荐入口”，而不是“第二个项目库页面”。

### 需求 7：点击单条项目链接必须在当前页面直接打开对应项目详情介绍

- What：用户点击助手里任意项目链接后，系统必须在当前页面打开对应项目详情介绍，侧边助手不得因为打开详情而消失、重置或丢失当前对话。
- Why：用户从预览进入详情的路径必须足够短，且详情查看后还要能继续追问；如果跳到独立页面导致助手消失，预览会退化成一次性跳转入口。
- Who：查看助手结果预览的用户。
- When：用户点击任意预览链接时。
- Expected outcome：用户把助手当成“快速去看项目详情并继续追问”的入口，而不是还要额外跳回列表再二次查找或重开对话。

### 需求 8：点击“查看全部结果”后主列表必须完全切换为本次结果

- What：用户点击“查看全部结果”后，主项目列表必须完全切换为本次自然语言搜索结果，而不是仅追加、混排或高亮。
- Why：用户需要一个清晰、完整的结果视图，知道当前正在浏览的是“这轮自然语言查询的全部结果”。
- Who：已经通过助手完成初步方向判断的用户。
- When：用户点击“查看全部结果”时。
- Expected outcome：完整结果视图的语义清晰，不与默认热门项目或普通关键词结果混在一起。

### 需求 9：系统必须显式区分助手结果态与默认项目库态

- What：当主列表已切换为助手结果时，页面必须明确告知用户当前是“AI 助手结果”，并允许用户返回普通项目库态。
- Why：如果主列表被替换但没有上下文提示，用户会失去对当前结果来源的判断。
- Who：浏览结果列表的用户。
- When：主列表由默认项目库态切换为助手结果态之后。
- Expected outcome：用户知道当前列表为何发生变化、如何返回默认状态、以及当前结果对应哪一轮查询。

### 需求 10：助手必须覆盖歧义、空结果与失败语义

- What：对于歧义查询、无结果查询和服务失败，助手必须分别给出清晰的用户可执行反馈，例如改写建议、热门项目回退或重试入口。
- Why：助手不能只在成功时工作；如果失败语义不清晰，用户会把“系统没理解”误判成“系统没有项目”。
- Who：输入过宽泛、过模糊或服务异常状态下的用户。
- When：助手返回歧义、空结果或失败状态时。
- Expected outcome：用户能区分“需要细化问题”“当前没有结果”和“服务暂时不可用”。

### 需求 11：敏感领域仍然必须保留站内搜索边界提示

- What：当用户查询金融、医疗、法律、安全等敏感领域时，助手仍然只返回站内项目搜索结果，并明确提示不提供真实专业建议。
- Why：新增助手入口后，用户更容易把它当作“能直接问”的助手，因此边界提示不能弱化。
- Who：输入敏感领域查询的用户。
- When：助手识别到金融、医疗、法律、安全等敏感领域查询时。
- Expected outcome：用户理解自己看到的是项目推荐入口，不是专业决策回答。

### 需求 12：侧边助手第一期不得演变成通用聊天产品

- What：第一期不要求长篇回答、自由对话知识问答、面板内分页浏览、复杂筛选或跨页面长期画像。
- Why：本需求的目标是“帮助找项目”，不是交付一个通用聊天机器人。
- Who：所有项目库用户与后续实现者。
- When：设计和实现侧边助手第一期时。
- Expected outcome：产品边界清晰，后续设计与实现不会被“多做一个聊天产品”带偏。

## 5. Interpretation Options

### 解读 A：“做一个侧边助手”

- 可能含义 1：做一个通用聊天机器人。
- 可能含义 2：做一个显式的自然语言项目搜索入口。
- 本次需求按“含义 2”为准。助手的核心任务是帮助用户找站内项目，不是提供开放问答。

### 解读 B：“支持多轮对话记忆”

- 可能含义 1：做长期、跨设备、可学习用户偏好的记忆系统。
- 可能含义 2：做当前会话内的上下文承接能力。
- 本次需求按“含义 2”为准。第一期只要求会话级连续追问成立。

### 解读 C：“展示搜索结果”

- 可能含义 1：在侧边栏里完整复刻项目库列表。
- 可能含义 2：先给少量预览，再把完整结果交给主列表。
- 本次需求按“含义 2”为准。助手负责预览与引导，主列表负责完整浏览。

### 解读 D：“点击结果看详情”

- 可能含义 1：点结果后只切换主列表或高亮项目。
- 可能含义 2：点结果后整页跳转到独立项目页。
- 可能含义 3：点结果后在当前项目页面内打开详情面板，同时保留侧边助手。
- 本次需求按“含义 3”为准。

## 6. Constraints

### 产品边界

- 侧边助手只负责站内项目搜索与推荐预览，不扩展为开放域聊天助手。
- 第一期开启多轮记忆，但记忆范围限定在当前浏览器会话内。
- 第一期结果预览只要求最多 3 条超链接，不要求复杂卡片和面板内完整浏览。

### 事实来源边界

- 助手结果仍然必须来自现有项目库和既有自然语言搜索链路，不得引入新的项目事实来源。
- 助手不能生成站外事实、真实专业建议、项目捏造结果或新的排序事实。

### 体验边界

- 普通搜索的即时关键词体验不得被助手能力替代或弱化。
- 助手必须提供“新对话”或等价重置入口，避免记忆不可控。
- 助手关闭后再次打开，应保持当前会话上下文，直到用户主动重置。
- 助手中的项目链接不得默认跳到没有助手的独立页面；第一期必须复用当前项目页详情打开能力，让助手在查看详情时继续存在。

## 7. Acceptance Criteria

### 验收 1：入口显式可发现

- 可观察结果：用户在产品中能稳定看到侧边助手入口，并通过它进入自然语言搜索流程。
- 成功条件：用户不需要依赖“普通搜索无结果”才意识到系统支持自然语言搜索。
- 失败条件：自然语言搜索仍只能通过普通搜索无结果隐式触发，或用户无法稳定找到助手入口。

### 验收 2：普通搜索与助手搜索分工清晰

- 可观察结果：普通搜索继续按关键词工作；助手作为自然语言搜索入口独立存在。
- 成功条件：用户能理解两个入口分别做什么，且主搜索框不会再承担隐式混合模式。
- 失败条件：普通搜索被改成不可预测的混合语义入口，或助手与普通搜索的职责在界面上不可区分。

### 验收 3：多轮追问成立

- 可观察结果：用户输入第二轮、第三轮追问时，系统能沿用上一轮主题与限制条件继续推荐。
- 成功条件：像“更偏开源一点”“再给我几个”“换成量化方向”这类追问不需要用户重写全部上下文。
- 失败条件：追问被当作完全独立查询处理，或刷新、关闭再打开面板后当前会话上下文非预期丢失。

### 验收 4：成功态先给 3 条轻量预览

- 可观察结果：助手成功返回时，先显示简短说明和最多 3 条项目超链接。
- 成功条件：用户可以只通过这 3 条链接快速判断方向是否正确，而不是立即面对完整列表。
- 失败条件：助手直接把完整项目列表塞进侧边栏，或成功态没有项目链接预览。

### 验收 5：点击链接直接进详情

- 可观察结果：用户点击助手里的任意项目链接后，系统在当前页面打开该项目详情介绍，侧边助手仍然可见且保留当前对话。
- 成功条件：用户不需要再回到列表做二次定位，也不需要重新打开助手或重建上下文。
- 失败条件：点击链接后跳到没有助手的独立页面，或详情打开导致助手消失、重置、丢失对话。

### 验收 6：查看全部结果语义明确

- 可观察结果：用户点击“查看全部结果”后，主项目列表完全切换为该轮自然语言搜索结果。
- 成功条件：用户能明确知道当前正在浏览的是“这次助手查询的全部结果”，并能返回默认项目库态。
- 失败条件：结果被追加、混排或高亮在默认列表中，或页面没有说明当前列表来自助手查询。

### 验收 7：异常态可区分

- 可观察结果：歧义、无结果、失败三种情况的提示不同，且都提供下一步可执行操作。
- 成功条件：用户能区分“我需要换种说法”“当前没有匹配项目”“服务暂时不可用”。
- 失败条件：歧义、空结果和服务失败都显示同一类空白或泛化错误提示。

### 验收 8：敏感领域边界可见

- 可观察结果：金融、医疗、法律、安全等查询中，助手显示站内项目搜索边界提示。
- 成功条件：用户不会把项目推荐结果误解为专业建议输出。
- 失败条件：助手对敏感领域查询输出真实专业建议，或只展示项目结果但没有边界提示。

## 8. Risks & Gaps

### 主要风险

- 如果多轮记忆过强且缺少重置入口，用户会失去对当前上下文的控制感。
- 如果助手返回内容过长，它会从“项目推荐入口”滑向“聊天回答面板”，削弱结果清晰度。
- 如果“查看全部结果”切换主列表后没有明确提示，用户会误以为列表被无原因改写。
- 如果点击预览链接不能直接打开详情，助手预览会退化成低价值中间层。
- 如果点击预览链接变成整页跳转且目标页没有助手，连续追问链路会断裂。

### 当前缺口

- 设计阶段仍需明确侧边助手的视觉样式、展开方式、移动端形态和微文案，但这些属于设计承接问题，不阻塞需求冻结。
- 设计阶段仍需定义“AI 助手结果”提示条的具体位置与样式，但其产品语义已经冻结。

### 隐含假设

- 用户接受第一期助手更像“项目推荐入口”而不是“长回答聊天框”。
- 用户接受多轮记忆是会话级能力，而不是长期个性化画像。
- 现有项目库覆盖度足以支撑第一期的预览推荐；如果项目本身不存在，助手仍然只能给出改写建议或热门回退。

## 9. Open Questions

当前无阻塞需求冻结的产品级开放问题。

仍可留给设计阶段决定的非阻塞问题：

1. 侧边助手入口使用图标、文字按钮还是图标加短标签的组合。
2. 预览超链接后是否始终附带一句短理由，还是在高密度场景下允许仅显示项目名。
3. “AI 助手结果”提示条放在主列表上方还是页面级状态区。

以上问题不影响需求进入设计阶段。
