# 自然语言模糊搜索与推荐需求分析

## 文档状态

- 状态：`READY`
- 需求级别：`S2 - Medium Feature`
- 分析方法：依据 [需求分析_skill.md](需求分析_skill.md#L1) 输出
- 本文目标：重新冻结“项目库搜索在原始查询无结果时，由 LLM 判断语义、提取关键词并扩展查询”的产品需求边界。
- 重写原因：上一版方案过度依赖预置规则、敏感词白名单与 `rules-first` 判断，无法覆盖用户未命中预设条件但按常识应被理解的查询。

## Requirement Size

`S2 - Medium Feature`

判定原因：

- 本需求改变项目库搜索的查询链路和失败语义，但不改变底层项目发现、评分、日报、周报与 mission discovery 主链路。
- 它会影响前端搜索体验、后端 LLM 查询解释、查询扩展、结果回退、缓存与可观测诊断。
- 它不要求重新生成项目事实，也不引入新的外部搜索源；LLM 只解释用户查询，不直接生产推荐事实。

## 1. Background

### 需求来源

- 项目库原有搜索在用户输入已有项目名、公司名、repo 名、方向词或已有中文别名时本来可用，不能因为加入 LLM 模糊搜索而变慢、变贵或改变结果。
- 当前新增模糊搜索方案把大量判断写死在代码条件里，例如预置敏感词、预置口语白名单、预置 intent 触发词。这能处理少数样例，但无法处理用户没命中预置条件、却按常识明显有语义的查询。
- 用户真正希望的是：原始搜索能查到就沿用原能力；原始搜索查不到时，系统不要直接空白，而是让 LLM 判断这句话有没有实际语义、应提取哪些关键词、是否需要扩展查询或只展示热门项目。

### 业务背景

- 当前项目库的搜索主要由 `app/visualConsole/clientScript.ts` 本地执行，核心是 `rankProjectSearchMatch` 和 `filterAndSortProjectCards`，基于项目名、简介和 `data-project-search` 元数据做精确、前缀、子串和 token 匹配。
- `app/visualConsole/ossProjectsPage.ts` 已经把 repo、公司别名、方向别名、tags、描述、why_today、direction_matches 等信息写入项目搜索元数据，因此“本来能查到的词”应优先使用这条快速本地链路。
- 当前仓库没有 `src/recommendation` 服务层，后续实现需要新增查询解释层，但它必须消费现有项目库索引和 artifact，不得成为新的项目事实来源。

### 用户动机

- 用户希望输入“电商 agent”“医疗 agent”“股票研究”“最近有什么值得看”“这怎么哈哈了”这类非精确词时，系统能给出更合理的结果或回退，而不是只有空结果。
- 用户不想为已经能搜到的词支付 LLM 延迟；例如 `claw`、`memory`、`字节`、`电商`、`UI-TARS` 这类查询如果原始搜索已有结果，就应立即返回。
- 用户希望系统对敏感或高风险领域有常识判断能力，而不是只靠代码里提前列好的几个词。

## 2. Goals

### 产品目标

- 建立一条明确的查询分流原则：`原始查询有结果 -> 不触发 LLM`；`原始查询无结果 -> 交给 LLM 做语义判断与查询扩展建议`。
- 让无结果查询不再只有“空列表”，而是根据语义类型进入不同结果策略：热门项目、扩展查询结果、边界提示或澄清。
- 让 LLM 负责常识层面的语义分类、关键词提取、领域敏感性判断和查询扩展计划，但不直接生成项目或排序事实。
- 保留项目库已有搜索的速度、可解释性和本地可用性。

### 用户价值

- 已有词仍然像原来一样好用，不被 LLM 改写或延迟。
- 用户输入原先查不到的自然语言请求时，更大概率看到相关项目。
- 用户输入无意义或混乱表达时，不会被错误扩展成奇怪结果，而是保留原查询并展示热门项目。
- 用户输入股票、医疗、法律、金融、网络安全等敏感领域相关请求时，系统不判断用户是否在请求专业建议，只抽取查询句中的领域关键词并用于站内项目库搜索，同时明确结果只是项目搜索结果。

## 3. Users & Scenarios

### 用户角色

- 项目扫描型用户：习惯在项目库里快速搜索具体项目、公司、方向词。
- 模糊探索型用户：只知道想看的大概方向，不知道系统里的准确标签。
- 垂直场景用户：输入“股票研究”“医疗助手”“客服工单”“电商导购”等业务场景词，希望看到相关 agent 项目。
- 随手输入型用户：会输入口语、半句、语义混乱甚至玩笑式文本。

### 使用场景

#### 场景 1：原始查询已有结果

- 触发：用户输入 `memory`、`字节`、`电商`、`UI-TARS`、`shopping-commerce-agent` 等已有索引可命中的词。
- 目标：系统直接展示原始搜索结果，不调用 LLM，不改写查询。
- 用户感知：搜索仍然即时响应，结果与加入 LLM 前保持一致。

#### 场景 2：原始查询无结果，但有明确名词或方向

- 触发：用户输入“股票研究 agent”“医疗问诊 agent”“帮客服处理工单的项目”“导购自动化”。
- 目标：LLM 提取名词、场景、任务和可扩展关键词，系统用扩展后的查询条件重新搜索项目库。
- 用户感知：原来空白的查询可以返回相关项目，且能看到系统提取了哪些关键词。

#### 场景 3：原始查询无结果，且语义混乱或无实际检索意图

- 触发：用户输入“这怎么哈哈了”“啊这是什么鬼”“随便看看嘛”。
- 目标：LLM 判断为低语义或无明确检索目标，不生成扩展词；系统保留用户原查询，并只展示热门项目。
- 用户感知：系统没有乱猜，不把无意义文本硬扩展成错误方向。

#### 场景 4：原始查询无结果，且是开放式发现请求

- 触发：用户输入“最近有什么值得看”“现在最火的方向”“给我看看新东西”。
- 目标：LLM 判断为泛探索，不提取狭窄关键词；系统展示当前热门项目或热门方向。
- 用户感知：即使没有具体关键词，也能进入可浏览结果。

#### 场景 5：原始查询无结果，且包含敏感或高风险领域

- 触发：用户输入“医疗诊断 agent”“股票投资 agent”“美股今天买什么”“帮我做漏洞利用”。
- 目标：LLM 抽取敏感领域关键词、任务词和对象词，系统直接按这些关键词扩展搜索站内项目库。
- 用户感知：即使输入像“美股今天买什么”“给我诊断这个病”这样的句子，系统也按金融/医疗等关键词检索相关 AI Agent 项目，但不输出真实投资、医疗、法律或安全建议。

### 触发条件

- 只在原始项目库搜索结果数为 `0` 时触发 LLM。
- 原始搜索结果数大于 `0` 时，无论 LLM 是否可能给出更丰富的扩展，都不触发 LLM。
- LLM 触发前必须使用与当前项目库一致的搜索索引和过滤条件，不能用另一套“预判是否该问 LLM”的规则替代原搜索。

### 关键用户路径

1. 用户在项目库输入查询词。
2. 系统先运行现有本地搜索。
3. 若有结果，直接展示结果并结束。
4. 若无结果，系统把原始查询交给 LLM 做结构化语义判断。
5. 系统根据 LLM 的结构化输出选择：扩展查询、展示热门项目、提示边界或请求澄清。
6. 最终展示仍只来自项目库已有项目和排序字段，不展示 LLM 生成的虚构结果。

## 4. Requirement Definition

### 需求 1：已有直接命中查询不得触发 LLM

- What：用户输入任何能被当前项目库搜索直接命中的查询时，系统必须沿用原始搜索结果，不触发 LLM。
- Why：这类查询在加入模糊搜索前就已经好用，LLM 只会增加延迟、成本和行为漂移。
- Who：所有项目库搜索用户。
- When：原始查询在当前过滤条件下至少命中 1 个项目。
- Expected outcome：用户看到和原有搜索一致的结果，且无 LLM 加载态。

### 需求 2：原始搜索无结果时必须进入 LLM 语义路由

- What：除已有直接命中查询外，所有无结果查询都应交给 LLM 判断语义类别、关键词、扩展策略和边界。
- Why：无结果查询原本无法返回内容，正是模糊搜索要解决的范围；代码预置条件无法覆盖用户真实表达。
- Who：模糊探索型用户、垂直场景用户、随手输入型用户。
- When：原始搜索结果数为 0，且查询非空。
- Expected outcome：原本空白的查询进入可解释的二级处理，不再只显示“没有匹配项目”。

### 需求 3：LLM 必须区分“无实际语义”和“有语义但需要扩展”

- What：LLM 至少必须区分低语义/混乱表达、泛探索请求、有明确名词或任务的请求、属性过滤请求、敏感领域关键词查询和歧义请求。
- Why：不同类型的无结果查询需要完全不同的响应；把所有无结果都扩展关键词会制造噪声。
- Who：所有无结果查询用户。
- When：LLM 接收原始无结果查询后。
- Expected outcome：混乱输入不会被强行扩展；有明确名词的输入能提取关键词并扩展查询。

### 需求 4：有明确关键词或名词的查询必须提取关键词并扩展查询条件

- What：当用户查询中包含领域名词、任务名词、技术名词、公司/项目线索或对象属性时，LLM 应抽取这些词，并给出用于项目库搜索的扩展查询计划。
- Why：用户常用自然语言表达场景，而不是系统已有标签；需要从“句子”转成“项目库可搜索词组”。
- Who：垂直场景用户、模糊探索型用户。
- When：原始查询无结果但含有实际语义。
- Expected outcome：系统用扩展后的关键词重新搜索，并展示命中的站内项目。

### 需求 5：敏感领域必须由 LLM 抽取关键词并转为站内项目搜索

- What：股票、医疗、法律、金融、网络安全等领域不能只靠代码里预置的关键词判断；LLM 必须从整句中抽取可用于站内项目库搜索的领域、任务、对象和技术关键词。
- Why：用户可能用没被预置的表达触发同类领域；硬编码无法覆盖常识语义，但 V1 不需要判断用户是否真的在请求专业建议。
- Who：垂直场景用户、深度探索用户。
- When：无结果查询涉及可能敏感或高风险领域。
- Expected outcome：系统能把“医疗 agent 项目”“股票研究 agent 项目”“美股今天买什么”“给我诊断这个病”等输入统一转成站内项目关键词搜索；结果只来自项目库，且不输出真实专业建议。

### 需求 6：无语义或泛探索查询只展示热门项目，不生成扩展词

- What：当 LLM 判断查询没有清晰检索目标，或只是泛泛“看看有什么”时，系统应保留原查询文本，但结果区域展示默认热门项目。
- Why：这类查询不适合关键词扩展；强行扩展会让用户误以为系统理解了不存在的意图。
- Who：随手输入型用户、趋势扫描型用户。
- When：LLM 输出 `low_semantic` 或 `open_discovery` 类别。
- Expected outcome：用户看到当前热门项目，而不是与混乱文本相关的伪匹配。

### 需求 7：LLM 不得直接生成项目、事实或最终排序

- What：LLM 只能输出结构化查询解释、关键词、扩展查询、过滤建议和边界说明；最终项目列表必须由系统使用现有项目库索引检索得到。
- Why：项目库结果必须可追溯到现有 artifact，不能变成 LLM 幻觉结果。
- Who：所有用户，以及后续实现者。
- When：任何 LLM 模糊查询路径。
- Expected outcome：所有展示项目都存在于当前项目库，排序仍来自现有项目字段和既有排序逻辑。

### 需求 8：LLM 结果必须可降级、可缓存、可审计

- What：系统必须记录 LLM 是否触发、分类结果、扩展词、是否命中、失败原因，并对相同日期/查询/过滤条件缓存解释结果。
- Why：LLM 调用有成本、延迟和失败风险，且后续需要验证“已有词未触发 LLM”和“无结果词正确触发 LLM”。
- Who：用户、维护者、测试和调试人员。
- When：每次无结果查询触发 LLM 时。
- Expected outcome：实现者能定位为什么某个查询进入热门回退、扩展查询或边界提示。

## 5. Interpretation Options

### 关键请求 A：“项目中本来就能直接查询的词不需要触发 LLM”

- 解释 A1：维护一份“不触发 LLM 的关键词列表”。
- 解释 A2：直接运行当前搜索函数，只有结果数为 0 才触发 LLM。
- 推荐冻结：采用 `A2`。
- 原因：只有真实搜索结果才能代表“本来就好用”；维护关键词列表会再次回到硬编码条件。

### 关键请求 B：“除了 1 之外的查询词原先都查不到，因此希望输入这些查询时能够出现结果”

- 解释 B1：无结果时统一展示热门项目，不做语义理解。
- 解释 B2：无结果时先让 LLM 分类；有语义则扩展查询，无语义或泛探索才展示热门项目。
- 推荐冻结：采用 `B2`。
- 原因：用户输入“股票研究 agent”和“这怎么哈哈了”都无结果，但前者应扩展，后者不应扩展。

### 关键请求 C：“敏感判断不能只靠代码预置条件”

- 解释 C1：继续扩充敏感词库。
- 解释 C2：让 LLM 根据整句语义做常识判断，并把判断限制在结构化输出枚举内。
- 推荐冻结：采用 `C2`。
- 原因：敏感性来自语义上下文，不只来自单个词；但输出仍需结构化，不能让 LLM 自由发挥。

### 关键请求 D：“LLM 分类还可以有哪些种类”

- 推荐分类：
  - `low_semantic`：混乱、玩笑、无实际检索意图。
  - `open_discovery`：泛探索，如“最近有什么值得看”。
  - `topic_keyword`：包含明确领域名词、技术名词、公司或项目线索。
  - `task_use_case`：描述任务或使用场景，如“帮客服处理工单”。
  - `attribute_filter`：包含风险、热度、持续性、新鲜度等过滤或排序意图。
  - `regulated_keyword_search`：涉及敏感领域，按查询句关键词转为站内项目库搜索。
  - `ambiguous`：多个解释冲突，扩展可能明显误导，需要澄清。
- 推荐冻结：V1 采用以上 7 类作为 LLM 主分类。
- 原因：这组分类能覆盖用户当前提出的三类样例，并补齐任务型、属性型、泛探索、边界型和歧义型查询。

## 6. Constraints

### 数据归属与真相边界

- LLM 不得访问外部搜索作为项目结果来源。
- LLM 不得生成不存在于项目库中的项目名、repo、评分、趋势事实或推荐排名。
- 扩展查询只能作用于当前项目库索引、项目字段和已有 artifact。
- 敏感领域的承接只代表“检索相关 AI Agent 项目”，不代表医疗、金融、法律或安全建议。

### 业务规则约束

- 原始搜索命中数大于 0 时，禁止触发 LLM。
- 原始搜索无结果时，LLM 是默认二级路由，而不是只在命中特定代码条件时触发。
- LLM 输出必须是结构化 JSON，且只能使用设计文档冻结的枚举。
- LLM 输出的扩展查询必须再经过系统检索；如果扩展查询仍无结果，系统必须按类别回退，而不是展示 LLM 文本答案。
- `low_semantic` 不允许产生扩展词。
- `regulated_keyword_search` 必须展示项目搜索边界提示，且不得输出专业建议或行动步骤。

### 兼容性约束

- 保留当前项目库本地搜索体验。
- 保留无 LLM 环境的基础可用性：直接搜索仍可用，无结果时至少能展示热门项目和“LLM 不可用”的降级状态。
- 不要求本次需求修改 daily / weekly artifact schema。
- 不要求本次需求引入用户登录态、长期个性化记忆或查询历史持久化。

## 7. Acceptance Criteria

### 验收 1：已有直接搜索词不触发 LLM

- 可观察结果：输入 `memory`、`字节`、`电商`、`UI-TARS` 等当前索引可命中的词时，系统直接展示结果。
- 成功条件：LLM 调用计数为 0，结果与原搜索一致。
- 失败条件：已有词触发 LLM，或被 LLM 改写后结果变化。

### 验收 2：无结果且有明确名词的查询可返回扩展结果

- 可观察结果：输入“帮客服处理工单的 agent”“医疗工作流 agent”等原始无结果查询时，系统通过 LLM 提取关键词并重新搜索。
- 成功条件：扩展查询命中项目库中相关项目，并展示提取的关键词或解释摘要。
- 失败条件：系统直接空白，或 LLM 生成不存在项目。

### 验收 3：无意义查询不生成扩展词

- 可观察结果：输入“这怎么哈哈了”时，LLM 分类为 `low_semantic`，系统保留原查询并展示热门项目。
- 成功条件：没有扩展关键词，没有伪相关结果。
- 失败条件：系统把混乱文本扩展成某个方向并过滤出误导结果。

### 验收 4：泛探索查询展示热门项目

- 可观察结果：输入“最近有什么值得看”时，系统分类为 `open_discovery`，展示热门项目或当前默认项目流。
- 成功条件：不要求用户输入精确词，也不返回空白。
- 失败条件：系统要求用户重新输入关键词，或随机抽取不相关项目。

### 验收 5：敏感领域按关键词承接为站内项目搜索

- 可观察结果：输入“股票研究 agent 项目”“美股今天买什么”“给我诊断这个病”时，系统抽取金融/股票/医疗/诊断等关键词并搜索站内项目库。
- 成功条件：结果只来自项目库，界面明确这是相关 AI Agent 项目搜索，不提供真实投资、医疗、法律或安全建议。
- 失败条件：系统输出真实专业建议、生成不存在项目，或因为用户句子像建议请求就拒绝搜索。

### 验收 6：LLM 输出不可越权

- 可观察结果：LLM 返回的扩展词被系统执行检索，最终展示项目都来自当前项目库。
- 成功条件：结果列表没有 LLM 幻觉项目，排序仍沿用现有字段。
- 失败条件：LLM 直接输出项目答案并进入 UI。

### 验收 7：LLM 不可用时可降级

- 可观察结果：关闭 LLM 后，已有直接搜索仍正常；无结果查询显示热门项目和降级状态。
- 成功条件：项目库搜索不因 LLM 不可用而整体不可用。
- 失败条件：无 LLM 时搜索入口报错、卡死或空白。

### 验收 8：调用链路可审计

- 可观察结果：测试或日志能区分 direct-search、llm-expanded、regulated-keyword-search、hot-only、llm-failed fallback。
- 成功条件：维护者能解释每次无结果查询为什么进入某个结果策略。
- 失败条件：LLM 决策不可见，无法判断是分类错、扩展错还是项目库确实无结果。

## 8. Risks & Gaps

### 风险

- LLM 可能过度扩展，把低语义查询误判成有语义查询。
- LLM 可能把敏感领域关键词扩展得过宽，导致项目结果不相关或边界说明不清。
- 如果前端对每次输入字符都触发 LLM，会导致延迟和成本不可控。
- 如果扩展查询逻辑与原始搜索逻辑不一致，会出现“明明原搜索有结果却触发 LLM”的回归。
- 如果只展示热门项目但不保留原查询，用户会误以为系统把他的输入清空了。

### 当前缺口

- 设计阶段必须冻结 LLM prompt、输出 JSON schema、结果策略映射和非法输出修复策略；冻结后不得在实现阶段改成自由文本回答或项目生成。
- 实现阶段必须把当前前端搜索逻辑抽成可复用的 server/client 一致函数，避免 direct gate 和扩展检索使用两套口径。
- 实现阶段必须把触发时机、缓存键、降级状态和诊断字段写入验收测试，避免 LLM 路由退化成不可审计的 best-effort 行为。

### 隐含假设

- 用户接受“已有词不触发 LLM”带来的行为：即使 LLM 可能能扩展出更多结果，只要原始搜索已有结果，就优先保持原体验。
- 用户接受无意义或泛探索查询展示热门项目，而不是要求系统解释“这句话没有意义”。
- 项目库当前元数据足够承接第一版扩展查询；如果元数据本身没有相关项目，系统只能给出无结果或热门回退。

## 9. Resolved V1 Decisions

1. LLM 触发时机：V1 同时支持输入稳定后自动触发和 Enter / 点击搜索立即触发；自动触发必须满足 debounce、请求取消、缓存、最小字符长度和 direct result 为 0，禁止每个输入字符直接调用 LLM。

2. UI 解释粒度：无结果查询触发 LLM 后，UI 必须显示简短解释或关键词摘要；不得显示大段对话式回答，也不得在 direct results 路径展示“AI 已优化搜索”。

3. `regulated_keyword_search` 边界提示：V1 每次在 LLM 路径返回敏感领域关键词搜索时，都显示紧凑边界提示，例如“仅按站内 AI Agent 项目检索，不提供医疗/投资/法律/安全建议”。V1 不依赖用户历史或同查询折叠状态。

4. 弱命中扩展：V1 不允许。只要原始搜索结果数大于 0，就不触发 LLM，也不追加 LLM 补充结果。
